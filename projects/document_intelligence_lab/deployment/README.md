# От локального сервиса к одному облачному запуску

Задача этого этапа — перенести уже проверенный CPU-сервис, объяснить его права
и стоимость, а затем убрать созданные ресурсы. Это не курс облачной инфраструктуры.
Начинайте после R04 в [плане](../../../docs/superpowers/plans/2026-10-11-remaining-roadmap.md#r04)
и существующего [урока Docker](../../../modules/02_python_backend/09_docker_delivery/README.md).

**Текущая граница: подготовка маршрута; deployment NOT_RUN.** Провайдер, регион,
лимит расходов и доступ ещё не выбраны. До их согласования ниже нет команд,
создающих ресурсы, и нет обещания бесплатного тарифа. Локальный API или контейнер
не является доказательством облачного запуска.

## Интуиция и границы доступа

На ноутбуке процесс читает файл модели с диска. В облаке файл обычно лежит
отдельно от временного диска процесса. Object storage (объектное хранилище)
хранит байты по ключу; это не обязательно диск, к которому приложение может
применять обычные файловые операции. Перед запуском приложение получает
согласованный bundle и проверяет его целостность.

```text
пользователь ── запрос ──> вход сервиса ──> validation ──> prediction
                               │                            │
                               │                     загруженный bundle
                               │                            ↑
                      только нужные логи             startup: read
                                                            │
                                                    private storage

service identity ── право читать выбранный bundle ────────────┘
оператор         ── право выпустить/откатить версию
клиент API       ── НЕ выбирает путь модели и НЕ имеет ключей хранилища
```

Service identity — учётная сущность приложения, а не личный пароль разработчика.
Least privilege (минимальные права) означает разрешить нужное действие над нужным
ресурсом: например, чтение выбранного набора объектов, без удаления всех данных.
Точное выражение прав зависит от выбранного провайдера.

Secret injection — передача секретов процессу через механизм окружения или
управляемого хранилища, а не запись в образ, исходники или отчёт. Переменная
окружения сама по себе не делает секрет безопасным: не печатайте её в логи,
диагностику или ответы API. Используйте workload identity без долгоживущих ключей,
если выбранный сервис это поддерживает.

## Разобранный сценарий без создания ресурсов

Представьте две уже проверенные версии: A и B. A использует preprocessing v1,
B — v2. Перед выпуском B сохранены оба целых bundle, их digest и конфигурации.

| Событие | Что проверяет оператор | Что не следует заключать |
| --- | --- | --- |
| Процесс B стартовал | Загружены согласованные model + preprocessing, пробный запрос работает | Что B качественнее A |
| Readiness B успешна | Этому процессу можно передать запрос в заданном контракте | Что все зависимости мира доступны |
| На фиксированных запросах B выдаёт ошибки | Причину, число запросов, версии, время и область отказа | Что надо немедленно переобучать модель |
| Возврат A | Восстановлен весь bundle A; повторный запуск и ответы совпадают | Что смена строки `active=A` сама всё восстановила |
| Очистка | Сопоставлены реальные ресурсы с записанным списком | Что остановка процесса удалила диски, образы и логи |

Это учебный сценарий, не журнал выполненного deployment. Реальные имена ресурсов,
время, ответы и стоимость заполняются только после запуска.

Частая ошибка — открыть сервис в интернет «на минуту» без ограничений. Для первого
опыта определите, кто имеет доступ, как ограничены запросы и что происходит при
ошибке. Не публикуйте учебную модель с персональными данными или открытым endpoint
загрузки произвольных файлов. Public URL не обязателен для доказательства переноса.

## Что согласовать до команд запуска

Заполните [карточку запуска](launch-card.md) самостоятельно. Нужны один провайдер
и сервис, регион, разрешённые данные, способ доступа, небольшой CPU-профиль,
верхняя граница расходов и срок жизни ресурсов. GPU и vLLM остаются отдельным R08:
для переноса первого классификатора они не требуются.

Далее порядок такой:

1. Проверить актуальные официальные команды выбранного сервиса и цены выбранного
   региона. Подготовить точные имена только новых учебных ресурсов.
2. Зафиксировать образ/зависимости и bundle. Проверить минимальные права и секреты
   без публикации значений. Сохранить перечень создаваемых ресурсов для cleanup.
3. Явно запустить один сервис. Проверить liveness, readiness, invalid input и
   parity на тех же безопасных текстах, что локально.
4. Наблюдать ограниченное число запросов. Сохранить counts, ошибки, задержки,
   версии и реальные расходы/их доступную оценку с единицами.
5. Провести restart и контролируемый rollback A → B → A с повторной проверкой.
6. Удалить только ресурсы из согласованного списка. Проверить отсутствие оставшихся
   вычислений, хранилищ и других платных объектов; учесть задержку обновления billing.

Budget alert — сигнал, не обязательно жёсткий выключатель. Даже при лимите бюджета
нужны срок жизни и проверка cleanup. Не считайте любой stop подтверждением
прекращения всех расходов.

## Самостоятельная вариация

Не меняя модель, предложите вариант «сервис доступен только вам» и вариант
«небольшая группа пользователей». Объясните отличия в доступе, наблюдении,
ограничениях запросов и стоимости. Привяжите решения к существующему
`production-product-study`, не создавая новый проект.

Вопросы для защиты:

1. Какие байты нужны новому процессу, кроме весов?
2. Почему хеш модели не заменяет права доступа к хранилищу?
3. Какие сведения нельзя писать даже в диагностический лог?
4. Чем readiness отличается от оценки качества на test split?
5. Какие ресурсы могут остаться после остановки контейнера?
6. Почему бюджетное уведомление не гарантирует прекращения расходов?

## Проверка результата

Техническая приёмка потребует sanitized журнал launch/smoke/restart/rollback/cleanup,
записанные версии, перечень ресурсов и подтверждение их удаления. Отдельно ученик
объясняет выбор режима и стоимость. До выбора провайдера точная инструкция и
внешний запуск остаются **AWAITING_CHOICE / NOT_RUN**, а не «готовое облако».

Переиспользуйте [rollout и incident response](../../../modules/08_production_ai/06_rollout_incidents/README.md)
для критериев отката. Внешние provider-specific ссылки и команды добавляются
после выбора сервиса, чтобы не оставлять непроверенные альтернативы.
