# Проверка качества AI-сервиса перед релизом

ID `document-release-eval`. Вы заменили генератор в сервисе поиска по документам. Один удачный ответ ещё не подсказывает, надо ли выпускать новую версию. Здесь вы проведёте одни и те же вопросы через два варианта API, найдёте причину изменения по трассе и примете решение о релизе.

Начните после [сквозного RAG](../../../labs/03_real_rag/end_to_end/README.md) и [модуля об эксплуатации](../../../modules/08_production_ai/README.md). Потребуется Python 3.12 из окружения проекта. Учебный прогон работает без сети, ключей, весов и дополнительных пакетов.

## Авторский пример — найдите пропавший контекст

Выполните из корня репозитория. Для каждого запуска нужен новый выходной каталог.

```powershell
python -m projects.document_intelligence_lab.release_eval.run --output-dir generated-reports/release-eval/demo
python -m projects.document_intelligence_lab.release_eval.run --candidate regressed --output-dir generated-reports/release-eval/regression
```

Откройте `report.json` в обоих каталогах. В примере три вопроса имеют ответ, два требуют отказа. Поиск считает общие слова с публичными документами. Генератор возвращает первую фразу выбранного фрагмента. Одна учебная замена добавляет к слову *digitisation* поисковый термин *scanner*. Вторая вдобавок сокращает бюджет контекста до двух символов. Обе используют архивные [документы и вопросы](../../../labs/03_real_rag/fixtures/) и [готовую сборку контекста](../../../modules/06_rag/05_grounded_answers/example.py).

| Вариант | Релевантный документ найден | Верный ответ или обоснованный отказ | Выход процесса |
| --- | --- | --- | --- |
| Baseline без расширения запроса | 2 из 3 | 4 из 5 | Служит точкой сравнения |
| Candidate с расширением | 3 из 3 | 5 из 5 | 0 |
| Regressed с крошечным контекстом | 3 из 3 | 2 из 5 | 1 |

Найдите у `regressed` случай `q-exact`. В `retrieved_ids` есть `A-SCAN@1:p1`, но `context_ids` пуст. Сервис отдаёт `no_answer` без вызова модели. Результат указывает на бюджет сборки контекста. По `trace_id` найдите тот же запрос в `traces.json`. От корневой операции `document.answer` идут два дочерних этапа `retrieval` и `generation`. Последний включает решение пропустить вызов при пустом контексте. В трассе хранятся идентификаторы, связи, время и технический статус. Вопрос, текст документа, ответ и HTTP-заголовки туда не попадают.

## Как читать измерения

| Поле | Что измерили |
| --- | --- |
| `quality_rate` | Доля верных исходов среди всех вопросов. У ответимого вопроса нужны цитата из релевантного источника и одна из размеченных фраз. У неответимого нужен явный `no_answer`. |
| `retrieval_hit_rate` | Доля ответимых вопросов, для которых в top-1 попал релевантный фрагмент. |
| `abstention_rate` | Доля корректных отказов среди вопросов без разрешённого ответа. Некорректный JSON генератора получает `invalid_output`. |
| `latency_p95_ms` | Ближайший ранг вверх в отсортированных задержках запроса. При пяти вопросах это максимум. В живом режиме время включает HTTP до API и, когда есть контекст, обращение к генератору. |
| `input_units`, `output_units`, `estimated_cost_usd` | Офлайн считается число слов как грубая мера объёма. В живом режиме используются только токены, сообщённые сервером. Если заданы обе цены за миллион токенов, стоимость равна `(input × цена входа + output × цена выхода) / 1 000 000`. Без тарифа значение остаётся `null`. |

Правила релиза фиксируются до запуска. Кандидат должен сохранить каждый прежний правильный ответ и каждый прежний релевантный результат поиска, верно ответить минимум на 2/3 ответимых вопросов и корректно отказаться во всех случаях без ответа. Можно добавить потолок p95 через `--max-p95-ms` и суммарного выхода через `--max-output-units`. Время и trace ID меняются при повторе, офлайн-решение по умолчанию воспроизводимо. Для решения о производительности повторите измерения после прогрева, поменяйте порядок A/B и укажите нагрузку.

Код 0 означает, что кандидат прошёл указанные правила. Код 1 сохраняет отчёт с причинами в `violations` и блокирует релиз. Код 2 означает, что сравнение не завершилось. Проверьте настройки, доступность сервера, совпадение alias и выдачу `usage` с числом токенов. В новом доступном каталоге останутся `failure.json` и доступные трассы.

## Живое сравнение двух версий модели

Подготовьте два локальных OpenAI-совместимых сервера, либо один сервер с двумя модельными alias. Для каждого запишите точный alias и проверенную ревизию весов, например SHA-256 файла GGUF. Серверу нужны JSON-ответы, поле `model` с запрошенным alias и `usage.prompt_tokens` / `usage.completion_tokens`. Стартовый вариант сервера с закреплёнными весами показан в [рабочем процессе GitHub](../../../.github/workflows/release-eval.yml). Сам runner модели не скачивает.

Команда PowerShell ниже показывает форму эксперимента. Подставьте адреса, alias и ревизии своих развернутых моделей. Сначала запустите её на демонстрационном наборе. Для самостоятельного прогона добавьте `--cases` и укажите отдельный каталог результатов по инструкции ниже.

```powershell
$module = 'projects.document_intelligence_lab.release_eval.run'
$models = @(
  '--mode', 'local', '--candidate', 'matched',
  '--endpoint', 'http://127.0.0.1:8080/v1/chat/completions',
  '--model', 'archive-a', '--model-revision', '<revision-A>',
  '--candidate-endpoint', 'http://127.0.0.1:8081/v1/chat/completions',
  '--candidate-model', 'archive-b', '--candidate-model-revision', '<revision-B>'
)
python -m $module @models --output-dir generated-reports/release-eval/models
```

`matched` оставляет одинаковыми поиск, лимит контекста, prompt и параметры декодирования. При одинаковых входах можно отнести различие ответов к сравнению двух конфигураций генератора. Обе идентичности записаны в `baseline.model` и `candidate.model`. Runner сверяет alias каждого ответа. Указанную ревизию нужно независимо подтвердить байтами весов или манифестом сервера. Рекомендуется повторить запуск, чтобы оценить вариативность. Для изучения изменения поиска на одной живой модели опустите все параметры `--candidate-*` и выберите `--candidate candidate`.

В живом режиме runner запускает временный локальный HTTP-сервис и для каждого случая выполняет настоящий `POST /answer`. Если модель требует авторизации, ключ первого сервера передайте через окружение `RELEASE_EVAL_API_KEY`, второго — через `RELEASE_EVAL_CANDIDATE_API_KEY`. Разные тарифы укажите парами `--input-usd-per-million` / `--output-usd-per-million` и `--candidate-input-usd-per-million` / `--candidate-output-usd-per-million`. Полученная оценка по тарифу не включает время собственной машины и её энергопотребление.

### Просмотр реальной трассы через OpenTelemetry

При наличии OpenTelemetry Collector откройте отдельный терминал. Конфигурация принимает OTLP/HTTP на loopback и выводит spans в консоль.

```powershell
otelcol --config=projects/document_intelligence_lab/release_eval/collector.yaml
```

Добавьте к выбранной команде `--otlp-endpoint http://127.0.0.1:4318/v1/traces` и укажите новый каталог. Найдите в выводе коллектора trace ID одного проблемного случая, сравните длительность этапов у baseline и candidate. Runner сохраняет тот же пакет OTLP в `traces.json`. Поле `otlp_exported` получает `true` только после подтверждения приёма. [Конфигурация Collector](https://opentelemetry.io/docs/collector/configuration/) · [OTLP/HTTP](https://opentelemetry.io/docs/specs/otlp/#otlphttp)

## Самостоятельная работа и критерий зачёта

1. До запуска сформулируйте гипотезу о замене модели и выберите допустимые потери, задержку и стоимость. Создайте файл `generated-reports/release-eval/my-cases.json` по схеме ниже. Включите случаи с ответом и без него, вопрос с перефразированием и вопрос о закрытом источнике. Хотя бы один собственный запрос должен отличаться от учебных. Лучше собрать независимую подборку с несколькими случаями каждого типа. Проверяйте gold вручную до эксперимента.
2. Проведите живое сравнение на неизменной подборке. Если цель — измерить именно замену модели, используйте две ревизии и `matched`. Сохраните точные байты набора вместе с отчётом и трассами. На разрешённых синтетических данных добавьте `--save-answers`, чтобы изучить формулировку. Этот флаг записывает ответы только в отчёт.
3. Выберите в `candidate.cases` один случай, сравните его с baseline и откройте обе трассы. Объясните, изменились ли поиск, переданный контекст или ответ. Приведите число успешных случаев и знаменатель, задержку, объём и решение `ship` либо `hold`. При регрессии сохраните первоначальный отрицательный результат и обоснуйте `hold`. Отрицательный результат подходит для защиты.
4. Положите `review.json` рядом с отчётом. При защите объясните, может ли ваша автоматическая проверка принять неверный смысл из-за совпадения фразы или отклонить допустимый пересказ. Видимые пять учебных вопросов и настроенная под один из них замена слов не характеризуют качество в новом домене.

Фрагмент схемы показывает один из вопросов. Добавьте собственные строки в массив. Для запроса без допустимого ответа укажите `answerable: false` и два пустых массива. Содержимое `answer_fragments` — альтернативные опорные фразы.

```json
{
  "schema_version": 1,
  "queries": [{
    "query_id": "archive-01",
    "text": "What resolution does the archive scanner use for paper copies?",
    "answerable": true,
    "relevant_chunk_ids": ["A-SCAN@1:p1"],
    "answer_fragments": ["300 dpi"]
  }]
}
```

Команды для собственного прогона используют массив `$models` из примера выше. Создайте новый каталог `submission` через runner.

```powershell
$dir = 'generated-reports/release-eval'
python -m $module @models --cases "$dir/my-cases.json" --save-answers --output-dir "$dir/submission"
Copy-Item "$dir/my-cases.json" "$dir/submission/cases.json"
```

Создайте `submission/review.json` с пятью полями. `case_id` и `trace_id` возьмите из одной измеренной строки кандидата. В `diagnosis` объясните конкретное наблюдение, в `release_decision` запишите `ship` или `hold`, в `rationale` обоснуйте решение.

```powershell
uv run python scripts/learn.py check document-release-eval
```

Проверка читает сохранённые артефакты локально, сверяет набор, пересчитывает измерения и связывает решение с трассой. Авторская демонстрация сама по себе не даёт зачёт. На защите потребуются объяснение выбранных данных и воспроизводимый запуск.

## Проверка в CI

В pull request и push с изменениями практикума, его входных данных или конфигурации выполняются тесты и быстрый офлайн-прогон. Отдельное задание с Qwen2.5-0.5B-Instruct Q4_K_M загружает закреплённые веса на CPU runner и сравнивает **два варианта сервиса с одной моделью**. На основной ветке его можно включить через **Run workflow → local_model** после появления workflow в этой ветке. До слияния поддерживается push в ветку `namepfchekcoutbranch-extended-pa1` исходного репозитория, когда изменён хотя бы один отслеживаемый путь, а сообщение последнего коммита содержит `[run-live-release-eval]`. Пустой коммит не проходит фильтр путей.

В разделе **Actions → Document release evaluation → Artifacts** доступны `release-eval-offline` и, после живой оценки, `release-eval-local`. Завершённые сравнения содержат `report.json` и `traces.json`, срок хранения — семь дней. Код 1 позволяет скачать результаты и найти вопрос, на котором ухудшилось качество. При операционной ошибке runner сохраняет `failure.json` и успевшие завершиться этапы.

## Результат прогона с моделью

17 ноября 2026 года GitHub Actions проверил на CPU две настройки поиска с одной Qwen2.5-0.5B-Instruct Q4_K_M. Обе получили одни и те же пять вопросов. Кандидат прошёл заданные пороги, список нарушений оказался пуст. Это демонстрация на открытых учебных вопросах. Для самостоятельной работы нужен свой набор. [Прогон с закреплёнными весами](https://github.com/DmitriyGrachev/Ml_roadmap/actions/runs/44156463286/job/134298545071)

В последующих прогонах шаг оценки также выводит сводные метрики `baseline` и `candidate` в журнал CI. По ним можно сравнить долю верных исходов, попадания поиска, задержку и расход токенов после истечения срока хранения архива. Подробности по отдельным вопросам и трассировки остаются в архиве.

В [повторном прогоне с метриками](https://github.com/DmitriyGrachev/Ml_roadmap/actions/runs/44159333880/job/134308775587) число верных исходов выросло с 3/5 до 4/5. Для трёх вопросов с ответом поиск вернул нужный фрагмент в 2/3 и 3/3 случаев соответственно. Обе версии верно отказались отвечать на два остальных вопроса. Кандидат использовал 380 входных и 88 выходных токенов, исходная версия — 253 и 52. Даже при попадании поиска во всех трёх случаях один ответ кандидата не прошёл проверку.
