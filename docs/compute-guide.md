# Окружение и ресурсы

База: Windows/PyCharm, Python 3.12. GPU не нужен для начала. Проверенные команды
и границы — [журнал первой волны](wave1-verification.md) и
[свежая проверка второй волны](wave2-verification.md).

## Два профиля одного проекта

```powershell
# База: Python, data и существующие offline modules
uv sync --locked
uv run python scripts/learn.py validate-env

# Только когда переходите к моделям
uv sync --locked --group training
uv run --group training python -m labs.01_pytorch_foundations.example
uv run --group training python -m labs.02_huggingface_models.example
```

Linux: те же команды `uv`; путь интерпретатора `.venv/bin/python` вместо
`.venv\Scripts\python.exe`. Инструкции Linux не равны проверке Linux.

В PyCharm выберите `.venv\Scripts\python.exe`, working directory — корень
репозитория. Run configuration использует module name, например
`labs.01_pytorch_foundations.example`, не директорию с lesson README.

`training` не default group. Не используйте старое `uv sync --all-groups` для
обычного старта: теперь это сознательная установка и тяжёлой группы.
После установки training используйте `uv run --group training ...`: простой
`uv run` синхронизирует базовый набор и может удалить opt-in библиотеки.
Верификация сопровождающего использует `.venv-training` через
`UV_PROJECT_ENVIRONMENT`, чтобы проверить отсутствие torch в базовой `.venv`.
Это два интерпретатора одного pyproject/lock, не отдельный проект или runner.

Чтобы держать лёгкую базу и training одновременно (рекомендуемый вариант для
второй волны), из корня проекта в PowerShell:

```powershell
uv sync --locked
$env:UV_PROJECT_ENVIRONMENT = ".venv-training"
uv sync --locked --group training
Remove-Item Env:UV_PROJECT_ENVIRONMENT
.venv/Scripts/python.exe scripts/learn.py test ml-knn-mechanics
.venv-training/Scripts/python.exe scripts/learn.py test lab-attention-mechanics
.venv-training/Scripts/python.exe scripts/learn.py check lab-attention-mechanics
```

В PyCharm для трёх continuation ID (`lab-training-resume`,
`lab-training-diagnostics`, `lab-attention-mechanics`) выберите
`.venv-training\Scripts\python.exe`. Остальные 11 новых exercise ID используют
базовую `.venv`. Прямой запуск выбранного interpreter не пересинхронизирует другой.
`check` до реализации TODO должен завершаться ненулевым кодом. Короткие offline
примеры и механические smokes не являются собственным исследованием ученика;
большой data release и все pretrained/GPU/cloud опыты требуют отдельного запуска.

Зафиксировано: `torch==2.14.0+cpu` из официального CPU index,
`transformers==5.17.0`, `datasets==5.0.1`; transitive versions — в `uv.lock`.
MLflow/Qdrant/PEFT доступны в отдельных opt-in группах `tracking`, `retrieval`,
`finetuning` (последняя включает `training`); в базовую группу они не входят.
[Окружения и реальные проверки](local-runtime-continuation.md).
vLLM/CUDA в Windows CPU training не включены. Base libraries не обновлялись массово.

Проверки типов разделены по зависимостям: `uv run mypy` проверяет базовые модули
и tooling; `uv run --group training mypy -p labs` дополнительно проверяет обе labs
с настоящими типами PyTorch. Это не заглушки типов тяжёлых библиотек в базовой среде.

## Профиль RTX 5060 Laptop для небольших экспериментов

Проверка 11 октября 2026 на текущем компьютере: **NVIDIA GeForce RTX 5060 Laptop GPU**,
`memory.total = 8151 MiB`, драйвер `616.64`. Это видеопамять (VRAM), не оперативная
память компьютера и не свободный остаток. Модель относится к Blackwell; штатные
8 GB подтверждает [спецификация NVIDIA](https://www.nvidia.com/en-gb/geforce/laptops/50-series/).

В существующей `.venv-training` фактически: `torch 2.14.0+cpu`,
`torch.version.cuda = None`, `torch.cuda.is_available() = False`.
Это ожидаемо для выбранного CPU index в pyproject, а не свидетельство неисправности
видеокарты. `uv sync --locked --group training` сейчас **не включает CUDA**.
Базу и проверенное CPU окружение сохраняем; GPU профиль ниже — PLANNED/NOT_RUN.

Для повторной диагностики, без установки и загрузки моделей:

```powershell
nvidia-smi --query-gpu=name,memory.total,driver_version --format=csv,noheader
.venv-training/Scripts/python.exe -c "import torch; print(torch.__version__); print(torch.version.cuda); print(torch.cuda.is_available())"
```

### Почему маленькая модель тоже требует запаса памяти

Весами (weights) называют сохранённые параметры модели. Во время inference нужны
также промежуточные вычисления (activations), рабочие буферы и, у генерирующей
модели с кешированием, KV cache — сохранённые ключи и значения прошлых токенов.
Обучение дополнительно хранит градиенты и состояние оптимизатора. Поэтому размер
файла модели не равен всей занятой VRAM.

Для грубой оценки только весов: число параметров × байты на параметр.
У условной модели с ровно 1 миллиардом параметров FP16 веса занимают примерно
2 GB (1.86 GiB); идеальная 4-bit упаковка — 0.5 GB (0.47 GiB) **до** служебных
данных квантования. Это арифметический пример, не измерение реальной модели и
не обещание, что её обучение поместится. LoRA уменьшает число обучаемых параметров,
но не убирает базовые веса и активации. Quantization и кеширование описаны в
[Transformers optimization overview](https://huggingface.co/docs/transformers/v5.19.0/optimization_overview);
это справочник, не требование обновить установленный Transformers.

В будущих объяснениях показывать отдельно состав памяти при inference и training,
затем график измеренной памяти при изменении batch size или длины входа. Сначала
предсказать направление изменения; после запуска объяснить результат и ограничения.

### Консервативные стартовые режимы

Это ориентиры для подбора и проверки, **не проверенные пределы GPU**. Начальные
эксперименты проектировать с запасом: целевой общий расход GPU около 5–6 GiB или
меньше, учитывая остальные приложения и фактически доступную память. Не стремиться
занять все 8 GB. RAM, свободный диск, питание/охлаждение ноутбука проверять отдельно.

| Работа | Начальный режим после prerequisites | Что проверять |
| --- | --- | --- |
| Python, SQL, Pandas, классическое ML, unit tests | CPU; GPU профиль не нужен | Корректность, память процесса и воспроизводимость |
| PyTorch lifecycle и диагностика | Существующая маленькая модель и синтетические данные; сначала CPU, затем тот же опыт на GPU | Forward/backward/update, конечные значения, checkpoint, допуск сравнения CPU/GPU |
| HF encoder и embeddings | Компактный encoder из существующей lab; небольшой batch и короткие тексты | Tokenizer/model revision, формы, peak VRAM и held-out метрики |
| RAG и локальная генерация | Для подбора рассматривать примерно 0.5–3B параметров, сначала batch 1 и короткий контекст; индекс на CPU, модели не держать вместе без измерения | Совместимость формата/precision/runtime, качество русского языка, latency, память и корректность источников |
| LoRA | Сначала механика на маленьком encoder; для будущего SFT рассматривать примерно 0.5–1.5B, micro-batch 1, ограниченную длину | Память обучения, число обучаемых параметров, независимая оценка, reload; QLoRA только после отдельной проверки backend |
| vLLM serving | Обязательный поздний результат; маленькая модель в отдельной Linux среде, см. маршрут ниже | Реальный API/streaming, версии, воспроизводимость и измерения; пока NOT_RUN |
| 7–8B, длинный контекст | Не обязательный старт; только отдельный ограниченный опыт после предыдущих измерений | Полная VRAM, поддержка ОС/Blackwell, ограничения concurrency; отказ от большой модели допустим |

`B` означает миллиард параметров; диапазоны не фиксируют конкретную модель.
Перед её явной загрузкой выбрать ID/revision, проверить лицензию, размер файлов,
формат и поддержку русского языка на выбранной задаче. Восьмимиллиардную модель
из Hub не переносить в основной учебный сценарий автоматически.

### Подготовка GPU среды и действия при нехватке памяти

1. Позже подготовить отдельное opt-in окружение с воспроизводимыми версиями,
   не заменяя текущую CPU среду и lock случайной установкой. Нужна CUDA сборка
   PyTorch с поддержкой Blackwell, совместимая с драйвером и выбранной ОС.
   Для vLLM использовать отдельную Linux среду со своим согласованным стеком.
   [PyTorch 2.7](https://pytorch.org/blog/pytorch-2-7/) впервые объявил Blackwell/CUDA 12.8;
   это история поддержки, не рекомендация ставить старую версию в текущий проект.
2. До pretrained загрузок проверить небольшой GPU tensor, forward/backward и
   шаг оптимизатора; записать реальные версии, устройство и peak memory. До этого
   `nvidia-smi` подтверждает обнаружение GPU, но не работу модельного стека.
3. Начать с маленького batch и короткого входа. При OOM (out of memory) сохранить
   конфигурацию ошибки, освободить ненужные модели и уменьшить batch/длину входа
   либо выбрать меньшую модель. Не запускать неконтролируемый стресс-тест памяти.
4. Для training разбирать gradient accumulation и activation checkpointing
   отдельными небольшими опытами; эти способы имеют ограничения и цену по времени.
   Mixed precision/quantization подключать после базовой проверки, не как обещание
   автоматической совместимости. При сокращении входа повторно оценивать качество.
5. Измерять память процесса через средства PyTorch и общий расход через
   `nvidia-smi`, не смешивая их показатели. Для времени GPU учитывать асинхронность
   вычислений, прогрев и синхронизацию; сравнивать одинаковые данные и параметры.

### Обязательный vLLM в Linux

**CORE · PLANNED; runtime NOT_RUN.** По уточнению пользователя vLLM обязателен,
но нативная Windows средой сервера не будет. Проверка `wsl.exe --status`
11 октября 2026 вернула код 50 и сообщение, что подсистема не установлена.
Наличие RTX 5060 и драйвера подтверждено выше; доступ к GPU из Linux пока не проверен.
11.10.2026 пользователь отложил фактический запуск до появления Linux/WSL:
**DEFERRED_ENV**. Материалы и кандидаты ниже сохраняются для этого следующего этапа.

Предлагаемые среды:

| Путь | Где работает vLLM | Когда использовать |
| --- | --- | --- |
| Основной: Ubuntu 24.04 LTS в WSL2 | Linux процесс, Linux Python и отдельное serving окружение; GPU ноутбука | Сохранить привычную Windows для редактора, использовать свою RTX без аренды GPU. WSL2 всё ещё зависит от Windows host |
| Полностью без Windows: отдельный Linux host с NVIDIA GPU | Нативный Linux; клиент общается с сервером по API | Если WSL не подходит или принципиально нужен Linux без Windows host. Собственная машина либо аренда после согласования бюджета/доступа |

Официальная [инструкция vLLM](https://docs.vllm.ai/en/latest/getting_started/installation/gpu/)
указывает Linux и допускает WSL с совместимым дистрибутивом. Это основание выбрать
путь, не результат запуска конкретного wheel на RTX 5060. По
[CUDA on WSL](https://docs.nvidia.com/cuda/wsl-user-guide/index.html) GPU предоставляется
через Windows NVIDIA driver: внутри WSL **не устанавливать отдельный Linux display
driver**. Версии vLLM/PyTorch/CUDA должны быть совместимы с Blackwell; готовый
serving wheel проверять в новой среде, не поверх проектного CPU PyTorch.

Порядок подготовки после отдельного разрешения на установку:

1. Проверить требования WSL2, виртуализацию, RAM и свободный диск; подготовить Ubuntu
   и подтвердить внутри неё GPU и небольшой CUDA расчёт. Если WSL2 непригоден,
   не исключать vLLM из плана, а согласовать нативный Linux host.
2. Создать отдельную Linux serving среду, например на Python 3.12, с зафиксированными
   совместимыми версиями. Windows `.venv` и `.venv-training` не переносить и не
   перезаписывать; текущую локальную копию не заменять удалённой main. Docker
   допустим позже для воспроизводимости, но не обязателен для первого запуска.
3. Выбрать точную revision маленькой модели, проверить лицензию и объём; скачать
   только отдельной явной командой. Серверу затем передать локальный snapshot,
   чтобы запуск не стал скрытой загрузкой. Окружение, кеши и веса отделить от
   ученических файлов. Сетевое обращение не должно происходить при pytest/import.
4. Запустить vLLM только на loopback, проверить API сначала внутри Linux, затем
   из клиента. Для Windows → WSL предусмотрен
   [доступ через localhost](https://learn.microsoft.com/en-us/windows/wsl/networking),
   но связность проверить отдельно. Не открывать порт всему интернету ради smoke.
   Для удалённого Linux использовать закрытый доступ/туннель и только разрешённые
   данные; аренда и передача данных требуют отдельного решения.

**Кандидат для первого smoke — [Qwen/Qwen3-0.6B](https://huggingface.co/Qwen/Qwen3-0.6B)**:
в карточке есть пример vLLM, 0.6B параметров и Apache-2.0. Это не обещание качества
RAG или измеренной вместимости. Начать без quantization, с FP16 и отключённым
thinking через chat template для короткого ответа; позже оценить русский язык
на своих фиксированных вопросах. Revision и конкретную версию vLLM зафиксировать
перед установкой; пример из карточки не копировать как проверенный локальный конфиг.

#### Ещё два кандидата для RTX 5060 Laptop

Карточки, лицензии и конфигурации просмотрены 11 октября 2026. Все кандидаты
**PLANNED / NOT_RUN**: веса не скачаны, совместимость и качество локально не измерены.
Qwen3-0.6B остаётся первым коротким smoke; две следующие модели — выбор для
последующего опыта, а не требование скачать три модели или держать их вместе в GPU.

| Дополнительный кандидат | Для чего пробовать | Ограничение и память только весов |
| --- | --- | --- |
| [Qwen/Qwen2.5-1.5B-Instruct](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct), Apache-2.0 | Короткие инструкции и русскоязычные вопросы; карточка заявляет многоязычность, включая русский. Предпочтительный второй кандидат | 1.54B параметров: приблизительно 3.08 GB / 2.87 GiB при 2 байтах на параметр. Качество на наших вопросах неизвестно |
| [HuggingFaceTB/SmolLM2-1.7B-Instruct](https://huggingface.co/HuggingFaceTB/SmolLM2-1.7B-Instruct), Apache-2.0 | Другая архитектурная конфигурация для коротких запросов, streaming и сравнения ресурсов | Преимущественно английский язык; не основной выбор для русского RAG. Около 3.4 GB / 3.17 GiB весов при номинальных 1.7B и 2 байтах на параметр |

Это расчёт `число параметров × bytes`, **не размер загрузки и не peak VRAM**.
Дополнительно нужны KV cache, временные tensors, runtime и память других процессов.
В [config Qwen](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct/blob/main/config.json)
указан `Qwen2ForCausalLM`, в
[config SmolLM2](https://huggingface.co/HuggingFaceTB/SmolLM2-1.7B-Instruct/blob/main/config.json)
— `LlamaForCausalLM`; обе архитектуры есть в
[списке vLLM](https://docs.vllm.ai/en/latest/models/supported_models/).
Это документальное основание испытать их, не проверка выбранной версии Linux wheel.

Небольшой прогноз перед экспериментом: похожий размер весов не означает одинаковый
KV cache. Для одной последовательности из 1024 токенов в FP16 идеализированная
формула `2 × layers × KV_heads × head_dim × tokens × 2 bytes` даёт около 28 MiB
для Qwen2.5 (28 слоёв, 2 KV heads, размер head 128) и 192 MiB для SmolLM2
(24, 32, 64). Это арифметика конфигураций без округления блоков/резервирования
пула vLLM; фактическое выделение памяти нужно измерить. При удвоении токенов
этот компонент удваивается, а веса — нет. Проверить прогноз отдельным опытом.

Порядок будущего сравнения: выбрать **одну** дополнительную модель → зафиксировать
revision, лицензию и объём → явно скачать → запустить с коротким профилем ниже
→ повторить фиксированные вопросы → сохранить качество и serving measurements
раздельно. Перед сменой модели остановить предыдущий сервер и проверить память.
Chat template и stop tokens брать от выбранной модели; отключение thinking,
упомянутое для Qwen3, не переносить автоматически на другие модели. Для сравнения
сохранять и тексты, и фактические token counts: tokenizers различаются.
Языковые результаты разделять; англоязычный smoke не доказывает качество русского.
Новые курсы технического английского из этого не следуют.

Предлагаемый стартовый профиль, **ещё не испытанный**:

| Параметр | Начальное значение | Смысл ограничения |
| --- | --- | --- |
| `--max-model-len` | `1024` | Общая длина входа и ответа в токенах |
| `--max-num-seqs` | `1` | Одна обрабатываемая последовательность за итерацию; после smoke проба с `2` |
| `--gpu-memory-utilization` | `0.65` | Начальный бюджет экземпляра vLLM; не глобальный предел всех процессов GPU |
| `--enforce-eager` | включён | Первый запуск без CUDA graphs; оптимизации исследовать после рабочего baseline |
| `--dtype` | `half` | FP16 без дополнительного quantization backend |
| `--host` | `127.0.0.1` | Локальный учебный сервер |
| Лимит ответа в запросе | `max_tokens = 128` | Вход вместе с chat template и ответом должен уложиться в общий контекст |

Значения — наш консервативный проектный выбор, а не рекомендованный benchmark.
Смысл флагов: [serve reference](https://docs.vllm.ai/en/latest/cli/serve/);
ограничения контекста, batch и CUDA graphs:
[conserving memory](https://docs.vllm.ai/en/latest/configuration/conserving_memory/).
Не поднимать лимит памяти без измерения. Если ресурсов/совместимости не хватает,
сначала уменьшить нагрузку или модель, затем рассмотреть другой Linux GPU host;
OOM не превращает обязательный результат в OPTIONAL.

Зачёт будущей [serving lab](../labs/05_model_serving/README.md) требует именно
vLLM: API ответ, streaming, перезапуск из тех же artifacts и ограниченное сравнение
