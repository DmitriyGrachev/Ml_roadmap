# Автоматическая проверка репозитория

После изменения кода хочется узнать, не сломались ли прежние примеры. CI
(continuous integration, непрерывная интеграция) повторяет проверки на чистой
машине. Он не проходит упражнения за ученика и не измеряет качество модели.

В [workflow](../.github/workflows/ci.yml) подготовлены две обычные независимые работы
(jobs). Первая устанавливает базовое окружение, вторая явно включает CPU training.
Отдельная matrix `local-runtimes` запускается только при ручном `workflow_dispatch`
с выбранным `local_runtime_checks`: MLflow, Qdrant и PEFT получают каждый свою
группу и чистое окружение. Обычный push/pull request эту matrix не включает.
Каждый шаг (step) запускает одну команду. Ненулевой код завершения, например из-за
упавшего assertion, останавливает обычные следующие шаги этой работы.

```text
код + pyproject.toml + uv.lock
                 │
           два чистых runner
           ┌─────┴────────────┐
           ↓                  ↓
       base install      training install
           ↓                  ↓
   pytest / Ruff / mypy   offline lab tests / mypy
           ↓                  ↓
    artifact smoke      CPU tensors, random weights
```

`uv.lock` фиксирует разрешённые версии. `--locked` требует согласованности файла
с зависимостями проекта; это не гарантия отсутствия ошибок в самих библиотеках.
После установки `--no-sync` запускает проверку без повторного изменения окружения.
Базовая работа не включает `training`, а training не получает vLLM или GPU stack.
Optional runtime matrix также использует offline Hub flags; MLflow telemetry
выключена. Она проверяет локальные библиотеки, без внешних endpoints и downloads
моделей. Настройка workflow не является его hosted исполнением — **NOT_RUN**.
Загрузка Python и пакетов при установке разрешена конфигурацией CI; загрузка
моделей и датасетов в тестах не нужна. Hub offline flags — дополнительная защита,
а не полный сетевой firewall. Локальные тесты входов/выходов остаются обязательными.

## Маленький разбор отказа

Представьте функцию, которая должна отклонять пустой документ. Её тест передаёт
пустую строку и ожидает ошибку. Если убрать проверку входа, тест должен завершиться
неуспешно. Линтер при этом может оставаться зелёным: аккуратно оформленный код
не обязательно ведёт себя правильно. В реальном workflow это две разные проверки.

Для безопасной пробы создайте временный файл вне ученических реализаций:

```python
def test_deliberate_failure():
    assert 2 + 2 == 5
```

Запустите только этот файл через `python -m pytest <путь-к-файлу> -q`: ожидается
exit code 1. После просмотра результата удалите только созданный вами файл.
Эта проба проверяет локальную передачу ошибки, а не состоявшийся hosted run.
В основных tests намеренно падающий тест не сохраняется.

## Что означает зелёный результат

Обычный `test` и полный pytest проверяют инфраструктуру; прежние незаполненные
starters могут оставаться xfail. Строгий `check <ID>` проверяет выбранный материал:
обязательные skip/xfail не засчитываются. Не запускайте глобальный ученический
зачёт в CI: будущие TODO не являются регрессией уже работающей программы.

Для модели отдельно нужны сохранённые predictions, пересчитанные metrics и
независимая оценка. Для освоения — самостоятельная вариация и объяснение ошибок.
Даже настоящий зелёный CI не подтверждает ни то, ни другое.

## Самостоятельная проверка понимания

1. Почему успех Ruff не компенсирует провал теста?
2. Что произойдёт с базовым стартом, если заменить группы на `--all-groups`?
3. Почему один и тот же тест может раскрыть зависимость от файлов вашей машины?
4. Какая проверка обнаружит замену байтов сохранённой модели?
5. Можно ли назвать локальный запуск доказательством работы GitHub runner?
6. Что проверяется через `check`, чего не обещает инфраструктурный pytest?

Сопоставьте команды с [правилами test/check](testing-exercises.md) и своими
[тестами](../modules/01_python_core/09_testing/theory.md). Учебные реализации
для этой пробы менять не требуется.

## Граница запуска

Workflow подготовлен локально. Hosted CI — **CONFIGURED / NOT_RUN** до отдельного
разрешения на публикацию и фактического запуска. Он не развёртывает сервис,
не получает облачных секретов и не запускает платные эксперименты. Публикация
репозитория с этим файлом активирует события push/pull_request; сейчас публикации нет.

Документация: [uv в GitHub Actions](https://docs.astral.sh/uv/guides/integration/github/)
— установка и sync; [синтаксис workflow](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)
— jobs, steps, permissions и exit status. Английский; достаточно этих разделов.
API и ссылки просмотрены 11.10.2026; проверку реального runner они не заменяют.

## Изменения маршрута ML Engineer (29.10.2026)

Основная CI-проверка теперь запускается на Windows и Ubuntu. В ней устанавливается
небольшая группа `migrations` для настоящего Alembic round trip; PyTorch остаётся
в отдельном training job. `uv_build` входит в dev для offline wheel-практики.
Обычный pytest допускает решения ученика. Отдельный шаг
`uv run --no-sync python -m pytest --maintainer -m maintainer_only -q` проверяет,
что распространяемые starters ещё не решены.

CLI принудительно пишет UTF-8; subprocess-потребители должны декодировать UTF-8.
Регрессия воспроизводит прежний сбой при `PYTHONIOENCODING=cp1252`. Тест относительных
путей PyTorch использует временный repository root, не предполагая один Windows drive
для checkout и temp. Актуальные результаты — [verification](ml-engineer-readiness-verification.md).
