# Защита практического исследования

Этот шаблон применяется к открытым контролям, а также к собственным проектам.
Заполните его своими результатами. Ниже вопросы для защиты, а не готовый отчёт.
Все текстовые обоснования, доступность данных, происхождение результатов и решение
о выпуске остаются `REQUIRES_REVIEW` до содержательной проверки человеком.

1. **Задача.** Кто принимает решение, в какой момент, что считается ошибкой?
2. **Доступность данных.** Источник, права, время появления каждого использованного
   поля; известные факты, допущения и недостающие свидетельства.
3. **Baseline.** С чем сравнивали и почему это полезная отправная точка?
4. **Разбиение.** Единица наблюдения и независимости, будущая популяция, использование
   разметки и данных при выборе решения; какие зависимости остаются?
5. **Метрика.** Почему она подходит цели, какие ошибки скрывает, как трактовать
   неопределённость? Порог/критерий успеха выбирает и защищает автор.
6. **Эксперименты.** Что меняли, что держали постоянным, фактические входы/выходы,
   конфигурации, команды, среда и измерения; отделите выполненное от запланированного.
7. **Ошибки.** Разберите конкретные наблюдения и категории, включая неприятные.
8. **Ограничения.** Внешняя валидность, неизвестная доступность, ресурсы, зависимость
   от разметки; чего автоматические проверки не доказывают?
9. **Запуск.** Как воспроизвести из исходных данных в новой папке; что проверяет
   unit, smoke, evaluation и что необходимо проверить человеку?
10. **Следующий шаг.** Какой новый факт изменил бы решение; стоимость, rollback и
    новая вариация задачи на защите.

Короткие инциденты для обсуждения: score изменился на новом периоде; обучение
остановилось без улучшения; после обновления каталога ухудшился retrieval.
Для каждого назовите наблюдения, первые различающие проверки и условие остановки.
Не угадывайте причину по одному числу.

## Контракт артефактов открытых контролей

Только для `ml-evaluation-case` и `production-product-study`; другие исследования
сохраняют свои контракты. Выходная папка новая, непустые файлы находятся внутри неё.
`manifest.json` — JSON object со следующими полями:

| Поле | Содержание |
| --- | --- |
| `schema_version` | целое `1` |
| `exercise_id` | точный ID своего контроля |
| `run_id` | непустой уникальный идентификатор данного запуска |
| `dataset_sha256` | lowercase SHA-256 фактических байтов основного входа |
| `split_sha256` | lowercase SHA-256 фактических байтов `split.json` |
| `config` | JSON object с конфигурацией; только конечные числа |
| `review_status` | `REQUIRES_REVIEW` |
| `artifacts` | object: относительное имя файла → lowercase SHA-256 его байтов |

Обязательны текущие входы упражнения, `split.json`, `outputs.json`, `report.md`,
`implementation.txt`. Включайте также дополнительные файлы экспериментов. Сам manifest
в `artifacts` не включается. Точные поля split/outputs описаны в README контроля.
Идентификаторы запуска, данных и разбиения должны повторяться в outputs; старые
файлы от другого запуска или упражнения не становятся новыми от переименования.
Изменение байтов требует нового digest; пересчёт digest не освобождает от проверок
ID, количеств, прав и текущих канонических входов.

Валидаторы **читают** файлы и не загружают pickle, не импортируют implementation,
не запускают команды из manifest. Общий небольшой `open_control_evidence` связывает
проверки файлов Task1 с этими двумя контрактами: обязательные файлы, сравнение
канонических байтов, JSON и числовая сверка. Это не runner экспериментов.

Проверка доказывает согласованность сохранённых данных и арифметики. Она не может
удостоверить автора/время запуска, что приложенный код действительно выполнялся,
что latency измерена, что число операций не придумано, что отсутствует подгонка
или что признаки доступны в момент решения. Проверяющий воспроизводит выбранные
запуски в согласованной среде и обсуждает эти ограничения. Не выдавайте зелёный
check за автоматическую оценку честности или разрешение производственного запуска.
