# Небольшой воспроизводимый эксперимент

Используется обеими labs. Это файловый протокол, не ML platform и не готовый отчёт.
Сначала [постановка задачи](../modules/04_machine_learning/01_problem_framing/README.md),
[validation](../modules/04_machine_learning/02_validation/README.md),
[метрики](../modules/04_machine_learning/05_evaluation/README.md) и
[provenance](../modules/04_machine_learning/06_reproducibility/README.md).

## До запуска

1. Назовите объект и момент предсказания, целевую переменную, доступные признаки,
   цену ошибок и ограничения. Для точного поиска ID используйте правила/SQL:
   модель здесь добавит ошибки, а не ценность. Для семантики рассмотрите encoder,
   для ответов по обновляемым документам — retrieval; fine-tuning не заменяет базу фактов.
2. Укажите происхождение/лицензию, immutable revision и локальный snapshot. Сохраните
   checksum **реальных байтов**, не только название dataset. Большие данные вне Git.
3. Опишите инструкцию разметки, неоднозначные случаи и процедуру проверки спорных
   меток. Не подглядывайте в label/response при построении признаков. Не используйте
   персональные или рабочие данные; примеры синтетические/публичные разрешённые.
4. Сделайте split до fit preprocessing; сохраните sample IDs, content hashes,
   train/validation/test membership. Проверьте точные и близкие дубликаты между
   split, группы/время доступности признаков. Exact dedup не гарантирует отсутствие
   шаблонного leakage в синтетическом тексте.
5. Зафиксируйте baseline, metric, seed, число шагов, batch/max length, device/dtype,
   budget и правило остановки. Настройка по validation; финальный test оценивается
   только после фиксации выбора. Сложная модель не обязана выиграть.

## Во время и после

Для новых упражнений минимальная общая проверка использует manifest со значениями
`schema_version: 1`, `exercise_id`, `dataset_sha256`, `split_sha256` и `config`.
Оба SHA-256 — ровно 64 строчных шестнадцатеричных символа. `config` — объект из
вложенных объектов, списков и JSON-значений; числа должны быть конечными.
`validate_identity` сверяет ID и оба checksum с ожидаемыми значениями конкретного
упражнения. `checked_artifact` принимает только относительный переносимый путь
внутри корня, проверяет фактические байты файла и ничего не записывает.
Дополнительные поля отчёта определяет само упражнение; его проверка обязана
сопоставить сохранённые строки, их ID и фактический inference/trace с заявленными
предсказаниями и метриками. Общая проверка identity не доказывает эти результаты.

- JSON/CSV: config, code revision (при dirty tree так и написать), package versions,
  data/model revisions, seed, split identity, measured metrics, predictions/labels
  там, где это нужно для независимого пересчёта. Checkpoint/model config/tokenizer
  должны существовать, иметь checksums и использоваться при reload inference.
- Пишите measured timing с размером batch и warm/cold условием. Не сравнивайте
  произвольные разбиения или разные preprocessing между методами.
- Отдельно unit correctness, integration smoke и ML evaluation. Случайный tiny
  encoder проверяет только механику. Нельзя переносить его accuracy в отчёт
  pretrained experiment. Неизмеренные поля не заполняются выдуманными числами.
- Добавьте собственные ошибки по классам/срезам, неоднозначные примеры, ограничения
  и решение о следующем эксперименте. Валидатор структуры не оценивает глубину анализа.
- Перезапуск сохраняет тот же dataset/split identity; не дописывает дубликаты.
  При смене схемы меняйте schema_version и явный preprocessing contract.
- Seed не гарантирует побитовое совпадение устройств/версий. Сравнивайте допустимые
  численные погрешности, а не универсальный accuracy threshold.

Старый schema-1 отчёт PyTorch проверяет происхождение файлов, их checksum и
арифметику метрики по заявленным predictions. Он не запускает inference из
сохранённого snapshot и потому сам по себе не подтверждает эти predictions.
Это ограничение действует и для ранее созданных отчётов. Пояснения и выводы во
всех labs и упражнениях имеют статус `REQUIRES_REVIEW` до проверки человеком;
строка статуса в отчёте не меняет код выхода CLI и не обновляет progress.

## Дальнейшая глубина, не обязательная инфраструктура первой волны

Один ablation меняет ровно один компонент. Bootstrap требует правильной единицы
наблюдения: зависимые обращения одного пользователя нельзя считать независимыми.
Calibration оценивает вероятности (Brier/log loss, reliability diagram), а не только
классы. A/B требует единицы рандомизации, целевой метрики, guardrails и достаточных
данных: маленький smoke этого не доказывает. MLflow/tracking — [следующая волна](ai-ml-extension-plan.md).
