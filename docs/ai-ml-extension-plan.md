## Согласованный план пяти этапов от 11 октября 2026

Цель — дополнить существующий маршрут самостоятельной инженерной практикой:
Python → воспроизводимая модель → работающий сервис → настоящий RAG → выбранная
специализация. План согласован; **R01/R02 подготовлены**, оставшиеся части развиваются по пакетам,
а реальные модельные/сервисные эксперименты — NOT_RUN.
Запись плана не означает реализацию лабораторий или выполнение заданий учеником.

Git, Linux и технический английский исключены из новых учебных тем этого плана.
CI, контейнеризация и развёртывание остаются: для них нужны инструкции запуска,
но не отдельные курсы по исключённым темам. Старые материалы и их контракты
сохраняются. Основа практики — развитие существующего
[Document Intelligence Lab](../projects/document_intelligence_lab/README.md),
а не новый параллельный курс или второй портфель одинаковых проектов.

### Этап 1 Самостоятельная разработка на Python

Переиспользовать [Python Core](../modules/01_python_core/README.md), включая
Object Model, Collections, Functions, Typing, исключения и тестирование.
Не переписывать готовую теорию. Добавлять только недостающее проверяемое умение:

- собственные тесты на обычный, пустой, ошибочный и граничный ввод;
- поиск причины ошибки по traceback и пошаговому состоянию программы;
- выделение функций и модулей с понятными обязанностями;
- проверку предложенного AI-помощником кода: воспроизвести дефект независимым
  тестом, объяснить исправление и ограничения, не поручая ему решение student TODO.

Результат — небольшой обработчик документов или обращений с валидацией и тестами
ученика. Критерий освоения — самостоятельно изменить требование, реализацию и
проверки, объяснив новую вариацию без копирования демонстрации.

### Этап 2 Данные и самостоятельный ML проект с CI

Prerequisites: [Data Foundations](../modules/03_data_foundations/README.md),
[классическое ML](../modules/04_machine_learning/README.md), соответствующие
SQL-упражнения. Использовать готовые EDA, split, preprocessing, статистическую
оценку, [протокол экспериментов](experiment-protocol.md) и
[шаблон защиты](project-defense.md).

1. Продолжить [аналитический SQL](../modules/02_python_backend/exercises/analytics_sql/README.md):
   план запроса, индексы, сравнение времени и неизменности результата. Начать
   с имеющейся локальной БД; реальный PostgreSQL проверять отдельно в подготовленной среде.
2. Подготовить небольшой разрешённый датасет: происхождение, лицензия, правила
   разметки, неоднозначности, очистка и обоснованное разбиение. Переиспользовать
   [data release](../modules/03_data_foundations/exercises/data_release/README.md).
3. Сделать вводный этап A1 Document Intelligence: классификатор на правилах
   и classical ML. Это отдельная будущая промежуточная точка; она не отменяет
   PyTorch/HF prerequisites существующей полной части A проекта.
4. Сохранить версии данных, split, параметры, seed, модель, реальные предсказания,
   метрики и категории ошибок. Повторный запуск не перезаписывает прежние результаты.
5. Подготовить действующий CI: pytest, Ruff, mypy и небольшой автономный smoke
   без моделей из сети. Сохранить свидетельство фактического запуска pipeline;
   наличие YAML само по себе не означает проверенный CI.

Результат — воспроизводимый эксперимент, модель, тесты, отчёт и инструкция запуска.
Критерий освоения — воспроизвести результат в новой папке и защитить метрику,
разбиение, доступность признаков и ошибки. Не требовать выдуманного улучшения
baseline: отрицательный результат с корректной оценкой допустим.

### Этап 3 Сервис и жизненный цикл модели

Prerequisites: результат этапа 2 и нужные уроки
[backend](../modules/02_python_backend/README.md). Сначала обслуживать классическую
модель проекта; это не зачёт всей будущей HF/LLM serving lab.

Последовательность небольших проверяемых частей:

1. API с загрузкой модели, единым preprocessing, валидацией, ошибками и версией модели.
2. Контейнер и локальная проверка запуска сервиса.
3. Сохранение параметров, метрик и artifacts, затем реальный experiment tracking.
4. Одно облачное развёртывание: хранение, минимальные права, секреты, журналы,
   ограничения расходов и удаление ресурсов. Выбор провайдера и расходы согласуются
   отдельно; локальный запуск не засчитывается как облачный.
5. Выпуск новой версии модели вместе с preprocessing, проверка совместимости
   и восстановление предыдущей версии.
6. Контролируемая нагрузка: задержка, частота ошибок и память; наблюдение за данными
   и качеством при доступных метках. Не запускать переобучение по любому proxy-сигналу.

Переиспользовать спецификации [serving](../labs/05_model_serving/README.md),
[lifecycle](../labs/06_ml_lifecycle/README.md) и локальные задания модуля 08.
Для полных labs сохраняются их prerequisites; вводный сервис не подменяет их.
Результат — работающий сервис, привязанные к версиям измерения и инструкция
восстановления. Критерий освоения — воспроизводимый запуск, диагностика сбоя и откат.

### Этап 4 Настоящий RAG и независимая оценка

Перед этапом пройти существующие [PyTorch](../labs/01_pytorch_foundations/README.md),
[Hugging Face](../labs/02_huggingface_models/README.md), модули
[LLM](../modules/05_llm_engineering/README.md) и [RAG](../modules/06_rag/README.md).
Реализовать существующую спецификацию [Real RAG](../labs/03_real_rag/README.md):

- разрешённый corpus и независимые проверочные вопросы с relevance-разметкой;
- реальные embeddings, постоянный Qdrant index и lexical baseline;
- отдельные измерения retrieval и качества ответа выбранной модели;
- источники, отсутствие ответа, обновление/удаление и разграничение доступа;
- регрессионные проверки, задержка и стоимость;
- hybrid/reranking только после измерения пользы на фиксированной выборке.

Результат — часть B Document Intelligence с ответами по документации.
Критерий освоения — оценка на новых, в том числе неудобных вопросах, известные
категории ошибок и обоснованные отказы. Успешная демонстрация и оценка другой LLM
не заменяют независимую разметку и ручную проверку части ответов.

### Обязательный результат vLLM в Linux

Уточнение пользователя от 11 октября 2026: **vLLM обязателен, CORE · PLANNED**.
Недоступность нативной Windows меняет среду запуска, а не требование освоения.
После этапа 4, перед необязательными специализациями, пройти существующую
[serving lab](../labs/05_model_serving/README.md) на vLLM. Сохраняются её prerequisites:
backend, HF inference и локальные уроки Production AI. LoRA не требуется;
вводный CPU сервис этапа 3 не подменяет эту лабораторную.

Основной предложенный путь — Ubuntu в WSL2 с RTX 5060 Laptop; vLLM исполняется
в Linux, Windows остаётся только основной ОС и возможным клиентом. Если требуется
полностью исключить Windows, выбрать отдельный нативный Linux host с NVIDIA GPU.
Удалённая аренда — только с согласованным бюджетом. Подробности, ограничения
8 GB и резервный путь: [ресурсный план](compute-guide.md#vllm-linux-route).
Выбор маршрута не означает разрешение установить WSL, изменить ОС или оплатить сервер.

Четыре небольших результата внутри одной lab: проверить GPU в Linux → запустить
локальный vLLM API → подключить клиент и streaming → измерить ограниченную нагрузку,
обработать отказ и повторить запуск. Сохранить версии среды/модели, конфигурацию,
логи и измерения. Схемы: клиент → очередь → prefill/decode → ответ; отдельно
weights/KV cache и временная шкала первого/следующих токенов.
Ollama, другой inference runtime или успешный import не засчитываются вместо
реального vLLM. Статус остаётся NOT_RUN до опыта; новые ID и progress не добавляются
одной записью плана. Полный Linux курс по-прежнему не входит в программу.

### Правила реализации и приёмки

- Работать по одному небольшому результату; сохранять старые ID, CLI, test/check,
  progress, student TODO и пользовательские реализации.
- Новые ID вводить только для нового проверяемого умения. Ссылки на источники
  и спецификация PLANNED не создают исполняемое задание или ложный зачёт.
- Теория — по-русски с английскими терминами: интуиция → объяснение → разобранный
  пример → ошибка → самостоятельная вариация. Готовая демонстрация не решает задание.
- Разделять unit, integration/smoke и фактическую ML evaluation. `test` допускает
  незавершённые xfail; `check <ID>` проверяет только выбранный материал строго.
- Зависимости новых labs — opt-in. Загрузка моделей/датасетов и обращения к внешним
  сервисам — только явными командами, не при обычном pytest или базовом uv sync.
- Для каждого реализованного пакета проверять примеры, ссылки, связанные тесты,
  Ruff, форматирование, mypy и затронутые регрессии. Указывать реальные команды,
  среду и NOT_RUN для невыполненных проверок; освоение учеником оценивать отдельно.
- Платные ресурсы, публикация, commit/push/merge требуют отдельного разрешения.

## Небольшая практика и более подробные объяснения

Уточнение пяти этапов от 11 октября 2026: больше коротких самостоятельных шагов,
объяснений причин и наглядных промежуточных состояний. Ниже **20 учебных блоков,
а не 20 новых exercise ID**. Это план разбиения работы; новые вариации, объяснения
и интеграции — PLANNED. Существующие материалы сохраняют свои статусы и контракты.
К этим блокам добавлен [обязательный результат vLLM](#required-vllm) существующей
serving lab; он не зависит от выбора специализации этапа 5.

Ориентир для одного занятия после prerequisites: 20–45 минут на разбор и одну
вариацию; интеграцию делить на занятия по 45–90 минут. Это оценка объёма, не срок
освоения с нуля и не обещание времени обучения модели. В каждом блоке менять
один фактор, сохранять один небольшой результат и объяснять его своими словами.
Полный `check` прежнего упражнения не сокращается до такой вариации.

Этапы 1–3 начинаются на CPU. Перед этапом 4 остаются PyTorch/HF prerequisites;
первые занятия с ними тоже не требуют GPU. Для будущих модельных опытов учитываем
[ресурсный профиль RTX 5060 Laptop с 8 GB VRAM](compute-guide.md#rtx5060-profile).
Это не повод переносить Python, SQL и классическое ML на видеокарту.

### Как объяснять каждый небольшой блок

Использовать [существующий шаблон теории](theory-lesson-template.md), дополняя
только реальные пробелы. Object Model и готовые пакеты не переписывать.

1. Поставить бытовой нейтральный вопрос: например, почему повторный запуск
   обработчика даёт другой результат или почему найденный документ не отвечает
   на вопрос. До запуска попросить предсказать конкретный результат.
2. Дать интуицию простыми словами, затем точные определения с английскими
   терминами. Новый термин объяснять там, где он впервые нужен; наличие слова
   в списке технологий не считать объяснением.
3. Полностью разобрать маленькую демонстрацию: вход → действия по шагам →
   промежуточные значения → результат → причина. Для формул расшифровать символы,
   единицы и формы тензоров, вручную посчитать один небольшой случай.
4. Добавить визуальную опору там, где она проясняет связи: таблицу состояний,
   схему потока, матрицу, временную шкалу или график. Сначала проверить, нет ли
   подходящей опоры в текущем уроке. Не рисовать отдельную картинку для каждого API.
5. Показать типичную ошибку и объяснить, почему она возникает. Затем предложить
   самостоятельную вариацию с другими данными или условием, а не копию демонстрации.
6. Проверять понимание вопросами «почему?», «что изменится, если…?» и требованием
   объяснить неожиданный результат. Для графика: «Какой вопрос проверял?
   Что увидел? Чего это не доказывает?». Ответы и отчёт пишет ученик.

Визуальные опоры должны быть связаны с кодом: одинаковые входные числа, названия,
формы и порядок шагов. Численные графики строить из реального запуска, обозначать
синтетические данные и упрощения. Для схем нужны подписи и текстовое объяснение;
картинка не заменяет теорию. Использовать имеющиеся SVG/Markdown и opt-in Matplotlib,
без нового веб-приложения, виджетов или автоматического добавления зависимостей.

### Этап 2 Четыре блока данных и классического ML

Prerequisites — Data Foundations, SQL и ML по ссылкам соответствующих заданий.

smoke, ML evaluation и понимание — четыре разных свидетельства.
Начать будущую реализацию с собственных тестов и одного нейтрального debugging
разбора этапа 1; затем двигаться по пяти этапам, не реализуя всё одновременно.

## Специализации после общей базы — OPTIONAL, PLANNED

- CV/multimodal: prerequisites PyTorch/images; проект OCR каталога; done — независимая

  artifact и rollback. Kubernetes/IaC/distributed training только при обоснованной потребности.

network boundary, logs, budget и удаление ресурсов. Платное развёртывание необязательно.
