# Как читать собственные измерения serving

Prerequisites: среднее/медиана, единицы времени, [serving theory](../theory.md).
Цель — связать наблюдение с формулой и границей вывода. Никакие числа ниже
не получены на реальном vLLM: это арифметические примеры.

## 1. Batch wall time и перекрывающиеся запросы

Допустим, три успешных запроса заняли 80, 120 и 160 ms. Они перекрывались,
а вся серия от старта до последнего результата длилась 200 ms.

| Величина | Расчёт | Значение |
|---|---|---|
| Медиана успешной latency | середина `[80,120,160]` | 120 ms |
| Сумма длительностей запросов | `80+120+160` | 360 ms |
| Throughput серии | `3 / 0.2` | 15 requests/s |

Сумма 360 ms не является временем серии. Одновременно это не доказательство
ускорения модели: нужен сопоставимый опыт с тем же input/output бюджетом,
состоянием прогрева и окружением. Изменение длины ответа меняет объём работы.

## 2. Ошибки не исчезают из отчёта

В другой серии три запроса: ok за 100 ms, deadline за 500 ms, ok за 300 ms;
wall time 1 s. Успешных 2, ошибок 1, error rate `1/3`, successful throughput
`2/s`, медиана успешной latency `(100+300)/2 = 200 ms`.

Если написать только «latency 200 ms», пропадёт треть запросов. Нельзя также
выдать deadline за медленный успешный ответ. Поэтому latency по успехам и
число неуспехов должны читаться вместе; времена ошибок остаются в raw.

## 3. TTFT, chunks и tokens

TTFT клиента — время dispatch → первый непустой content. Это ещё не чистое
время GPU prefill: там есть транспорт, очередь и подготовка. Client admission
queue хранится отдельно. Отсутствующий TTFT — `None`, не ноль.

Событие SSE может содержать несколько токенов, один токен или служебные поля.
Поэтому `len(chunks)` не заменяет `completion_tokens` от сервера. Для успешных
ответов с 4 и 8 tokens за wall time 1 s completed-output throughput равен 12/s.
Если один usage отсутствует, результат неизвестен. Частичный текст ошибочного
запроса не включён в эту метрику, но ошибка отражается рядом.

## 4. Маленькая выборка и процентили

Медиана двух чисел — среднее центральной пары. В нашем контракте эмпирический
p95 определяется ближайшим рангом `ceil(0.95*n)`; на `[1,2,…,20]` это 19.
Выбор определения должен быть записан: разные программы интерполируют иначе.

Для `n<20` поле оставляем пустым. Двадцать наблюдений тоже не обеспечивают
устойчивую оценку хвоста: правило лишь не позволяет печатать p95 на двух точках.
Production tail latency требует специально спроектированного опыта. Не нужно
маскировать этот пробел сотнями случайных повторов на своём ноутбуке.

## 5. Целостность артефакта и достоверность результата

SHA-256 показывает, что файл совпал с зафиксированными bytes. Совпадение model
revision и версии runtime исключает часть случайных сравнений разных запусков.
Ни hash, ни строка `provider: vllm` не доказывают происхождение файла: это требует
проверки команды, среды, логов и воспроизведения человеком.

После перезапуска проверяются тот же snapshot/config и наблюдаемый ответ.
Это отдельный результат от «модель отвечала один раз». В анализе нужно сохранить
и ограничения: OOM, невозможность concurrency 2, неизвестный peak memory или
отсутствующий server token usage — наблюдаемые ограничения, которые нельзя заменять нулями.
