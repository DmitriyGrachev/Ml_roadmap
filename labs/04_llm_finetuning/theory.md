# Как адаптировать поведение модели и не потерять контроль над результатом

Представьте модель, которая знает общие слова, но часто нарушает нужный формат
ответа. У вас есть несколько разрешённых примеров правильного поведения.
Стоит ли переобучать все её веса? Сначала задайте более дешёвый вопрос: можно ли
исправить инструкцию и проверить её на отложенных примерах?

Если же ответ зависит от свежего документа, смена весов сама по себе не делает
документ доступным: сначала рассмотрите retrieval. Fine-tuning (дообучение)
меняет параметры модели; RAG передаёт контекст на вход; prompting меняет
инструкцию. Эти механизмы могут дополняться, но сравниваются на одной задаче.

Prerequisites: [короткий gradient bridge](../../modules/04_machine_learning/07_training_bridge/README.md),
[PyTorch lifecycle](../01_pytorch_foundations/README.md) и
[Hugging Face](../02_huggingface_models/README.md). Здесь их не повторяем.

## От примера ответа к обучающей цели

SFT (supervised fine-tuning, дообучение по размеченным примерам) использует
входы и желаемые выходы. Для causal language model модель предсказывает следующий
токен по предыдущим. Chat template — конкретное оформление ролей и разделителей,
которое должно соответствовать выбранной модели и одинаково применяться при
обучении и использовании.

Условный учебный диалог просит перевести `red` в `rouge`. Символы ниже — маленький
алфавит для объяснения, **не** токенизация реальной модели:

| Позиция | 0 | 1 | 2 | 3 | 4 | 5 |
| --- | --- | --- | --- | --- | --- | --- |
| Токен | BOS | user | red | assistant | rouge | EOS |
| input ID | 1 | 2 | 7 | 3 | 8 | 4 |
| attention mask | 1 | 1 | 1 | 1 | 1 | 1 |
| labels для loss | -100 | -100 | -100 | -100 | 8 | 4 |

Все шесть входных токенов нужны для контекста. Но loss masking исключает из
целевой ошибки пользовательский текст и маркеры до ответа: `-100` — принятое
значение игнорируемой цели в данном PyTorch-контракте. Для обычного causal LM API
с внутренним сдвигом logits позиции 3 сравниваются с label позиции 4:
после `assistant` нужно предсказать `rouge`; после него — EOS. Не сдвигайте цели
вручную второй раз. Проверяйте контракт выбранного API, а не переносите схему
на любой head без проверки.

```text
контекст:  BOS user red assistant ──> цель rouge
контекст:  BOS user red assistant rouge ──> цель EOS
           видимый контекст              оцениваемый ответ
```

Прогноз: если все labels равны `-100`, чему обучается batch? Полезных целей нет;
это ошибка подготовки, даже если tensor имеет правильную форму. Если обнулить
attention mask на пользовательском тексте вместо labels, модель потеряет часть
вопроса. Это разные маски с разными задачами.

Packing объединяет короткие примеры в последовательности. Экономия padding
не оправдывает незаметное смешение независимых диалогов: нужно понимать границы,
attention и loss выбранной реализации. Первый опыт делайте без packing; усложняйте
только после проверки числа целевых токенов и отсутствия утечки между примерами.
Train/validation/test разделяются до вариантов одного исходного диалога.

Проверяемая связь таблицы с вычислением:

```powershell
.venv/Scripts/python.exe -m labs.04_llm_finetuning.sft_contract
```

Результат `[(3, 8), (4, 4)]` — пары `(позиция logits, ID следующего токена)`.
Этот маленький контракт проверяет одну последовательность с padding справа,
не сдвинутыми labels и хотя бы одной полезной целью. Он не токенизирует диалоги,
не реализует packing и не заменяет проверку chat template выбранной модели.

## Интуиция LoRA

Большую матрицу весов можно оставить неподвижной, а рядом обучить небольшую
поправку. LoRA (low-rank adaptation) описывает эту поправку произведением двух
матриц. Для одного слоя и строкового batch:

```text
                    frozen W [out, in]
                  ┌── x @ W.T ───────────────────┐
x [batch, in] ─────┤                              + ──> y [batch, out]
                  └── x @ A.T ──> @ B.T ──> scale ┘
                       [batch,r]    [batch,out]

A [r,in], B [out,r]; scale = alpha/r для обычного варианта
```

То есть `y = x @ W.T + scale * (x @ A.T) @ B.T`. Rank `r` задаёт размер
промежуточного пространства. Обучаются `r * (in + out)` чисел вместо `in * out`
исходной матрицы; это экономия только при достаточно малом `r`. Базовые веса,
активации и промежуточные вычисления всё равно нужны. LoRA не означает «модель
больше не занимает память» и не гарантирует улучшение качества.

## Один шаг полностью вручную

[demo.py](demo.py) намеренно не язык и не pretrained model: три числовых входа,
два выхода, rank 1, scale 1, без bias и dropout.

```text
W = [1 0 0]    A = [1 1 1]    B = [0]    x = [1 1 1]
    [0 1 0]                      [0]    target = [4 1]
```

До запуска предскажите: может ли нулевая B изменить начальный результат?

1. `x @ W.T = [1, 1]`; `x @ A.T = [3]`.
2. `[3] @ B.T = [0, 0]`, поэтому выход `[1, 1]` совпадает с базовым.
3. Mean squared error: `((1-4)^2 + (1-1)^2) / 2 = 4.5`.
4. Градиент ошибки по двум выходам равен `[-3, 0]`. Для B он умножается на
   промежуточное `[3]`: `grad_B = [[-9], [0]]`.
5. В первом шаге `grad_A = [[0, 0, 0]]`, потому что обратный путь проходит через
   пока нулевую B. У W градиента нет: её параметры заморожены.
6. SGD с learning rate `0.1`: `B_new = B - 0.1 * grad_B = [[0.9], [0]]`.
7. Новый выход `[1,1] + [2.7,0] = [3.7,1]`; ошибка `0.3^2 / 2 = 0.045`.

В float32 фактический выход — примерно `3.7000000477`, ошибка
`0.0449999869`: это округление, не иной алгоритм. В примере шесть frozen и пять
trainable параметров. Он выбран ради ручной арифметики, а не впечатляющей экономии.
Для слоя `4096 × 4096`, rank 8: `16 777 216` исходных чисел против `65 536`
чисел в поправке; это число параметров, не замер полной VRAM.

```powershell
.venv-training/Scripts/python.exe -m labs.04_llm_finetuning.demo
.venv-training/Scripts/python.exe -m labs.04_llm_finetuning.demo --output artifacts/lora-mechanism-01
```

Вторая команда требует нового каталога. Она сохраняет W и A/B отдельно,
загружает собственные только что созданные файлы, сравнивает выходы, затем
нарочно меняет базу. С прежней W `reload_parity=true`; с изменённой
`wrong_base_parity=false`. Формат этого минимального PyTorch примера — не PEFT
adapter format и не общий загрузчик произвольных checkpoint.

## Типичные ошибки и следующий опыт

### Настоящий PEFT lifecycle на локальном Transformer

Ручной шаг выше объясняет матрицы. Теперь [peft_demo.py](peft_demo.py) проверяет
следующий слой: causal Transformer с одной Llama-подобной decoder layer создаётся
из `LlamaConfig`, затем `get_peft_model` добавляет настоящие LoRA-параметры.
Все веса базы случайные, язык модель предварительно не изучала. Учебная задача —
повторить одно нейтральное слово (`repeat amber → amber`); задача самостоятельного
упражнения с описаниями предметов и выбранной pretrained моделью остаётся вашей.

Словарь из 13 токенов и шаблон заданы прямо в коде и сохраняются в `vocab.json`.
Это прозрачный whitespace encoder, без скачивания tokenizer. Примеры имеют
стабильные ID; все варианты одного слова находятся только в одном split:
`amber/birch/coral` — train, `dune/elm` — validation, `fern/grove` — test.
Словарь объявлен заранее как схема, test ответы не входят в обучающий batch.
Здесь четыре train и по два отложенных примера: слишком мало для вывода о качестве.

```text
local config + seed 17 ──> base weights ──> base/*.safetensors
                                │ frozen
train IDs ──> masked labels ──> LoRA q_proj/v_proj ──> adapter/*.safetensors
                                │ 24 AdamW steps
validation/test ──> eval loss + greedy IDs ──> saved reference logits
base digest + adapter digest ──> fresh interpreter ──> exact logits parity
```

Точные формы: hidden size 32, четыре query heads, две key/value heads, head dim 8.
`q_proj` имеет вес `[32,32]`, `v_proj` — `[16,32]`. Для rank 4 матрицы LoRA
равны `A_q [4,32]`, `B_q [32,4]`, `A_v [4,32]`, `B_v [16,4]`.
Всего `4×(32+32)+4×(32+16)=448` trainable чисел, `10144` frozen;
`alpha/r=8/4=2`. Эти числа описывают параметры, а не полную память процесса.

Для первого train-примера padded batch имеет форму `[4,7]`, logits — `[4,7,13]`.
Строка `BOS repeat amber answer amber EOS PAD` получает labels
`[-100,-100,-100,-100,5,2,-100]`: logits позиции 3 оцениваются по цели 5,
позиции 4 — по EOS=2. `sft_contract.causal_targets` проверяет каждую строку,
а отдельный тест сравнивает loss API с явным `cross_entropy(logits[:,:-1], labels[:,1:])`.
При `model.train()` выполняются forward, loss, backward и AdamW step; optimizer
получает только `requires_grad=True`. Перед отложенной оценкой — `eval()` и
`inference_mode()`. Dropout равен нулю, CPU использует один поток и deterministic algorithms.

Из корня, после подготовки отдельного opt-in окружения:

```powershell
$env:UV_PROJECT_ENVIRONMENT = '.venv-finetuning'
uv sync --locked --group finetuning --python 3.12
.venv-finetuning/Scripts/python.exe -m labs.04_llm_finetuning.peft_demo --output artifacts/peft-author-01
.venv-finetuning/Scripts/python.exe -m labs.04_llm_finetuning.peft_demo --verify artifacts/peft-author-01
$env:ROADMAP_RUN_PEFT = '1'
.venv-finetuning/Scripts/python.exe -m pytest labs/04_llm_finetuning -q
Remove-Item Env:ROADMAP_RUN_PEFT
Remove-Item Env:UV_PROJECT_ENVIRONMENT
```

Каталог запуска должен быть новым. Скрипт не скачивает модели или данные; загрузка
ограничена собственными локальными файлами с `local_files_only=True` и offline flags.
`identity.json` содержит SHA256 фактических base/adapter/config/vocab/data/reference
байтов, а `source_identity.json` связывает запуск с кодом demo и masking contract.
Перед загрузкой проверяются digest и точный набор файлов в каталогах модели.
Это проверка целостности operator-owned bundle: подписанного доверия к чужому
checkpoint она не создаёт. Дополнительный consumer config или подмена базы должны
останавливать загрузку ещё до `from_pretrained`.

`report.json` сохраняет версии, параметры, реальные train losses по шагам, начальные
и итоговые validation/test losses, bounded greedy predictions и число обновлённых
LoRA tensors. `loss.svg` строится из этих же измерений. В авторском запуске
11.10.2026 train loss до шагов 1/24: `2.537451 → 2.203713`, validation:
`2.530804 → 2.388297`, test: `2.562154 → 2.562948` — небольшое ухудшение.
Greedy ответы на test после адаптации — `amber EOS` и `birch EOS`, хотя ожидаются
`fern EOS` и `grove EOS`: механизм обучения работает, задачу повторения на новых
словах модель не решила. Снижение train/validation loss не отменяет этой ошибки.

Типичная ошибка — создать новую случайную базу и загрузить прежний adapter:
одинаковая архитектура не означает одинаковые веса. Скрипт сначала проверяет
сохранённую базу, затем загружает её и `PeftModel.from_pretrained`; отдельный
интерпретатор сравнивает все held-out logits точно (`torch.equal`), losses и
предсказания. Эта точность проверена для записанных CPU/версий; перенос на другой
backend может требовать отдельно обоснованного численного допуска.

Adapter checkpoint здесь воспроизводит inference, но не точное продолжение
обучения. Для resume нужны состояние optimizer, RNG и позиция в данных; разберите
[существующее самостоятельное resume упражнение](../01_pytorch_foundations/exercises/resume_training/README.md).
Для независимой бумажной вариации предскажите формы LoRA при rank 2 и число
trainable параметров. Затем в новом авторском каталоге измените learning rate,
сравните реальные train/validation значения, не выбирая настройку по test.
Этот дополнительный teacher run не закрывает ваш pretrained SFT experiment,
сравнение prompting/adapter, GPU или QLoRA.

Если обнулить и A, и B, градиенты обеих матриц в таком произведении сначала
нулевые. Поправка не начнёт учиться. В демонстрации A задана явно, B нулевая;
это делает начальный выход базовым, но оставляет путь обновления B.

Adapter-only checkpoint не включает всю базовую модель. Для воспроизведения
нужны исходные веса, конфигурация, tokenizer/chat template и версия адаптера.
Повторная случайная инициализация — другая база, даже при одинаковой архитектуре.
PEFT изменяет переданную модель при оборачивании: для baseline держите отдельную
исходную копию, не сравнивайте адаптер с уже изменённым объектом.

QLoRA использует квантованную базу вместе с адаптацией. Это отдельная проверка
backend/dtype/device, а не универсальное обещание запуска на 8 GB. Сначала
CPU-механика, затем совместимое отдельное GPU-окружение, измеренная память и
ограничения sequence length/batch. Не меняйте CPU training lock ради vLLM или
quantization. Крупная платная GPU без отдельного выбора не нужна.

Практика — [сравнение baseline, prompting и адаптации](exercise/README.md).
Существующий loss/optimizer/lifecycle код не выдаётся как решение этого опыта.
Сначала выполните prerequisite HF exercise; затем сами выберите и объясните
конфигурацию. Снижение training loss без независимого улучшения не закрывает задачу.

## Вопросы на понимание

1. Почему первая B получает градиент, а A — пока нет?
2. Как изменятся формы и число параметров, если rank станет 2?
3. Почему модель видит user tokens, хотя они не входят в loss?
4. Чем ошибка с packing отличается от неправильного padding?
5. Почему загрузка адаптера на другую базу не воспроизводит эксперимент?
6. Когда retrieval полезнее изменения весов?
7. Какие две деградации проверите, даже если средняя метрика стала лучше?
