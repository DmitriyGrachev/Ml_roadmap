## 1. Почему одного линейного правила мало

Представьте изображение `4×4`: нужно выбрать, вертикальная на нём полоса или горизонтальная. **Признак (feature)** — число, доступное до ответа: здесь каждая из 16 яркостей. **Цель (target)** — правильный индекс класса `0` или `1`; её нельзя подавать модели как признак. **Параметры (parameters)** — числа, которые обучение меняет: **веса (weights)** масштабируют признаки, **смещение (bias)** добавляется и при нулевом входе. Вход и цель относятся к наблюдению, параметры принадлежат модели.

Одно правило `z = x Wᵀ + b` строит суммы признаков. Если подряд поставить два таких правила без нелинейности, результат снова будет одной линейной/аффинной функцией входа: `((x W₁ᵀ + b₁) W₂ᵀ + b₂)` можно перегруппировать. Поэтому между слоями ставят **активацию (activation)**. В нашем примере `ReLU(t) = max(0,t)` обнуляет отрицательные значения и сохраняет положительные. Она позволяет разным областям входов проходить через разные активные скрытые координаты. Это не обещание, что любая сеть или любой набор данных будут хорошо классифицироваться.

**Прогноз до запуска:** если изменить только вес, соединяющий яркость пикселя с первой скрытой координатой, затронет ли это оба выходных класса? Где изменение может остановиться?

## 2. Один проход по сети, с единым соглашением о формах

В формулах **наблюдения — строки**. Для `B` изображений вход `X` имеет форму `[B,1,4,4]` (`1` — канал). `Flatten` даёт матрицу `F` `[B,16]`; координаты каждой строки соответствуют пикселям в порядке развёртки. В коде `nn.Linear(in_features,out_features)` хранит `weight` как `[out_features,in_features]` и считает `input @ weight.T + bias`. Поэтому размеры модели `16 → 8 → 2` таковы:

| Шаг | Формула | Форма при `B=1` | Смысл |
| --- | --- | --- | --- |
| Изображение | `X` | `[1,1,4,4]` | число объектов, канал, строки, столбцы |
| Развёртка | `F = Flatten(X)` | `[1,16]` | 16 признаков одной строки |
| Первый слой | `Z₁ = F W₁ᵀ + b₁` | `[1,8]` | `W₁:[8,16]`, `b₁:[8]` |
| Активация | `H = ReLU(Z₁)` | `[1,8]` | скрытое представление |
| Второй слой | `S = H W₂ᵀ + b₂` | `[1,2]` | `W₂:[2,8]`, `b₂:[2]`; два **logits** |
| Цель и loss | `y:[1]`, `L=CE(S,y)` | `[]` | индекс класса `int64`, средний скалярный loss |

`Z₁` и `S` — разные выходы слоёв. **Logit** — ненормированный балл класса: он может быть любым действительным числом и не обязан суммироваться в единицу. **Слой (layer)** выполняет преобразование; сеть составляет из слоёв функцию `X → S`. Для предсказанного класса выбирают индекс максимального logit по последней оси. `argmax` полезен для метрики, но сам выбор индекса не даёт гладкий сигнал для обучения.

В полностью ручном опыте одна картинка имеет все нулевые пиксели, кроме `F[0,1]=1`. Здесь для точного сравнения с ручной производной используется `float64`; обычный цикл ниже использует `float32`. Все параметры принудительно равны нулю, кроме `W₁[0,1]=1` и `W₂[0,0]=1`; смещения нулевые. Эти индексы означают `[выходная координата, входная координата]`, как в `nn.Linear.weight`. Цель `y=[0]` формы `[1]` — первая категория. Считаем без скрытых шагов:

1. `Z₁[0,0] = 1×1+0 = 1`; остальные семь координат `0`. Значит `Z₁=[1,0,0,0,0,0,0,0]` формы `[1,8]`.
2. `H=ReLU(Z₁)=[1,0,0,0,0,0,0,0]` формы `[1,8]`.
3. `S[0,0]=1×1+0=1`, `S[0,1]=0`; значит `S=[1,0]` формы `[1,2]`.
4. Для объяснения переводим logits в вероятности: `p₀=e¹/(e¹+e⁰)≈0.731058579`, `p₁≈0.268941421`. Выбранный класс `0`, но правильный выбор сам по себе не означает нулевой loss: уверенность меньше 1.
5. Cross-entropy для правильного класса: `L=−log(p₀)=log(1+e⁻¹)≈0.313261688`. Это скаляр `[]`.

`nn.CrossEntropyLoss()` получает **именно `S` формы `[B,2]`**, а в этом варианте — `y` формы `[B]` с типом `torch.int64` и индексами `0`/`1`. Она внутри сочетает `log_softmax` и отрицательный log likelihood; передавать ей уже нормализованные вероятности `softmax(S)` означало бы применить преобразование дважды и изменить задачу. Вероятности нужны для интерпретации/калибровки после forward, индексы `argmax` — для accuracy. PyTorch поддерживает у этого loss также цели в виде распределений классов при ином контракте формы/типа; наши индексные метки — выбор этой лабораторной, не универсальный закон для каждого loss. Если вместо классификации предсказывать непрерывную массу, выход мог бы иметь форму `[B,1]`, цель — согласованную вещественную форму, а loss, например MSE, сравнивал бы число с числом: два logits и `int64` индекс класса тогда не нужны.

**Типичная ошибка:** увидеть форму `[B,2]` и принять ось `2` за размер батча либо передать цели `[B,1]` как будто это тот же индексный контракт. Запишите смысл каждой оси до исправления кода.

Ручная трасса использует `float64` на CPU для аккуратного сравнения производных;
короткое обучение ниже — обычный `float32`. Индексные метки в обоих случаях
остаются `int64`. Это разные роли типов, а не требование одного dtype для всех
тензоров программы.

## 3. Обратный проход и реальное изменение параметров

Прямой вычислительный граф для этой картинки выглядит так (это схема зависимостей, а числа выше — результаты):

```text
F[0,1]=1 -- W₁[0,1]=1, b₁[0]=0 --> Z₁[0,0]=1 -- ReLU --> H[0,0]=1
H[0,0]=1 -- W₂[0,0]=1, b₂[0]=0 --> S[0,0]=1
H[0,0]=1 -- W₂[1,0]=0, b₂[1]=0 --> S[0,1]=0
[S[0,0], S[0,1]]=[1,0] -- y=0 --> CE=0.313261688
```

При `backward` правило цепочки идёт от скалярного loss к параметрам. Для одного объекта производная по двум logits равна `p−one_hot(y)`, то есть `∂L/∂S=[−0.268941421,+0.268941421]` формы `[1,2]`. У первого скрытого значения `ReLU′(1)=1`. Поэтому `∂L/∂H[0,0] = (−0.268941421)×W₂[0,0] + (+0.268941421)×W₂[1,0] = −0.268941421`. Далее `∂L/∂Z₁[0,0]=−0.268941421`, а умножение на `F[0,1]=1` даёт градиент первого выбранного веса. Для остальных скрытых координат `Z₁=0`: PyTorch выбирает производную ReLU в нуле равной нулю, поэтому их входящие градиенты в этом специально устроенном опыте нулевые. Нулевая инициализация почти всех весов служит только ручной трассе: она создаёт симметрию/«мёртвые» пути и **не является рецептом инициализации обучаемой сети**.

| Параметр | До шага | `parameter.grad` после `backward` | После SGD при `lr=0.1` |
| --- | ---: | ---: | ---: |
| `W₁[0,1]` | `1` | `−0.268941421` | `1.026894142` |
| `b₁[0]` | `0` | `−0.268941421` | `0.026894142` |
| `W₂[0,0]` | `1` | `−0.268941421` | `1.026894142` |
| `b₂[0]` | `0` | `−0.268941421` | `0.026894142` |
| `W₂[1,0]` | `0` | `+0.268941421` | `−0.026894142` |
| `b₂[1]` | `0` | `+0.268941421` | `−0.026894142` |

Каждая строка использует `θ_new=θ_old−η ∂L/∂θ`, где `η=0.1` — **learning rate**. `b₁` и `b₂` отдельные обучаемые параметры, а не последние столбцы `W`. В оптимизатор переданы *все* параметры сети; таблица показывает только шесть информативных координат, не выборочно обновляемое подмножество. После `optimizer.step()` следующий forward использует новые веса: для той же картинки трасса даёт `loss_after≈0.271670202`, ниже исходного `0.313261688`. Это один проверяемый шаг. Большой `η` способен перескочить полезную область; один удачный шаг не задаёт подходящий `η` для всех задач.

`forward → loss → backward → gradients → optimizer.step → следующий forward` — причинная цепочка. **Autograd** записывает операции при forward и вычисляет производные обратным проходом с локальными правилами, не оценивает их конечными разностями. `.grad` у обучаемых листовых параметров (`nn.Parameter` с `requires_grad=True`) хранит накопленную производную; `torch.autograd.backward(loss)` в трассе (как и `loss.backward()`) обычно **прибавляет** новый вклад. Если выполнить два `backward` без очистки, в `.grad` будет сумма обоих вкладов — это может быть намеренное накопление, но обычный один шаг на батч требует `optimizer.zero_grad()` перед forward/backward. Трасса дважды вычисляет градиент той же картинки: `accumulated_w20` примерно вдвое больше `gradients.w20`; после `zero_grad(set_to_none=True)` все `.grad` становятся `None`, а новый `backward` получает одиночный вклад. `optimizer.step()` читает `.grad` и меняет параметры; он не вычисляет производные. Ручная таблица показывает механизм, [конечная разность в мосте](../../modules/04_machine_learning/07_training_bridge/theory.md#4-размер-шага-и-численная-проверка) — независимую численную проверку одной координаты, а autograd — рабочий способ обучения. В трассе конечной разностью проверяется `W₂[0,0]` вдали от излома ReLU: при `ε=10⁻⁵` этот вес сначала ставят в `1+ε`, затем в `1−ε`, остальные параметры фиксированы, и считают `[L(1+ε)−L(1−ε)]/(2ε)≈−0.268941421`. Слишком большой или крошечный `ε` даёт погрешность; буквального равенства последних цифр ждать нельзя.

Если перед `backward` заменить **нужный для loss** logit на `logit.detach()`, извлечь `logit.item()` в обычное Python-число или перейти через NumPy и создать новый tensor, связь с исходным параметром исчезнет. Это не запрет на `.detach()`/`.item()`: после вычисления настоящего loss ими удобно взять значение для журнала, например `float(loss.detach())`, не удерживая граф в списке логов. Но обучаемый `loss` должен остаться связанным с параметрами до `backward`.

**Самостоятельная вариация, без изменения задания:** сначала предскажите знак `∂L/∂W₂[1,0]`, если цель этой же картинки сменить на `1`, затем повторите ручные два logit и loss. Не переносите эту искусственную инициализацию на собственный набор.

## 4. Что происходит за эпоху

В этом опыте cross-entropy не использует веса классов и игнорируемые метки:
каждая строка участвует одинаково. Правило усреднения ниже относится к этому
случаю; для взвешенного loss сначала выясните, какой знаменатель использует API.

[Прежний пример](example.py) создаёт 26 локальных картинок с полосами и небольшим шумом. Первые 19 ID идут в train, последние 7 — в validation. Отдельная [преподавательская трасса](walkthrough.py) повторяет эту **соседнюю задачу** на свежей обычной инициализации сети, не импортируя `starter.py`. В ней батч train размера 6 даёт `6,6,6,1`, а батч validation размера 3 даёт `3,3,1`. **Итерация / optimizer step** — одно обновление после одного train-батча; **эпоха (epoch)** — проход по всему train-набору. Здесь 4 эпохи означают 16 шагов оптимизатора, включая четыре коротких последних батча. Validation проходит после эпохи без обновлений.

Одна строка `Dataset` возвращает изображение `[1,4,4]` `float32` и скалярную метку `int64`; `DataLoader` собирает `B` строк в `[B,1,4,4]` и `[B]`. При подготовке батча данные и модель должны быть на одном `device` (`cpu` здесь), а `dtype` должен соответствовать операциям и loss. Модель (`nn.Module`) и optimizer создаются **один раз** до циклов; параметры сохраняют состояние между батчами. Батч, logits, loss и граф возникают заново на каждом шаге. Для `CrossEntropyLoss(reduction="mean")` loss батча усреднён по его строкам. Средний loss эпохи при неодинаковых батчах — `Σ(batch_loss × batch_count)/Σbatch_count`, а не среднее четырёх средних: короткая последняя строка не должна весить столько же, сколько шесть строк. Accuracy — `число верных / число просмотренных` с явным `count`. Для validation правило счёта то же. В трассе `train_loss` собирается **во время** последовательных обновлений, когда параметры меняются между батчами; `validation_loss` измеряется **после** эпохи на одном итоговом состоянии параметров. Эти наблюдения полезны, но их разность не является чистой оценкой train–validation gap при одинаковых весах.

Состояние `model.train()` включает обучающее поведение слоёв, например dropout и обновление статистик BatchNorm. `model.eval()` переключает их поведение; **само по себе оно не отключает autograd**. `torch.no_grad()` не строит граф для validation и inference; **само по себе оно не переключает dropout в режим оценки**. Поэтому в полном цикле используют оба действия. У `ShapeNet` нет dropout/BatchNorm, но явный режим делает смысл цикла видимым. Отдельный `mode_probe` в трассе использует маленький dropout-модуль: в `eval()` с разрешённым autograd результат всё ещё отслеживает градиент; в `train()` под `no_grad()` градиента нет, хотя dropout остаётся в режиме обучения. Полный цикл сохраняет флаги и норму изменения параметров при validation; reload сравнивает logits исходной и свежей модели при inference.

Преподавательский checkpoint в прежнем формате примера содержит только `{"model_state": model.state_dict(), "epoch": ...}`. Его достаточно, чтобы загрузить веса в новый `ShapeNet` и сравнить inference на тех же данных. Он **не** сохраняет optimizer, курсор батча и случайные генераторы, поэтому не обещает продолжить тот же run. Для настоящего продолжения после остановки есть отдельное существующее упражнение [resume training](exercises/resume_training/README.md) со своим контрактом; ещё один формат checkpoint здесь не вводится. При чтении доверенного локального файла используйте `map_location` и `weights_only=True`; checksum подтверждает байты, но не делает произвольный чужой файл доверенным.

## 5. Если обучение выглядит неправильным

Идите от первого нарушенного предположения: данные и target → формы/`dtype`/loss → значения forward → наличие и масштаб `.grad` → разность параметров после `step` → режим и отсутствие графа на validation → агрегаты, ID и split. Измеряйте **один** подозреваемый переход на маленьком фиксированном батче. У симптома обычно несколько причин; таблица предлагает различающую проверку, а не готовый ответ для [контрольной диагностики](debugging/README.md).

| Наблюдение | Конкурирующие объяснения | Что измерить; как читать результат |
| --- | --- | --- |
| Параметры не меняются | Граф оборван; нет `backward`; нулевые градиенты; параметр не передан optimizer; `lr=0` | Сравните `requires_grad`, `.grad` и копию одного параметра до/после `step`. Ненулевой `.grad` при нулевой дельте сужает поиск к шагу/настройке optimizer, но не доказывает одну причину. |
| Train loss не снижается | Неверные метки/признаки; слишком большой или малый шаг; насыщенные/нулевые пути; ошибка подсчёта | Зафиксируйте батч и seed, выведите logits, loss, норму градиента и потери до/после одного шага. Падающий loss на одном батче подтверждает работоспособность этого пути, не гарантию сходимости по всем эпохам. |
| Появились `NaN`/`inf` | Неконечный вход; масштаб значений/градиента; неподходящий learning rate; неверная ручная формула | Найдите **первый** не конечный тензор: вход → logits → loss → grad → параметры. Если вход конечен, а первый сбой после шага, это повод исследовать масштаб шага и градиента, а не слепо заменять все числа нулями. |
| Train лучше, validation хуже | Переобучение; сдвиг split; leakage или неверный validation mode; малая шумная выборка | Сверьте ID, preprocessing и режим, затем кривые по эпохам при одном split. Расхождение может быть переобучением только после исключения ошибки измерения; маленький split даёт большую неопределённость. |
| Accuracy выглядит неверной | Перепутана ось `argmax`; порядок меток не совпал с ID; потерян короткий батч; усреднены batch accuracy без весов | Возьмите 2–3 строки с известными logits/метками и вручную пересчитайте `argmax`, верные ответы и общий `count`. Если ручной счёт не совпал, сначала исправьте способ измерения, не меняйте сеть. |

Контролируемый опыт проверяет механизм; оценка обобщения требует независимых данных и дисциплины [протокола эксперимента](../../docs/experiment-protocol.md). Зелёный unit test или короткий smoke подтверждает конкретный вычислительный контракт; реальное качество модели и содержательное понимание ученика проверяются отдельно.

## 6. Что ещё встретится в моделях

Это **дополнительное углубление** для чтения более сложных примеров, не новая обязательная реализация. Обычная случайная инициализация разрывает симметрию скрытых нейронов; при выборе её масштаба учитывают активацию и глубину. Нулевая ручная сеть выше годится только для арифметики. **Dropout** случайно обнуляет часть активаций во время обучения и обычно не делает этого при `eval`; он ограничивает зависимость от отдельных путей, но не заменяет проверку данных. **BatchNorm** в обычном режиме использует статистики батча и может хранить running statistics для оценки; **LayerNorm** нормирует по выбранным измерениям самого примера. Их оси и режимы различны, они не взаимозаменяемы. **Weight decay** сдерживает рост весов, однако связь с явным L2 штрафом зависит от оптимизатора и способа реализации; для AdamW decay отделён от моментов градиента. Проверяйте конкретный API, прежде чем переносить формулу из одного optimizer в другой.

SGD без momentum в ручной таблице использует текущий градиент и один общий `lr`. **Adam** дополнительно поддерживает скользящие оценки среднего градиента и его квадрата, корректирует стартовое смещение оценок и масштабирует обновление каждой координаты; это помогает при разном масштабе координат, но не отменяет выбор `lr`, проверку данных и validation. Состояние optimizer существенно для точного resume. Реализовывать Adam самостоятельно в этой лабораторной не нужно.

## Источники и граница чтения

Сверено с официальной документацией PyTorch **2.14**, 2026-10-04; версии окружения закреплены в [compute guide](../../docs/compute-guide.md). Читать достаточно указанные разделы; документация дополняет рассчитанный выше пример.

- PyTorch, [Linear](https://docs.pytorch.org/docs/2.14/generated/torch.nn.Linear.html), английский: `Variables` и `Shape` для ориентации веса `[out,in]` и входа `[*,in]`; остановитесь после описания формы и примера.
- PyTorch, [CrossEntropyLoss](https://docs.pytorch.org/docs/2.14/generated/torch.nn.CrossEntropyLoss.html), английский: описание **class indices** и `Shape`; для logits, целевых индексов и встроенной `LogSoftmax`+`NLLLoss`. Не переносите этот контракт на другой loss.
- PyTorch, [Autograd mechanics](https://docs.pytorch.org/docs/2.14/notes/autograd.html), английский: `How autograd encodes the history` и `Locally disabling gradient computation`, особенно различие grad modes и `eval()`; дальше внутренние детали не обязательны.
- PyTorch, [SGD](https://docs.pytorch.org/docs/2.14/generated/torch.optim.SGD.html) и [Adam](https://docs.pytorch.org/docs/2.14/generated/torch.optim.Adam.html), английский: описания `Parameters`/алгоритма для роли learning rate, momentum и weight decay; реализовывать их формулы здесь не требуется.

Материал проверяет вычислительную механику на одной искусственной сети. Самостоятельный отчёт ученика и оценка качества на пригодных данных остаются отдельной работой.
