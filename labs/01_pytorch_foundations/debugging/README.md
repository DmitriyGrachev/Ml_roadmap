# Контроль №3 — расследование обучения

Prerequisites: [lab-pytorch](../README.md),
[ml-training-bridge](../../../modules/04_machine_learning/07_training_bridge/README.md).
Новый независимый ID: `lab-training-diagnostics`, optional training group, CPU/offline.

## Цель и входы

Расследуйте четыре независимых варианта A–D. Для каждого воспроизведите наблюдаемый
сбой, предложите конкурирующие гипотезы, выберите измерение, внесите минимальное
обоснованное изменение и защитите результат. В наборе затрагиваются градиенты,
формы тензоров/маски/loss, train/eval и взаимодействие LR с масштабом данных.
Соответствие вариантов причинам предстоит установить самостоятельно.

`case_a.py` … `case_d.py` — неисправные входные программы, а не образцы правильного
обучения. `fixtures.SNAPSHOT` содержит шесть небольших последовательностей по два
токена, два признака и скалярную цель; bool-маска `True` обозначает учитываемую цель.
Четыре объекта обучающие, два валидационные; split по ID фиксирован. Harness создаёт
Dropout(0.3) + Linear(2,1), SGD и восемь шагов на CPU. Для этого расследования
целевая функция — средний squared error только по учитываемым целям. Требования
к accuracy нет; способность исправить симптом не доказывает обобщение модели.

## Editable files и ограничения

Редактируйте `starter.py` и собственные локальные модули (например,
`my_case_a.py`); сохраните исходные case-файлы, fixtures, evidence и тесты.
`investigate(case_id: str, output_dir: Path) -> Path` остаётся вашим TODO.
Все обязательные действия CPU/offline, без загрузки модели/данных и внешних API.
Не подавляйте исключения, не заменяйте вычисления готовыми JSON-метриками и не
подбирайте ответ по ID. Сравнивайте одну и ту же выборку, split, seed, архитектуру,
число шагов и контракт loss; LR можно изменить с обоснованием. При анализе масштаба
не подменяйте сохранённые входные данные. Изменение предобработки внутри вашего
варианта требует отдельного объяснения. Избегайте изменений нескольких факторов сразу.

## Контракт измерений и артефактов

`run_case(case_id, output_dir, *, seed)` возвращает новый каталог с фактическими
наблюдениями исходного варианта. `run_variant(case_id, source: Path, output_dir,
*, seed)` исполняет **явно переданный доверенный** локальный Python-файл и сохраняет
те же наблюдения. Это исполнение кода, не песочница; импортов, скачиваний и побочных
эффектов в модуле быть не должно. Файл должен быть самостоятельным, без относительных
импортов, и определять:

- `CONFIG = {"lr": <положительное конечное число>, "steps": 8}`;
- `step(model, optimizer, x, y, mask) -> (prediction, scalar_loss)`: один реальный
  шаг, возвращающий тензоры, по которым он обучался; shapes `(4, 2, 1)` у prediction/y;
- `validate(model, x) -> prediction`: один forward на валидации `(2, 2, 1)`.

Harness регистрирует параметры до/после, возвращённые prediction/loss, градиенты
после шага, реальные train outputs, повторные validation outputs, режим и grad context
внутри validation forward. Во время фактического ученического training forward
отдельный hook фиксирует режим Dropout child и вероятность: родительского
`model.training` недостаточно. Harness не сбрасывает режим перед ученическим шагом:
переход из validation в train тоже является частью вашего варианта.
Измерительные validation-повторы изолируют RNG, не потребляя
случайность обучающего шага. RuntimeError/ValueError шага сохраняются как симптом,
но прочие ошибки harness остаются ошибками. При таком исключении trace обрывается.
После исправления нужны восемь шагов: конечные loss/градиенты/параметры,
изменение параметров, корректные формы/маски/loss, стохастичность только в train,
детерминированная валидация без графа градиентов. См. `assert_healthy`.

`investigate` возвращает корень следующего набора, используя новый каталог:

```text
investigation/
  before/  manifest.json, snapshot.json, split.json, source.py, trace.pt
  after/   manifest.json, snapshot.json, split.json, source.py, trace.pt
  report.json
```

Оба подкаталога создавайте соответствующими harness-вызовами с одинаковым seed.
В `report.json` нужны непустые текстовые поля `hypotheses`, `measurements`,
`minimal_change`, `defense` и `review_status: "REQUIRES_REVIEW"`. Включите численные
измерения и ссылки на шаги trace, отвергнутую альтернативу, минимальный diff,
ограничения и собственное объяснение причин. Наличие текста не оценивает его качество.
Hashes привязывают manifest к bytes данных, split, source и trace; validator
независимо повторяет обе программы и сверяет фактические наблюдения, включая ID.
Файлы с nonfinite тензорами допустимы как исходное свидетельство сбоя.

`validate_evidence(root, *, trusted_student_source=None) -> None` проверяет
сопоставимость и replay, **не** утверждает, что исправление удачно. По умолчанию
он отказывается исполнять after/source.py. Для проверки сохранённой работы сначала
прочитайте этот файл и явно укажите его точный путь; hash/manifest не дают разрешения
на исполнение. Corrective tests доверяют только результату собственного вызова
вашей `investigate` в заранее назначенном новом временном каталоге. До выдачи
доверия проверяются отсутствие каталога до вызова, точное совпадение resolved root
и нахождение resolved source внутри него, включая symlink/junction. Затем проверяют
`assert_healthy(after)`. Ученический отчёт не генерируется инфраструктурой.

## Команды (из корня, PowerShell / PyCharm terminal)

Используйте уже подготовленный interpreter с training group (см. lab-pytorch).
Каждый путь результата должен быть новым; существующие файлы не перезаписываются.

```powershell
python -m labs.01_pytorch_foundations.debugging.fixtures a .scratch/diagnostic-a-001 --seed 23
python scripts/learn.py test lab-training-diagnostics
python scripts/learn.py check lab-training-diagnostics
python -m labs.01_pytorch_foundations.debugging.evidence .scratch/my-investigation --trusted-student-source .scratch/my-investigation/after/source.py
```

Повторите исследования для `b`, `c`, `d`. Выходы при разработке тестов создавайте
через `tmp_path`, а не поверх своей работы. `test` допускает только ожидаемую
незавершённость TODO; `check` отклоняет любой xfail/skip. Старый `check lab-pytorch`
не включает эту контрольную. Базовая среда без Torch пропускает эти optional tests;
это не зачёт, strict check требует training interpreter.

## Staged hints

1. Сначала сравните входные размеры, ID, scalar loss и изменение параметров между
   соседними шагами. Найдите самое раннее расхождение с ожидаемым инвариантом.
2. Повторите наблюдение с тем же seed. Измерьте градиенты, распределения чисел и
   одинаковые входы в разных фазах; отделите проблему измерения от проблемы обучения.
3. Сопоставьте порядок операций с жизненным циклом одного шага. Проверьте смысл
   каждой оси и каждой masked цели, состояние модели и контекст вычислений.
4. Для защиты объясните, какое измерение опровергло бы вашу гипотезу. Проверьте
   устойчивость вывода на дополнительном seed; не подменяйте сравнение новой выборкой.

## Rubric и виды свидетельств

- Unit/infrastructure: bytes, identity, отказ при подмене trace, явное доверие source.
- Smoke: все исходные варианты реально исполняются и сохраняют различные симптомы;
  их неисправность ожидаема и не означает поломку инфраструктуры.
- Corrective/evaluation: ваш TODO вызывается для каждого варианта; неверная готовая
  реализация падает обычным assertion. Только NotImplementedError границы даёт xfail.
  Восстановленные инварианты не являются оценкой качества на реальном датасете.
- Human review: воспроизводимость гипотез, выбор измерений, минимальность изменения,
  честное before/after и устная защита — `REQUIRES_REVIEW` до проверки человеком.

Контрольная завершена, когда все четыре расследования проходят строгие проверки
и человек принимает объяснения. Инфраструктурный зелёный набор этого не означает.
