# Лабораторная 01 — основы PyTorch

**Приоритет:** CORE. **Готовность материала:** READY. **Зачёт ученика:** не начат.
Ориентир: 3–5 часов. Здесь вы реализуете полный локальный цикл классификации
предметов по числовым признакам; оценки качества реальной задачи эта лабораторная
не обещает.

## Цель и опора

После работы вы сможете объяснить и выполнить цепочку `Dataset → DataLoader →
Module.forward → loss → backward → optimizer.step → validation → checkpoint →
reload → inference`. Перед началом полезны [NumPy и формы массивов](../../modules/03_data_foundations/01_numpy/README.md),
[разделение без утечки](../../modules/03_data_foundations/05_splits_and_leakage/README.md),
[метрики](../../modules/04_machine_learning/05_evaluation/README.md) и
[воспроизводимость](../../modules/04_machine_learning/06_reproducibility/README.md).
Короткий [мост к autograd](../../modules/04_machine_learning/07_training_bridge/README.md)
связывает знакомое обновление параметров с этой работой.

## Минимальная теория

Отдельное продолжение после `lab-pytorch`: [возобновление той же траектории обучения](exercises/resume_training/README.md)
(`lab-training-resume`, собственный зачёт).

Тензор имеет форму (`shape`), тип (`dtype`) и устройство (`device`). Для одного
предмета пусть есть четыре числовых признака: ширина, высота, масса и яркость.
Батч из пяти предметов имеет форму `[5, 4]` и тип `float32`; метки пяти классовых
наблюдений имеют форму `[5]` и тип `int64`. Первая ось — количество наблюдений,
поэтому последний неполный батч нельзя молча отбросить. Параметры модели, признаки
и метки должны находиться на согласованных устройствах. Для `CrossEntropyLoss`
модель возвращает **логиты** `[batch, classes]`, без предварительного `softmax`.

В `forward` параметры преобразуют признаки в логиты. Функция потерь сравнивает
логиты с метками. `loss.backward()` накапливает градиенты по правилу цепочки;
`optimizer.step()` использует их для изменения весов. Каждый train-батч начинает
с `zero_grad()`, иначе градиенты сложатся с предыдущими. Валидация включает
`model.eval()` и `torch.no_grad()`: режим отключает поведение вроде dropout, а
контекст не строит граф вычислений. Сравнивайте метрики на одном заранее
зафиксированном validation split, не подбирая модель по тестовому набору.

## Подготовка

Из корня репозитория в PowerShell:

```powershell
uv sync --group training
uv run --group training python -m labs.01_pytorch_foundations.example --output generated-reports/pytorch/smoke
uv run --group training python -m pytest labs/01_pytorch_foundations -q
uv run --group training python scripts/learn.py check lab-pytorch
```

В Linux/WSL команды те же. В PyCharm выберите интерпретатор окружения после
`uv sync --group training`, working directory — корень репозитория, а модуль
примера — `labs.01_pytorch_foundations.example`. Скачивания данных и моделей нет;
ключи и платные сервисы не нужны. CPU достаточно. Сам smoke занимает небольшие
секунды и использует меньше мегабайта собственных данных и весов; объём
установки PyTorch зависит от выбранных платформенных wheel. GPU не требуется,
CUDA/8 GB VRAM и скорость на вашем ноутбуке здесь не проверены.

`example.py` — маленькая **соседняя** задача: синтетические картинки с горизонтальной
или вертикальной полосой. Он показывает все стадии цикла и пишет только механический
smoke-checkpoint. Его вывод `quality_claim: false` означает, что он не подтверждает
прикладную точность. Ваша задача ниже использует **табличные признаки предметов**,
отдельный контракт и отдельный отчёт. Не переносите готовые ответы из примера в
`starter.py`.

## Ваш контракт

Создайте локальный набор без персональных данных: стабильные ID предметов,
четыре числовых признака и два или более класса. Можно придумать небольшие
синтетические наблюдения, но пометьте их в собственном анализе. Не скачивайте
неизвестные файлы. Зафиксируйте seed, исходные строки/версию, train и validation
ID. `starter.py` оставлен незавершённым намеренно:

1. `make_loaders`: проверьте одинаковую длину данных, прямоугольные конечные
   признаки, целочисленные метки, допустимые непересекающиеся индексы, положительный
   размер батча и seed. Оберните строки в `Dataset`; создайте воспроизводимый
   перемешиваемый train loader и неперемешиваемый validation loader. Ни одну строку
   не теряйте, включая последний короткий батч.
2. `build_model` и `prepare_batch`: создайте `nn.Module` с trainable параметрами
   и `forward` для `[batch, input_dim] → [batch, n_classes]`; подготовьте `float32`
   признаки и `int64` метки на выбранном device. Неконечные входы и неверные формы
   отвергайте `ValueError`.
3. `train_epoch`: `train()`, очистка градиентов, forward, loss, backward, step;
   возвращайте среднюю loss, взвешенную по **количеству строк**, и count. Пустой
   loader отвергайте. `validate_epoch`: `eval()`, без градиентов и обновления
   весов; возвращайте loss/count/accuracy на всех строках.
4. `analyze_errors`: по логитам, меткам и ID верните только ошибочные прогнозы
   в порядке наблюдений. Равные логиты разрешайте так же, как `argmax` (первый
   индекс). Осмотрите ошибки и сформулируйте закономерность в отчёте.
5. Для итогового прогона используйте `torch.optim.SGD` с ненулевым `momentum`
   (например, `0.9`), чтобы checkpoint содержал состояние optimizer после
   выполненного шага. `save_checkpoint`/`load_checkpoint`: сохраняйте словарь из `state_dict()`
   модели (`model_state`), optimizer state (`optimizer_state`) и простых
   метаданных (`metadata`: `seed`, `epoch`, `train_ids`, `validation_ids`);
   загрузка с `map_location=device`
   и `weights_only=True`. Никаких сериализованных экземпляров `nn.Module` или
   непроверенных pickle-файлов. `predict_classes`: `eval()` и `no_grad()`, одна
   метка на строку после повторной загрузки.

### Артефакт эксперимента

Создайте `generated-reports/pytorch/report.json`, локальный снимок исходных строк
(например, `observations.csv`) и checkpoint под `generated-reports/pytorch/`.
Все пути в JSON задавайте относительно **корня репозитория** (working directory
команд выше) или абсолютными путями; каталог снимка и checkpoint должен быть
`generated-reports/pytorch/`. Эти outputs не коммитятся. Схема версии 1:

```json
{
  "schema_version": 1,
  "task": "object-features-v1",
  "seed": 23,
  "dataset": "generated-reports/pytorch/observations.csv",
  "dataset_sha256": "64 lowercase hex chars",
  "code_revision": "git commit SHA or working-tree (dirty)",
  "config": {
    "batch_size": 8, "learning_rate": 0.01, "epochs": 2, "device": "cpu",
    "input_dim": 4, "n_classes": 2, "optimizer": "SGD", "momentum": 0.9
  },
  "train_ids": ["..."],
  "validation_ids": ["..."],
  "checkpoint": "generated-reports/pytorch/your-run.pt",
  "checkpoint_sha256": "64 lowercase hex chars",
  "versions": {"python": "actual version", "torch": "actual version"},
  "labels": [0],
  "predictions": [0],
  "metrics": {"count": 1, "accuracy": 1.0},
  "analysis": {
    "error_pattern": "Ваше наблюдение о неверных ответах и ограничениях набора",
    "next_experiment": "Следующий конкретный опыт для проверки гипотезы"
  }
}
```

Значения выше показывают **форму**, не результат: замените каждое на фактический
прогон. Список `validation_ids` имеет тот же порядок, что `labels` и `predictions`.
`report.validate_report` сверяет длины, пересечение split, пересчитывает accuracy,
проверяет SHA-256 байтов снимка и checkpoint, параметры запуска, размеры модели,
версию кода и наличие вашего анализа. Отдельная проверка в training-окружении
загружает веса в свежую модель с указанными `input_dim`/`n_classes`, восстанавливает
состояние SGD и выполняет шаг для проверки совместимости. Снимок должен включать ID, порядок колонок,
числовые признаки и метки всех строк, использованных в прогоне. Если код ещё не
закоммичен, укажите `working-tree (dirty)` и сохраните команду запуска; не
придумывайте commit SHA. Валидатор не может доказать происхождение данных,
обучение или обобщающую способность модели. Поэтому объясните источник признаков,
ошибки и ограничения. Универсального проходного порога accuracy нет.

## Подсказки по ступеням

- Сначала распечатайте формы и типы одного батча; проверьте `batch_size=3` на
  восьми строках. Какой размер у последнего батча?
- Перед вызовом `backward` сравните параметр с его копией; затем после `step`.
  В каком месте он действительно меняется? Что случится без `zero_grad`?
- На валидации сравните веса до/после. Затем проверьте модель с dropout в
  `train()` и `eval()` на одинаковом входе.
- Сначала сохраните checkpoint, испортите веса в памяти и загрузите обратно.
  Сравните логиты одного входа до сохранения и после загрузки.
- Для анализа ошибок начните с трёх известных логитов и ID; вручную вычислите
  ожидаемые классы и сравните с результатом функции.

`pytest` как health-проверка покажет незавершённые TODO как `xfail` и не требует
ученического отчёта. `python scripts/learn.py check lab-pytorch` — строгий зачёт: TODO, skip и
отсутствующий отчёт дают ненулевой код. Отдельно прогоните CPU-пример; он не
создаёт ученический отчёт. Завершение: все контрактные тесты проходят, отчёт
содержит реальные результаты и ваш анализ, вы можете объяснить каждый переход
тензора и почему вес не меняется во время валидации.

Вопросы для самопроверки: почему усреднение средних loss по батчам неверно при
неравных размерах? Чем `eval()` отличается от `no_grad()`? Почему checksum
checkpoint не делает безопасной загрузку произвольного pickle? Что поменяется,
если признаки при прогнозе расположить в другом порядке?
