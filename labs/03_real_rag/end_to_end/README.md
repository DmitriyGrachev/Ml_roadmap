# Dense retrieval → local generator → независимая оценка

ID: `rag-end-to-end-evaluation`. Это самостоятельное упражнение после
[основной RAG-лаборатории](../README.md),
[теории retrieval](../theory.md),
[локального генератора](../runtime.md) и
[Hugging Face](../../02_huggingface_models/README.md).
Нужны NumPy, формы тензоров, cosine similarity, dev/holdout и контракты Python.
Успех старых CLS/Qdrant-проверок сохраняет прежний смысл; новый ID требует новых
артефактов и реализации. Одна успешная цепочка API не доказывает качество ответов.

## Что именно вычисляет embedding

Выход encoder — тензор `H` формы `[N,T,D]`: число текстов, длина с padding,
размерность представления. Минимальный способ получить вектор предложения — взять
`H[:,0,:]`. Это исторический CLS baseline нашей лаборатории. У pretrained модели
архитектура первого токена сама по себе не обещает подходящую геометрию предложений.
Прежние отчёты поэтому сохраняют метку
`EXPERIMENTAL_CLS_BASELINE_NOT_MODEL_CARD_MEAN_POOLING`.

Здесь добавлен явный режим `pooling="masked_mean"`. Для текста `i` вычисляем
`u_i = sum_t(H_it * mask_it) / sum_t(mask_it)`, затем `v_i = u_i / ||u_i||₂`.
При включённых tokenizer масках CLS и SEP тоже входят в среднее. Padding не входит.
Сначала усредняем скрытые векторы, затем нормируем среднее: усреднение заранее
нормированных токенов задаёт другую геометрию. При нулевой маске или нулевой норме
вектора нет определённого cosine, поэтому нужен `ValueError`, а не придуманный
вектор из нулей. Проверяем размерности, бинарность маски и конечность значений.

Разобранный числовой пример: два валидных токена `[3,0]` и `[0,4]` дают среднее
`[1.5,2]`, его норма `2.5`, ответ `[0.6,0.8]`. Добавление padding `[900,-900]`
с маской `0` ничего не меняет. Усреднение всех трёх токенов сломало бы результат.
Сравнение с текстом, закодированным отдельно и внутри padded batch, ловит эту ошибку.
Float погрешность допустима; разные документы и запросы должны использовать одну
модель, ревизию, pooling, truncation и нормировку.

После L2-нормировки скалярное произведение равно cosine. Однако score `0.7` не
является вероятностью корректности ответа. Распределение зависит от корпуса,
языка, длины, embedding-модели и похожих, но неверных документов. Перенос порога
из игрушечного корпуса в рабочую систему требует новой калибровки на dev.
Мы сохраняем точную pinned identity MiniLM и запрещаем дополнительные loader-файлы;
названия каталога с весами недостаточно для воспроизводимости.

## Две независимые задачи измерения

Retriever получает вопрос и возвращает ранжированный список ID. Его разметка —
множество релевантных ID, допустимых для данного пользователя и момента времени.
`Recall@k = |retrieved ∩ relevant| / |relevant|`. `MRR` усредняет обратный ранг
первого релевантного фрагмента. Если relevant пусто, обе величины здесь `null`,
потому что делить на ноль или приписывать идеальную релевантность нельзя.
Отдельно сохраняем число таких вопросов и факт отказа системы. Средние считаем
с явными знаменателями и никогда молча не превращаем `null` в ноль.

Генератор получает только собранный контекст. Мы независимо проверяем:

- `correct`: нормализованный exact match ответа с допустимыми gold-ответами;
- `supported`: текст ответа встречается в каждом указанном supporting passage;
- `abstention_correct`: для неответимого вопроса статус `no_answer`, для ответимого
  статус `answer`; `provider_error` и `invalid_output` всегда проваливают эту проверку;
- факт и тип provider failure, задержки, конкретный prompt и использованные ID.

Это намеренно узкие автоматические проверки. Exact match может отвергнуть верный
парафраз, а substring может принять фразу, которую документ отрицает или цитирует.
Поэтому `human_entailment` всегда `REQUIRES_REVIEW`. В самостоятельной работе
прочитайте каждый ответ и каждый supporting passage, отметьте ложные положительные
и ложные отрицательные с объяснением. Для более свободного формата ответов заранее
определите ручную рубрику или другую проверку; нельзя выбирать её после просмотра
неудобных heldout результатов. Валидный citation ID сам по себе не означает,
что источник подтверждает утверждение.

Хороший retriever может найти `300 dpi`, а генератор написать `900 dpi` и сослаться
на верный ID: recall остаётся 1, correctness и support равны false. Плохой retriever
может пропустить требуемый текст, а модель угадать ответ из памяти: correctness
может оказаться true при неподтверждённом ответе. Поэтому один общий "RAG score"
без компонент скрывает причину ошибки. Сравните также результаты при фиксированном
контексте: это помогает отделить влияние retrieval от поведения генератора.

## Policy до обращения к модели

В `runtime.rank` доступ и актуальность проверяются **до top-k**. Иначе приватный
ближайший вектор вытеснит публичный, а фильтрация после top-k даст пустой результат
даже при доступном релевантном фрагменте. В реальной системе права приходят из
проверенной identity пользователя, а текущая ревизия — из авторитетного хранилища,
не из JSON запроса пользователя или текста документа. Наш синтетический эксперимент
передаёт доверенные `revoked_ids` и `stale_ids`; они моделируют текущее состояние.
Для production их нужно вычислять по текущим source metadata и проверять повторно
перед генерацией, особенно при очередях, кэше и параллельном изменении прав.

`needs_clarification` — маленькая явно ограниченная policy: вопрос про settings
без scanner/paper/dpi вызывает отказ и запрос уточнения на уровне продукта.
Это не универсальный классификатор неоднозначности. В независимом отчёте покажите
его ложные срабатывания и пропуски; добавьте другой неоднозначный запрос. Не
используйте `kind`, `should_abstain` или `expected_answers` для выбора ответа:
они являются оценочной разметкой и доступны только после предсказания.

Нужны пять типов сценариев в каждом split:

| Сценарий | Проверка | Типичная ошибка |
| --- | --- | --- |
| Answerable | Правильный ответ опирается на текущий доступный текст | Верная ссылка при неверном числе |
| Missing/noanswer | Корпус не содержит ответа, требуется отказ | Dense всегда возвращает ближайшего соседа |
| Ambiguous | Недостаточно уточнения объекта или области | Уверенное угадывание намерения |
| Stale | Старый snapshot не даёт права отвечать по устаревшему тексту | Смешение ревизий индекса и источника |
| ACL restricted | Нельзя передавать отозванный или staff-only текст провайдеру | Права проверили только после генерации |

Текст документов — недоверенные данные. Наша fixture содержит prompt injection;
provider prompt запрещает следовать ему, а транспорт не выдаёт инструменты.
Проверки ID и формы JSON полезны, но не доказывают семантическую устойчивость к
инъекциям. При ручном разборе обязательно включите этот failure mode.

## Dev и holdout

До первого запуска запишите гипотезу, варианты CLS/mean, набор значений k/порога,
метрику выбора, бюджет контекста и stopping rule. На dev разрешено анализировать
ошибки и менять параметры. В author runner порог выбирается из пяти значений
по dev answerability accuracy; ни gold-ответы, ни heldout метрики не управляют
ranker. Это ограниченный пример, который может выбирать неудовлетворительный порог.
`Config` замораживается перед обработкой heldout.

Holdout нужен для оценки выбранной процедуры. Повторный подбор после просмотра
ошибок превращает его в dev. Если изменили policy/порог/prompt после результата,
пометьте прежний holdout как использованный и соберите новый независимый набор.
Разделяйте по семействам намерений и источникам, когда возможно: дословные дубли
в dev и holdout дают оптимистичную оценку. Метаданные одного документа могут
отличаться в ACL/stale сценариях, поэтому одинаковый вопрос внутри одного split
иногда осмысленен; переносить его дословно в другой split нельзя.

На десяти вопросах проценты имеют большую неопределённость. Покажите числитель,
знаменатель, per-case таблицу и paired differences CLS/mean. Для CI разницы можно
сделать paired bootstrap по вопросам, сохраняя пары систем и группируя связанные
варианты одного намерения. Он отражает неопределённость фиксированных предсказаний,
а не обучение encoder заново. Укажите, что выборка синтетическая и мала. Не обещайте
обобщение на рабочий корпус или русский язык только по этим английским fixtures.

## Author пример и независимая задача

`runtime.py` — разбор автора, `test_author.py` проверяет его wiring/policy и настоящий
SSE-контракт существующего `LocalGenerator` через локальный HTTP fixture. Ни один
из этих тестов не доказывает качество pretrained encoder или живой LLM. Offline
пример можно просмотреть без сети и весов:

```bash
python -m labs.03_real_rag.end_to_end.demo
python -m pytest labs/03_real_rag/test_pooling.py labs/03_real_rag/end_to_end/test_author.py -q
```

В `starter.py` самостоятельно реализуйте `pool_tokens` и `answer_case` без вызова
`runtime.run_case`/`runtime.rank` как готового решения. Оставлены явные TODO.
Контракт `answer_case` такой же, как у author `run_case`: получите `[N,D]` документы,
`[D]` вопрос, `Config`, вызываемый generator; верните `case_id`, `split`, `kind`,
query/hash, retrieved IDs/scores, context IDs, отдельные retrieval/answer metrics,
answer/status/citations, generator_called, prompt/hash, stream и три задержки.
Для `LocalGenerator` сохраняйте `last_prompt` и `last_result` через `asdict`.
Вызов provider должен получать именно отобранные Chunk, а не весь корпус.

Сначала пройдите `test_starter.py`. Затем создайте собственный `my-cases.json`:
минимум 10 случаев, оба split, все пять типов в каждом; тексты вопросов должны
отличаться от author fixtures, включая heldout. Схему случая смотрите в
`runtime.teacher_cases()`: `case_id`, `split`, `kind`, `query`, `revoked_ids`,
`stale_ids`, `relevant_ids`, `expected_answers`, `should_abstain`. Проверьте gold
и доступ вручную до запуска. Более сильная работа содержит больше независимых
намерений, hard negatives, неоднозначности другого типа и несколько источников.
Учебный runner фиксирует исходный корпус; расширение корпуса — transfer-задача,
для которой понадобятся новые pinned corpus hashes и проверка разметки.

Для реального эксперимента явно подготовьте optional training environment и
проверенные локальные MiniLM-файлы по [инструкции HF](../../02_huggingface_models/README.md).
Ollama должен уже обслуживать точную cached модель из `local_generator.py`:
никаких автоматических pull, подмены модели или платных API здесь нет.
Прежний [runtime guide](../runtime.md) описывает установленную модель и ограничения.
Сохраните каталоги с результатами вне git. В Windows используйте `python` из
своего venv; Linux/WSL команды имеют ту же структуру.

```bash
python -m labs.03_real_rag.end_to_end.runtime --run-local --learner --model-dir /absolute/pinned-minilm --cases /absolute/my-cases.json --pooling cls --output /absolute/my-rag-cls
python -m labs.03_real_rag.end_to_end.runtime --run-local --learner --model-dir /absolute/pinned-minilm --cases /absolute/my-cases.json --pooling masked_mean --output /absolute/my-rag-mean
```

Без `--learner` запускается отдельный author runner; такой receipt не принимается
за самостоятельную работу. Флаг `--learner` заменяет только `answer_case`:
оба live-режима используют проверенную авторскую реализацию encoder/pooling.
Собственный `pool_tokens` ученика оценивается отдельно offline в `test_starter.py`;
live receipts CLS/mean не подтверждают его работу на реальных hidden states.
Без существующих assets/локального сервиса live команда
падает явно, сохраняя FAILED receipt. Default pytest ни сеть, ни модель не запускает.
Локальные маленькие случайные веса в optional pooling test проверяют вычисления,
но никогда не получают статус pretrained quality.

Скопируйте два `receipt.json` в новый каталог submission под именами `cls.json`
и `masked_mean.json`. Добавьте собственный `review.json`: `status` должен остаться
`REQUIRES_REVIEW`; поля `hypothesis`, `dev_selection`, `retrieval_vs_answers`,
`failure_analysis`, `uncertainty`, `transfer`, `human_support_review` содержат
содержательные объяснения (каждое не короче 40 символов). Шаблон с заполненными
выводами намеренно не поставляется. Низкое качество допустимо при честном анализе;
пропущенный эксперимент или набор fake ответов нельзя выдавать за живой прогон.

```bash
# Linux/WSL
ROADMAP_RAG_SUBMISSION=/absolute/submission python -m pytest labs/03_real_rag/end_to_end/test_starter.py labs/03_real_rag/end_to_end/test_evidence.py -q
# PowerShell
$env:ROADMAP_RAG_SUBMISSION = 'C:\work\submission'
python -m pytest labs/03_real_rag/end_to_end/test_starter.py labs/03_real_rag/end_to_end/test_evidence.py -q
```

Без submission evidence test будет xfail; strict catalog check не выдаёт credit.
При указанном, но неправильном каталоге будет обычная ошибка, которую нельзя
спрятать за xfail. Проверяющий читает оба receipts, сверяет identity, hashes,
полноту cases, dev-only tuning, измеренные задержки и пересчитывает метрики.
Хеши доказывают согласованность байтов, но не происхождение JSON: финальная защита
включает воспроизведение эксперимента преподавателем и проверку исходников ученика.
Отметка PASS runner означает техническое завершение, а не педагогический зачёт.

## Рубрика защиты и перенос

| Критерий | Слабое свидетельство | Сильное свидетельство |
| --- | --- | --- |
| Pooling | Формы совпали на одном тексте | Ручной расчёт, padding invariance, empty-mask policy, CLS/mean на тех же запросах |
| Retrieval | Один удачный top-1 | Recall/MRR по типам, null policy, hard negatives, права до top-k |
| Ответы | Все ответы содержат citation ID | Независимая correctness/support/abstention, ручной entailment разбор, ошибки провайдера отдельно |
| Split | Порог выбран по красивой таблице holdout | План до запуска, dev история выбора, frozen config, новый holdout после изменения |
| Воспроизводимость | Название модели и screenshot | Pinned files/revision, model digest до/после, corpus/query/prompt/config hashes, каждый case и latency |
| Вывод | "Mean лучше всегда" | Парное сравнение, знаменатели и ограничения, плохие результаты сохранены, понятный следующий эксперимент |

Transfer: представьте, что права меняются между retrieval и генерацией, один документ
обновляется во время очереди, а запрос "настройки" относится к нескольким устройствам.
Опишите и реализуйте повторную проверку текущих source revisions/access перед provider,
инвалидацию кэша и новый сценарий гонки без сети. Затем предложите новый heldout для
другого языка/домена и объясните, какие параметры придётся заново выбрать на dev.
Сильная защита показывает провал старой policy на новом случае и объясняет причину,
не подгоняя метрики задним числом.
