# Ошибка до публикации: кому принадлежит временный файл

## Зачем и что уже нужно знать

Представьте, что читатель открывает вчерашний файл, пока программа готовит
сегодняшний. Если писать прямо в destination, неудача посреди операции может
оставить обрезанный результат. Здесь разберём две разные границы: подготовку
содержимого и публикацию готового файла. Нужны
[функции](../03_functions/README.md) и
[границы значений](../05_data_modeling/README.md). Прежний `example.py` читает
summary и переводит неизвестный status в доменную ошибку; он остаётся прежним.

## Ситуация и прогноз

В `catalog.json` уже лежат байты `b"old catalog"`. Новые данные содержат Python
`set`, который стандартный JSON encoder не умеет кодировать. Предскажите:
может ли `json.dump` успеть записать часть текста до `TypeError`? Что будет со
старым файлом, если запись ведётся в отдельный draft и публикация ещё не началась?

Интуиция: сначала готовим черновик рядом с опубликованным объявлением, затем
одним действием меняем видимый файл. Но «одно действие для читателя» не означает
«данные переживут любое отключение питания». Публикация и долговечность — разные
обещания.

## Точность: фазы и владение

**Serialization** переводит Python-значения в формат хранения. Исключение
сериализации может случиться после частичной записи. **Replacement** меняет
destination на уже подготовленный файл; здесь отдельно возможен `OSError`.
`with` закрывает writer при обычном выходе и при исключении (**context manager**).
Это управление временем жизни ресурса, а не откат записанных байтов.

**Ownership** означает, что этот вызов создал конкретный draft и имеет право
его удалить. Имя вроде `keep.tmp` ничего не доказывает: нельзя убирать все
`*.tmp` в каталоге. Уникальное имя берётся у `NamedTemporaryFile`, не собирается
из пользовательского имени. `delete=False` оставляет путь после закрытия для
следующей фазы; ответственность за его судьбу теперь явная.

| Момент | Writer | Draft | Старый destination |
|---|---|---|---|
| До создания | отсутствует | отсутствует | старые байты |
| Подготовка | открыт | может быть частичным | старые байты |
| Выход из `with` | закрыт | готов либо подлежит cleanup | старые байты |
| Успешный replace | закрыт | имя потреблено заменой | новые байты |
| Ошибка до/при replace | закрыт | удаляем только свой путь | старые байты в наших сценариях |

На Windows особенно важно закрыть writer **до** replace: открытый файловый
handle может блокировать переименование/удаление. Временный файл создаётся в
родительском каталоге destination, чтобы не пересекать файловые системы.
Для обычного локального файла успешный `os.replace` даёт атомарную замену
видимого имени; необычные/сетевые файловые системы имеют свои ограничения.
Читатель, уже державший старый файл открытым, не обязан увидеть новые байты в
том же handle. Это не глобальная транзакция для всех участников.

## Разобранные демонстрации на разных артефактах

[walkthrough.py](walkthrough.py) содержит два узких примера:

1. `serialize_broken_catalog(directory)` пишет **фиксированный** проблемный
   каталог в draft. Set приводит к реальной ошибке JSON. Эта функция вообще
   не публикует `catalog.json`: мы наблюдаем только фазу сериализации.
2. `publish_notice(destination)` пишет **фиксированное** текстовое объявление
   `Library closes at 18:00.\n`, закрывает writer и заменяет цель. В ней нет
   JSON, произвольного payload или общего export API. Так можно наблюдать
   публикацию отдельно от кодирования данных.

`main` создаёт изолированный `TemporaryDirectory`: личные файлы не затрагиваются.
Для успеха используется обычный `notice.txt`. Для ошибки replace — непустой
каталог `occupied` с чужим `keep.txt`: файл не может заменить такой каталог.
Это настоящий отказ файловой системы, а не заранее напечатанная строка.

Из корня репозитория, с уже подготовленным окружением:

```powershell
uv run --no-sync python modules/01_python_core/06_exceptions_io/walkthrough.py
uv run --no-sync pytest modules/01_python_core/tests/test_r01_atomic_phases.py -q
```

Полный вывод:

```text
success: Library closes at 18:00.
serialization: TypeError; old=b'old catalog'
replacement: failed; unrelated=b'other owner'
drafts remaining: 0
```

Каждая строка читает реальное состояние. Вторая показывает байты старого
каталога после ошибки; третья — байты `keep.txt` внутри несовместимой цели.
Тип системной ошибки замены зависит от ОС, поэтому демонстрация ловит `OSError`
и печатает устойчивое описание фазы. Авторские тесты дополнительно моделируют
отказ replace **обычного существующего файла**, проверяя его старые байты.

До изменения кода предскажите результат одной замены в копии: направьте
`publish_notice(blocked)` в `publish_notice(notice)`. Теперь replace успешен;
строка `replacement: failed...` исчезнет, чужой `keep.txt` по-прежнему не затронут.
Это изменение цели, а не исправление JSON encoder.

## Как сохранить исходную ошибку

Ключевой путь ресурса: `draft = None` → созданное уникальное имя → writer внутри
`with` → закрытие → replace. `None` означает «этот вызов ещё не получил путь»;
если само создание не удалось, удалять нечего. Успешный replace потребляет имя
draft, поэтому отдельное удаление после успеха не требуется.

В обеих демонстрациях обработчик ловит `BaseException` только ради cleanup
созданного ресурса и сразу использует голый `raise`. Это сознательный узкий
смысл широкого перехвата: ошибка не превращается в успех, не заменяется новой
ошибкой и не подавляется. Обычная прикладная обработка в `main` ловит только
предсказанный `TypeError` или `OSError`. Не копируйте широкий перехват в места,
где ошибка просто игнорируется.

`cleanup_owned` вызывает `draft.unlink(missing_ok=True)`. Если unlink тоже
получил `OSError`, он добавляет **exception note** к исходной ошибке. Затем
вызывающий обработчик повторно поднимает исходный объект исключения.
Авторский тест сравнивает `caught.value is original`, а не только текст:
это проверяет, что первопричина сохранилась. Отдельный тест допускает отказ
удаления и проверяет note и оставшийся draft.

| Ошибка подготовки/replace | Удаление draft | Что получает caller |
|---|---|---|
| есть | успешно | исходный объект ошибки; draft отсутствует |
| есть | `OSError` | исходный объект + note; draft может остаться |
| нет, replace успешен | не нужно | успешное завершение, имя draft уже перемещено |

Типичная ошибка — голый `finally: draft.unlink()` без учёта сбоя cleanup:
новый `PermissionError` может заслонить исходный `TypeError`. Другая ошибка —
`except: return destination`, который выдаёт неудачную публикацию за успех.
Обещать безусловное удаление при отказе ОС нельзя. В нашем протоколе первичная
ошибка важнее; note оставляет информацию для ручной диагностики оставшегося пути.
Аварийное завершение процесса может вовсе не дать Python выполнить cleanup.

## Атомарная видимость и crash durability

**Visibility atomicity** здесь означает переход имени от старого файла к новому
без состояния «наполовину переписанный опубликованный файл» при успешной замене.
**Crash durability** — сохранение данных после сбоя питания/системы. Закрытие
handle и replace сами по себе не составляют универсальный протокол durability.
Буферы ОС, синхронизация файла и каталога, ОС и конкретная файловая система
имеют значение. Этот урок не реализует `fsync`-протокол и не обещает его.

Также здесь нет защиты от конкурирующих писателей, восстановления после сбоя
процесса, управления ACL или нескольких файлов в одной транзакции. Предполагаем
изолированную директорию и отсутствие стороннего изменения файлов между шагами.
Авторские проверки доказывают свойства именно контролируемых сценариев, а не
любого хранилища и любой аварии.

5. Что доказывает `caught.value is original`, чего не доказывает совпадение строки?
6. Что происходит, если cleanup тоже не имеет разрешения? Почему это не успех?
7. Чем переход видимого имени отличается от обещания пережить отключение питания?

## Перенос в практику

Самостоятельно нарисуйте временную линию для другого артефакта: CSV с двумя
строками, где преобразование второй строки падает. Не пишите готовый exporter:
отметьте момент возможной частичной записи, закрытия, допустимой замены и cleanup.
Добавьте случай, когда ошибка возникает ещё при создании draft. Это ручной прогноз.

Затем [атомарный JSON export — `python-json-export`](exercises/json_export/README.md).
В нём вы сами соединяете сериализацию и публикацию для **произвольного payload**
по указанному контракту. Учитель не предоставляет общего JSON exporter под новым
именем. Сначала сверьте требования к UTF-8, пути, возвращаемому значению и каждой
ошибке. Не меняйте существующие acceptance tests.

```powershell
uv run --no-sync pytest modules/01_python_core/06_exceptions_io/exercises/json_export -q -rx
```

`xfail` незаполненного стартера и успех демонстрации — не освоение упражнения.
Сравните наблюдаемые байты, список путей и идентичность ошибок, затем объясните
границы своего решения.

## Источники и остановка

Официальные ссылки на английском; локальный запуск проверен 2026-10-11 на
Python 3.12.14/Windows. Документация описывает механизмы и ограничения API;
она не является обещанием durability для произвольного хранилища.

- PSF, [os.replace](https://docs.python.org/3.12/library/os.html#os.replace): ограничения source/destination, разные файловые системы и успешная атомарная замена; остановитесь перед следующими API.
- PSF, [NamedTemporaryFile](https://docs.python.org/3.12/library/tempfile.html#tempfile.NamedTemporaryFile): прочитайте параметры удаления и замечания о Windows; остальные классы не обязательны.
- PSF, [json.dump](https://docs.python.org/3.12/library/json.html#json.dump): поддерживаемые типы и параметры сериализации; не пишите свой encoder в этом уроке.
- PSF, [BaseException.add_note](https://docs.python.org/3.12/library/exceptions.html#BaseException.add_note): как приложить дополнительную диагностику без подмены первопричины.
- PSF, [os.fsync](https://docs.python.org/3.12/library/os.html#os.fsync): только различие flush и синхронизации; полный протокол durability вне R01.
