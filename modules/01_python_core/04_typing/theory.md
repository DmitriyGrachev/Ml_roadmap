# Typing: обещание о форме значения

[Вход в урок](README.md) · [Запускаемый пример](example.py)

Это продолжение [Object Model](../01_object_model/README.md): имя связано с объектом,
и тип принадлежит объекту. Здесь мы добавляем *ожидание* о значениях, которое
можно проверить до запуска. Для чтения примеров пригодятся Collections и Functions;
знания о платёжных системах не нужны.

## Ситуация и прогноз

Сервис получает метки заявки и должен вернуть их без пробелов по краям,
в нижнем регистре, без дублей и по алфавиту. Перед чтением реализации
предскажите: примет ли функция объект класса, который не наследуется от
`LabelSource`, но предоставляет подходящее свойство `labels`? Что будет,
если у объекта есть только `name`?

Минимум синтаксиса: `def f(x: T) -> R` объявляет функцию, где `x: T` — аннотация
параметра, а `-> R` — аннотация результата. Двоеточие с отступом начинает тело.
`obj.labels` читает атрибут объекта. `@property` над методом позволяет читать
его результат как атрибут, без скобок. В нашем примере это читаемый атрибут;
отсутствие setter не даёт присвоить новое значение через `ticket.labels = ...`.
`tuple[str, ...]` означает кортеж из произвольного числа строк; многоточие здесь
часть записи типа, а не команда пропустить упражнение. Кортеж не имеет `append`.

## Интуиция: ожидание отдельно от значения

Аннотация похожа на подпись у входа функции: «сюда передают объект с такими
возможностями». Подпись позволяет заранее заметить несоответствие, если запустить
статический анализатор (static type checker), например mypy. Она не ставит
охранника у входа во время выполнения (runtime). Когда функция реально обращается
к `source.labels`, Python ищет этот атрибут у переданного объекта; неподходящий
объект может вызвать обычную ошибку выполнения. Аннотации сами не заменяют
проверку недоверенных данных.

В Java тип переменной участвует в обязательной проверке компиляции. В Python
аннотации обычно проверяет отдельный инструмент; сам интерпретатор их не
использует для принятия решения «пускать ли значение в функцию».

## Точные записи типов

| Запись | Смысл для статической проверки | Граница |
| --- | --- | --- |
| `list[str]` | изменяемый список строк (generic collection) | это не проверка содержимого при запуске |
| <code>str &#124; None</code> | строка **или** отсутствие значения (union/optional) | перед строковой операцией нужно сузить тип (narrowing) |
| `Literal["ready", "failed"]` | только эти конкретные строковые значения (literal type) | не создаёт runtime-валидатор |
| `type Labels = tuple[str, ...]` | псевдоним типа (type alias), равный указанной форме | не создаёт новый класс |
| `Callable[[str], int]` | вызываемый объект (callable): один `str` на входе, `int` на выходе | не описывает все сложные сигнатуры |
| `Protocol` | набор требуемых членов (structural protocol) | оценивается по форме, а не по наследованию |

`None` — отдельный объект отсутствия значения; пустая строка `""` остаётся
строкой. Сужение типа означает, что после явной проверки ветка больше не
содержит `None`. `Literal` нужно импортировать из `typing`, `Callable` — из
`collections.abc`, а `Protocol` — из `typing`. `type` для псевдонима доступен
начиная с Python 3.12, который требуется этим проектом.

Прогноз № 2: какой результат даст следующий вызов и почему `.strip()` безопасен
только после проверки?

```pycon
>>> def clean(value: str | None) -> str:
...     if value is None:
...         return "missing"
...     return value.strip()
>>> clean(None), clean("  urgent  ")
('missing', 'urgent')
```

Сначала `None` приводит к раннему возврату. В оставшейся ветке `value` — строка;
без проверки вызов `None.strip()` упал бы при запуске. Аннотация не вставляет
проверку за нас.

Псевдоним полезен, когда длинная форма повторяется, но смысл остаётся тем же.
`Callable` описывает форму функции, переданной как значение:

```pycon
>>> from collections.abc import Callable
>>> type Labels = tuple[str, ...]
>>> def count(label: str) -> int:
...     return len(label)
>>> measure: Callable[[str], int] = count
>>> labels: Labels = ("billing", "urgent")
>>> tuple(measure(label) for label in labels)
(7, 6)
```

Здесь `Labels` — другое имя для `tuple[str, ...]`, а не новый вид кортежа.
Вызов `measure(label)` выполняет обычную функцию `count`. Если она была бы
аннотирована как возвращающая `str`, статический анализатор отметил бы
несовместимость с `Callable[[str], int]`.

`Literal` сообщает допустимые значения статически:

```pycon
>>> from typing import Literal
>>> def is_ready(status: Literal["ready", "failed"]) -> bool:
...     return status == "ready"
>>> is_ready("ready"), is_ready("failed")
(True, False)
```

Значение `"pending"` противоречило бы контракту, хотя обычный вызов Python
не получил бы автоматический отказ. Если внешние данные обязаны иметь только
два статуса, проверьте их отдельно во время выполнения.

## Разбор неизменённого примера

Откройте [example.py](example.py). `class LabelSource(Protocol)` объявляет
ожидаемую форму: читаемое свойство `labels` возвращает `tuple[str, ...]`.
Тело свойства в протоколе — `...`: это описание контракта, а не реализация
нормализации. `SupportTicket` хранит аргументы `*labels: str` в `_labels`;
звёздочка собирает переданные строки в кортеж. Его `@property labels`
возвращает этот кортеж. Класс не наследуется от `LabelSource`.

Трассировка вызова из `main()`:

| Шаг | Значение |
| --- | --- |
| Создание | `SupportTicket(" Billing ", "urgent", "billing")` хранит `(" Billing ", "urgent", "billing")` |
| Фильтр | `if label.strip()` оставляет все три строки; пустые или состоящие лишь из пробелов были бы пропущены |
| Преобразование | `strip().lower()` даёт `"billing"`, `"urgent"`, `"billing"` |
| Множество | `{...}` убирает повтор `"billing"`; порядок множества не служит порядком вывода |
| Сортировка | `sorted(...)` даёт `['billing', 'urgent']` |
| Возврат | `tuple(...)` даёт `('billing', 'urgent')` |
| Печать | `", ".join(...)` даёт строку `billing, urgent` |

Запуск из корня репозитория:

```powershell
uv run --offline --no-sync python modules/01_python_core/04_typing/example.py
```

Полный ожидаемый вывод:

```text
billing, urgent
```

В строке с comprehension `{label.strip().lower() for label in source.labels
if label.strip()}` проверка идёт для каждого исходного элемента, затем для
оставшихся строится нормализованное значение. `sorted` нужен, чтобы результат
не зависел от порядка обхода множества. Функция не меняет кортеж у заявки.

Если заменить только `"urgent"` в конструкторе на `"   "`, эта метка
отсеется проверкой; вывод станет `billing`. Сначала предскажите это сами,
затем проверьте в отдельном вызове без правки файла примера.

Типичная ошибка — считать, что `source: LabelSource` автоматически проверяет
наличие `labels` при входе. На самом деле ошибка возникнет лишь при попытке
прочитать отсутствующий атрибут. Другая ошибка — ожидать от множества
алфавитного порядка без `sorted`.

## Форма объекта и Java interface

`Protocol` в Python выражает структурную совместимость (structural typing).
Для статической проверки у объекта должны быть члены нужной формы. В Java
обычный `implements` явно называет интерфейс; здесь совместимый класс может
быть создан независимо. Сравните три формы:

| Кандидат | Есть читаемое `labels: tuple[str, ...]`? | Для `LabelSource` |
| --- | --- | --- |
| `SupportTicket` из примера | да, через `@property` | совместим |
| Независимый `BatchLabels` ниже | да, через своё `@property` | совместим |
| Воображаемый `NamedOnly` с одним `name: str` | нет | несовместим при статической проверке; при чтении `labels` будет `AttributeError` |

Прогноз № 3: нужен ли `BatchLabels` явный `implements`? Проверьте результат:

```pycon
>>> from runpy import run_path
>>> namespace = run_path("modules/01_python_core/04_typing/example.py")
>>> normalize_labels = namespace["normalize_labels"]
>>> class BatchLabels:
...     @property
...     def labels(self) -> tuple[str, ...]:
...         return ("  Review ", "review", "")
>>> normalize_labels(BatchLabels())
('review',)
```

Этот вызов показывает реальное поведение. Сам запуск не доказывает, что
статический анализатор одобрит *любую* реализацию: ему важны аннотации и
совместимость члена, а не только наличие атрибута с тем же именем. Кроме того,
наличие `labels` не гарантирует, что внешние данные действительно являются
строками; при недоверенном вводе нужна отдельная проверка данных.

У `LabelSource` именно свойство без setter. Оно сообщает читателю, что
нормализатор только читает метки. В реализации `SupportTicket` кортеж не
допускает изменения элементов. Это не универсальная гарантия «весь объект
навсегда неизменяем»: здесь речь о конкретной границе чтения.

## Ответы после попытки

1. Аннотация сама не остановит возврат `7`; статический анализатор отметит несовпадение `int` и `str`.
2. Обычный список примет `3`; анализатор отметит нарушение `list[str]`.
3. Ранний `return` исключил `None` из оставшейся ветки. Без него `strip` недопустим для одной из альтернатив и может вызвать `AttributeError`.
4. Контракт допускает `"ready"` и `"failed"`; runtime-проверки он не добавляет.
5. Нужны один аргумент `str` и результат `int`; функция с результатом `str` не подходит.
6. Независимый класс с читаемым свойством нужной формы подходит структурно; `name` вместо `labels` не подходит. Проверка статическая, если вы запускаете анализатор.
7. Функция вернёт `('billing', 'urgent')`, а `main()` напечатает `billing, urgent`: пробелы сняты, регистр снижен, дубль убран, результат отсортирован.
