# Контракт, проверка и первая неверная предпосылка

## Зачем и что уже нужно знать

Тест помогает только тогда, когда его ожидание выведено из договора, а не из
текущего кода. Здесь полностью разберём маленькую функцию, затем перенесём
способ рассуждения на **другой** обработчик документов. Нужны
[функции](../03_functions/README.md),
[типы и runtime-границы](../04_typing/README.md) и
[исключения](../06_exceptions_io/README.md).

Прежний `example.py` показывает параметризацию Unicode-правила валютного кода.
Он не проверяет ASCII и не решает контракт `python-payment-model`:
`isalpha()`/`isupper()` работают с Unicode. Это важное ограничение примера,
а не причина подменить его контракт. Новый [walkthrough.py](walkthrough.py)
учит проектировать тесты с явно выписанными границами.

## Ситуация и прогноз: что означает «короткий preview»?

Договор `preview(text, limit)`:

- `text` — строка; `limit` — целое число, кроме `bool`, не меньше нуля.
- Вернуть первые **не более limit символов Python-строки**, без заполнения,
  многоточия, удаления пробелов и изменения регистра.
- Пустая строка допустима; нулевой limit даёт пустую строку.
- Недопустимые аргументы дают `ValueError`, называющий `text` или `limit`.

Это число code points строки, а не экранных колонок, байтов UTF-8 или визуальных
графем. Не добавляйте такую функциональность, которой нет в договоре.
Предскажите `preview("atlas", 0)`, `preview("", 4)` и `preview("atlas", 6)`.
В чём разница между пустым **валидным** входом и нестроковым `None`?

Интуиция: проверка — маленький эксперимент с заранее записанным результатом.
Она не доказывает всё о программе; набор случаев проверяет выбранные риски.
**Contract** — обещание границы, **test case** — конкретный вход и проверяемое
ожидание, **assertion** — утверждение о наблюдаемом результате.

## От договора к cases, а не от реализации к её копии

| Категория | Вход | Ожидание | Какое нарушение ловит |
|---|---|---|---|
| Ordinary | `"atlas", 3` | `"atl"` | неверное обрезание |
| Empty | `"", 4` | `""` | предположение о первом символе |
| Boundary: ноль | `"atlas", 0` | `""` | off-by-one в нижней границе |
| Boundary: длина | `"atlas", 5` | `"atlas"` | лишнее удаление последнего символа |
| Boundary: больше длины | `"atlas", 6` | `"atlas"` | заполнение/ошибка за пределом строки |
| Invalid | `"atlas", -1` | `ValueError`, поле limit | пропущенная проверка диапазона |
| Invalid type | `"atlas", True` или `1.5` | `ValueError`, поле limit | принятие флага/дроби |
| Invalid text | `None, 3` | `ValueError`, поле text | случайный TypeError вместо контракта |

Ожидание `"atl"` написано руками из условия «первые три символа».
`assert preview(text, limit) == preview(text, limit)` ничего не проверяет:
та же ошибка воспроизводится с обеих сторон. Не вычисляйте expected собственной
копией алгоритма с теми же ветками. Значение `len(result) <= limit` полезно,
но недостаточно: всегда пустой результат его тоже удовлетворяет.

**Parametrization** запускает одну проверку на нескольких независимых случаях.
Это не цикл, проглатывающий первую ошибку, и не разрешение смешать разные
контракты в одну нечитаемую таблицу. В walkthrough положительные случаи дают
пять отдельных pytest items:

```python
@pytest.mark.parametrize(
    ("text", "limit", "expected"),
    [
        ("atlas", 3, "atl"),
        ("", 4, ""),
        ("atlas", 0, ""),
        ("atlas", 5, "atlas"),
        ("atlas", 6, "atlas"),
    ],
)
def test_preview_examples(text: str, limit: int, expected: str) -> None:
    assert preview(text, limit) == expected
```

Отдельная проверка ошибки имеет узкий блок:

```python
with pytest.raises(ValueError, match="limit"):
    preview("atlas", -1)
```

**pytest.raises** провалит тест, если исключения нет или его тип не подходит.
`match` — регулярное выражение по сообщению; здесь достаточно имени нарушенного
поля, а не полного текста. Не помещайте в этот блок подготовку файлов, вызовы
помощников и проверку результата: их случайная ошибка может выдать ложный PASS.
Неверные runtime-типы в teacher tests подаются намеренно; локальные
`type: ignore[arg-type]` поясняют это статическому анализатору, а не выключают
runtime-валидацию.

Прогноз перед запуском: если заменить `text[:limit]` на `text[:limit + 1]`,
какие строки таблицы должны стать красными? Если убрать только проверку
`limit < 0`, отрицательный slice вернёт строку, а тест `raises` обнаружит нарушение.

## Полная реализация учителя и запуск

После тестового RED минимальная реализация:

```python
def preview(text: str, limit: int) -> str:
    if not isinstance(text, str):
        raise ValueError("text must be a string")
    if type(limit) is not int or limit < 0:
        raise ValueError("limit must be a nonnegative integer, not bool")
    return text[:limit]
```

Python slice уже обрабатывает пустоту и верхнюю границу. Отдельный доступ
`text[0]` не нужен. Это **usable implementation** учителя; ниже будет отдельный
намеренно сломанный образец.

Из корня, с уже подготовленным окружением:

```powershell
uv run --no-sync python modules/01_python_core/09_testing/walkthrough.py
uv run --no-sync pytest modules/01_python_core/09_testing/walkthrough.py -q
uv run --no-sync pytest modules/01_python_core/tests/test_r01_test_design.py -q
```

Первая команда исполняет `main`, две следующие запускают тесты. Явный путь
к `walkthrough.py` нужен, потому что обычный автопоиск ищет `test_*.py`.
В нём девять teacher cases: пять возвратов, три недопустимых limit и один
нестроковый text. Их успех показывает работу демонстрации, не освоение учеником.

Полный вывод `main`:

```text
preview('atlas', 3) = 'atl'
preview('', 4) = ''
preview('atlas', 0) = ''
paragraphs: ('red blue', 'green\nleaf')
word counts: (2, 2)
```

## Разобрать traceback до первой неверной предпосылки

[debugging/empty_preview/broken.py](debugging/empty_preview/broken.py) содержит
намеренный дефект и не импортируется usable реализацией. В нём цепочка вызовов
`main → inspect_document → broken_preview`; последняя функция делает
`text[0] + text[1:limit]`. Предскажите поведение на пустой строке до запуска.

```powershell
uv run --no-sync python modules/01_python_core/09_testing/debugging/empty_preview/broken.py
```

Полный вывод (команда намеренно возвращает **exit code 1**):

```text
Actual traceback frames (outermost first):
main: inspect_document("")
inspect_document: return broken_preview(text, 4)
broken_preview: return text[0] + text[1:limit]
IndexError: string index out of range
```

Это реальные frames из `traceback.extract_tb(error.__traceback__)`, с именами
функций и строками исходника. Машинные абсолютные пути/номера строк опущены
ради одинакового вывода; стек не сочинён вручную. Обработчик в main печатает
его для урока и сохраняет неуспешный exit code. В обычном необработанном
traceback Python также показывает файл и номер строки каждого frame.

| Frame | Что уже известно | Какая ответственность |
|---|---|---|
| `main` | передаёт `""` | воспроизвести разрешённую пустоту |
| `inspect_document` | передаёт text дальше с limit=4 | показать промежуточный вызов |
| `broken_preview` | `len(text) == 0` | ошибочно требует элемент с индексом 0 |

Читайте тип и сообщение внизу, затем последний frame, затем поднимайтесь к
caller, чтобы восстановить вход. Первая нарушенная предпосылка здесь —
«у строки есть первый символ», хотя контракт допускает пустоту. Перехватить
`IndexError` в caller и вернуть произвольный текст — не объяснение и не
доказательство исправления. Сначала зафиксируйте контрактный тест пустого входа;
правильная slice-реализация выше проходит его без отдельного `try`.

Измените в копии только вызов на `inspect_document("atlas")`: ошибка исчезнет,
но дефект не исправлен, просто вход его не проявляет. Ещё один прогноз:
`broken_preview("atlas", 0)` вернёт `"a"`, нарушая договор **без traceback**.
Поэтому отладка исключений не заменяет тесты результатов. Не объявляйте
expected failure или исчезновение traceback признаком освоения.

Для самостоятельного воспроизведения другого механизма используйте
[`python-debug-mutable-defaults`](../03_functions/debugging/mutable_defaults/README.md):
там состояние протекает между вызовами и ошибка обнаруживается assertion,
а не обязательно исключением внутри функции.

```powershell
uv run --no-sync pytest modules/01_python_core/03_functions/debugging/mutable_defaults -q --runxfail
```

Этот существующий стартер намеренно сломан; ожидаемый RED до вашей правки —
диагностическая точка, а не выполненное задание.

## Полная декомпозиция учителя: другая задача

`paragraph_word_counts` считает слова по абзацам, не извлекает заголовки.
Контракт: строковый вход; разделитель абзацев **ровно `\n\n`**; внешние пробелы
обрезаются, пустые chunks пропускаются. Внутри абзаца `split()` разделяет слова
по whitespace. Порядок абзацев сохраняется, выход — tuple чисел. Это простая
текстовая модель, не полноценный Markdown parser или языковой tokenizer.

Учитель разделяет причины изменения: `paragraphs` решает границы абзацев,
`count_words` — правило слов, `paragraph_word_counts` связывает их. Временное
состояние принадлежит одному вызову; нет экземпляра с reset/clear и общего списка.

| Этап для `"red blue\n\ngreen\nleaf\n\n  "` | Полученное значение |
|---|---|
| split по `\n\n` | `["red blue", "green\nleaf", "  "]` |
| strip и удаление пустых | `("red blue", "green\nleaf")` |
| split слов и len | `(2, 2)` |

Весь код композиции:

```python
def paragraphs(text: str) -> tuple[str, ...]:
    return tuple(chunk.strip() for chunk in text.split("\n\n") if chunk.strip())


def count_words(paragraph: str) -> int:
    return len(paragraph.split())


def paragraph_word_counts(text: str) -> tuple[int, ...]:
    return tuple(count_words(paragraph) for paragraph in paragraphs(text))
```

Авторская проверка использует буквальное `(2, 2)`, затем вызывает ту же функцию
с `"one"` и `""`, получая `(1,)` и `()`. Повторные вызовы не разделяют состояние.
Не следует нарезать каждую строку на функцию ради количества функций:
здесь границы отражают два отдельно меняющихся правила. При смене разделителя
правило слов не должно случайно поменяться.

Связь с уже существующим
[`python-review-stateful-report`](../03_functions/code_review/stateful_report/README.md):
там поведение уже корректно и защищено **characterization tests**. Цель —
убрать ненужное состояние экземпляра, сохранив порядок, суммы и публичный API.
Зелёные тесты до рефакторинга отличаются от RED при отсутствующей функции.

```powershell
uv run --no-sync pytest modules/01_python_core/03_functions/code_review/stateful_report -q
```

## Проверка понимания

1. Какие два теста нужны, чтобы отличить всегда пустой preview от корректного?
2. Почему предел 0 и пустой text — отдельные случаи одного контракта?
3. Почему expected, вычисленный вызовом функции под тестом, не является доказательством?
4. Где должен находиться вызов внутри `pytest.raises`, и что он проверяет при отсутствии ошибки?
5. Как из последнего frame восстановить первую неверную предпосылку, а не просто место падения?
6. Что меняется в декомпозиции при смене границ абзацев, а что должно сохраниться?
7. Почему `no tests ran`, ожидаемый xfail и GREEN учительского файла не доказывают вашу самостоятельную работу?

## Источники и остановка

Официальные материалы на английском. Локальные команды проверены 2026-10-11,
Python 3.12.14. Для тестов важен контракт конкретной функции; документация
объясняет инструменты проверки и чтения стека.

- pytest maintainers, [assertions and expected exceptions](https://docs.pytest.org/en/stable/how-to/assert.html): обычный assert и `pytest.raises`; остановитесь до расширения вывода assertion.
- pytest maintainers, [parametrizing test functions](https://docs.pytest.org/en/stable/how-to/parametrize.html#pytest-mark-parametrize): прочитайте первый пример и отдельные test items, без динамического generate_tests.
- PSF, [traceback.extract_tb](https://docs.python.org/3.12/library/traceback.html#traceback.extract_tb): откуда берутся реальные frames; код собственного debugger не нужен.
- PSF, [errors and exceptions](https://docs.python.org/3.12/tutorial/errors.html): распознайте структуру traceback и обработчик; остановитесь до создания пользовательских исключений.
- PSF, [mutable default arguments](https://docs.python.org/3.12/tutorial/controlflow.html#default-argument-values): разберитесь с единственным вычислением default и вернитесь к существующей debugging-практике.
