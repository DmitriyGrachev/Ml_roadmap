# Значение, которое нельзя создать неверным

## Зачем и что уже нужно знать

Если две границы страницы передаются отдельными числами, каждый вызывающий код
должен заново помнить правило их порядка. Небольшой **value object** (объект-значение)
собирает данные и правило в одном месте. Здесь это интервал страниц, а не платёж.
После урока вы сможете объяснить, почему успешное создание объекта обещает
определённые свойства, и где это обещание заканчивается.

Нужны [объекты и ссылки](../01_object_model/README.md),
[функции](../03_functions/README.md) и
[аннотации типов](../04_typing/README.md). Сначала запустите прежний
`example.py`: `LedgerEntry` хранит данные, но не проверяет их. Новый разбор
дополняет его, не меняя поведение.

## Ситуация и первый прогноз

В просмотрщике страницы нумеруются с нуля. `PageSpan(2, 5)` означает страницы
2, 3 и 4: правая граница исключена, как в Python slice `pages[2:5]`.
До запуска предскажите длины `PageSpan(2, 5)` и `PageSpan(5, 5)`.
Должен ли `PageSpan(5, 2)` вообще вернуться вызывающему коду?

Интуиция: объект — маленький договор. Конструктор либо отдаёт значение, которому
можно доверять в рамках договора, либо сообщает о нарушении. Это похоже на
контроль у входа, но не на защитный сейф: низкоуровневый обход возможен.

| Вызов | Проверка | Результат |
|---|---|---|
| `PageSpan(2, 5)` | `0 <= 2 <= 5` | страницы 2, 3, 4; длина 3 |
| `PageSpan(5, 5)` | `0 <= 5 <= 5` | пустой интервал; длина 0 |
| `PageSpan(5, 2)` | порядок нарушен | `ValueError`, объект не возвращён |

## Точный механизм конструктора

`@dataclass` генерирует обычный `__init__` по полям. При вызове класса Python
создаёт экземпляр и инициализирует его; сгенерированный `__init__` присваивает
`start`, `stop`, затем вызывает ваш `__post_init__`. **Constructor validation** —
проверка в этом пути создания, а не особый режим системы типов.

**Invariant** (инвариант) — условие, истинное для каждого допустимого состояния.
Здесь обе границы имеют тип именно `int`, и `0 <= start <= stop`. Пустой интервал
допустим. `bool` исключён сознательно: `isinstance(True, int)` истинно, но флаг
не является номером страницы в этом контракте. Аннотация `start: int` сама
по себе не отклонит `"2"`, `2.5` или `True` во время выполнения (**runtime**).
Статический анализатор помогает до запуска, а проверка защищает реальную границу.

Ключевая часть [walkthrough.py](walkthrough.py):

```python
@dataclass(frozen=True)
class PageSpan:
    start: int
    stop: int

    def __post_init__(self) -> None:
        if type(self.start) is not int or type(self.stop) is not int:
            raise ValueError("endpoints must be integers, not bool")
        if self.start < 0 or self.stop < self.start:
            raise ValueError("endpoints require 0 <= start <= stop")

    @property
    def length(self) -> int:
        return self.stop - self.start
```

`@property` даёт чтение `span.length` без `()`. Длина вычисляется из границ:
отдельное хранимое поле могло бы рассогласоваться с ними. Dataclass также
сравнивает значения полей: два отдельно созданных `PageSpan(2, 5)` равны через
`==`, хотя это не один объект через `is`. Сходство с Java record полезно для
равенства по данным, но генерация методов и runtime-проверки в Python имеют
свои правила; аннотации не становятся проверками конструктора.

## Две отдельные пробы: Decimal и ASCII

**Decimal** хранит десятичные значения; конструирование из строки `"0.1"`
избегает предварительного двоичного округления `float`. Но этот тип включает
нечисла и бесконечности. Нельзя считать «имеет тип Decimal» равнозначным
«конечное измерение». Прогноз: что произойдёт, если сразу выполнить
`Decimal("NaN") < 0`? При стандартном decimal context возникнет
`decimal.InvalidOperation`, а не выбранный нами `ValueError`.

В `finite_sign` сначала проверяются тип и `is_finite()`, затем выполняется
сравнение. `or` вычисляется слева направо с **short-circuit**: для не-Decimal
метод `is_finite()` не вызывается. Это также отклоняет signaling NaN до сравнения.

| Измерение | `is_finite()` | Возвращаемый знак |
|---|---|---|
| `Decimal("-2.5")` | `True` | `-1` |
| `Decimal("0")` | `True` | `0` |
| `Decimal("2.5")` | `True` | `1` |
| `Decimal("NaN")`, `Decimal("Infinity")` | `False` | `ValueError` до сравнения |

`is_ascii_digits` проверяет совсем другой контракт: строка состоит из
непустого набора десятичных ASCII-цифр. У `"٤٢".isdecimal()` результат `True`:
это арабско-индийские цифры Unicode. `isascii()` отделяет ограниченный алфавит
ASCII от более широкого **Unicode character predicate**. Пустая строка ASCII,
но её `isdecimal()` ложно. Поэтому результат пробы для неё тоже `False`.

Та же ловушка встречается у `isalpha()` и `isupper()`: они не означают ASCII.
Прежний [пример Testing](../09_testing/example.py) показывает маленькое Unicode
правило, а не полный контракт валюты. Прежде чем переносить его в упражнение,
сверяйте алфавит и остальные требования. Не исправляйте учебный пример под
другой контракт молча.

## Типичная ошибка и пределы frozen

Ошибка: добавить только аннотации и `frozen=True`, ожидая автоматической
валидации и глубокой неизменяемости (**deep immutability**). `frozen` запрещает
обычное присваивание полей после создания (`FrozenInstanceError`), но не делает
вложенные объекты неизменяемыми. Например, у frozen dataclass с полем
`notes: list[str]` вызов `obj.notes.append("new")` меняет сам список, не поле-ссылку.
Если нужны неизменяемые заметки, рассмотрите tuple и неизменяемые элементы.

У `PageSpan` поля — неизменяемые числа, поэтому такого вложенного списка нет.
Тем не менее `object.__setattr__`, ручное выделение через `object.__new__` и
другие специальные пути способны обойти обычный договор. `frozen` — средство
моделирования, не граница безопасности. Не показывайте такой обход как
нормальный способ обновления; создавайте новое корректное значение.

2. Когда `__post_init__` видит значения полей? Что получит вызывающий код при ошибке?
3. Почему `start: int` и `isinstance(start, int)` — разные проверки, и где здесь `bool`?
4. Зачем проверять конечность Decimal до порядка? Чем `NaN` отличается от нуля?
5. Почему `"٤٢".isdecimal()` не доказывает допустимость ASCII-номера?
6. Как nested list нарушает ожидание глубокой неизменяемости frozen объекта?

## Источники и остановка

Официальные ссылки, английский; целевая среда Python 3.12. Проверка авторского
запуска: 2026-10-11, Python 3.12.14. Источники относятся к механизмам языка;
доменные правила заданы отдельно в договоре.

- Python Software Foundation, [dataclasses: post-init processing](https://docs.python.org/3.12/library/dataclasses.html#post-init-processing): прочитайте порядок init/post-init и остановитесь до наследования dataclass.
- PSF, [dataclasses: frozen instances](https://docs.python.org/3.12/library/dataclasses.html#frozen-instances): границы эмуляции неизменяемости, без низкоуровневых обходов в практике.
- PSF, [Decimal.is_finite](https://docs.python.org/3.12/library/decimal.html#decimal.Decimal.is_finite): сравните с `is_nan` и `is_infinite`; весь decimal context сейчас не нужен.
- PSF, [str.isascii](https://docs.python.org/3.12/library/stdtypes.html#str.isascii) и [str.isdecimal](https://docs.python.org/3.12/library/stdtypes.html#str.isdecimal): прочитайте определения и Unicode-пример, остановитесь до остальных строковых методов.

Эти ссылки объясняют механизм языка; выбранные доменные ограничения задаёт
контракт упражнения, а не документация Python.
