# Пакет как проверяемая единица доставки

Предпосылки: Python modules/imports, пути, JSON, тесты, virtualenv. Java-разработчику
удобно сравнить wheel с поставляемым артефактом, а `pyproject.toml` — с описанием
сборки и зависимостей. Сравнение ограничено: Python импортирует модули по путям
интерпретатора, поэтому случайно успешный запуск из каталога проекта особенно
легко принять за корректную поставку.

## Исходники, distribution и import package

`parcel-features` — имя distribution в метаданных и у установщика;
`parcel_features` — имя import package. Дефис допустим в первом и не является
символом Python-идентификатора во втором. `src/parcel_features` отделяет исходники
пакета от текущего каталога. Папка с тестами, README и build runner не должна
случайно оказаться частью runtime API. В примере backend `uv_build` выбирает
пакет по нормализованному имени проекта. У корневого roadmap другой module-name;
каждый вложенный `pyproject.toml` описывает отдельную сборку.

`[build-system]` указывает backend и требования **сборки**. `[project].dependencies`
описывает зависимости **установленного пакета**. Здесь runtime-зависимостей нет:
достаточно стандартной библиотеки. Указать backend в dependencies не заменяет
build-system и без необходимости увеличивает среду сервиса. `uv.lock` корневого
проекта фиксирует рабочие инструменты, но не подменяет метаданные отдельного wheel.

Обычная изолированная сборка может скачать backend в отдельное окружение. Поэтому
наш офлайн-тест напрямую вызывает PEP 517 hook установленного `uv_build` и добавляет
каталог его окружения в `PATH`: backend находит executable `uv-build` именно там.
Мы не подменяем backend ручным ZIP-файлом. Установите dev-зависимости заранее;
внутри проверки нет разрешения или скачивания зависимостей.

## Почему editable install недостаточно

Editable install полезен при разработке, но часто продолжает читать исходники.
Тогда удалённый из wheel файл, неправильная сборочная конфигурация или импорт
соседнего учебного модуля остаются незаметными. Проверка доставки должна:
собрать `.whl`; создать новый venv без system-site-packages; установить только
этот wheel; перейти в другой каталог; запустить другой Python без `PYTHONPATH`.
`python -I` включает изоляцию путей, в частности не добавляет текущий каталог и
игнорирует переменные `PYTHON*`. Это полезная проверка честности импорта, а не
песочница для исполнения недоверенного кода.

`venv` создаётся с `with_pip=True`: `ensurepip` использует комплект интерпретатора,
а не сеть. Установка выполняется с `--no-index --no-deps --no-cache-dir` и локальным
wheel. `--no-deps` здесь честен только потому, что dependencies пусты. Для реального
пакета с зависимостями сначала готовят wheelhouse всех транзитивных зависимостей,
проверяют совместимость Python/платформы, затем устанавливают из него без индекса.
Нельзя переносить venv как универсальный дистрибутив между Windows и Linux.

Путь `venv/bin/python` нельзя бездумно превращать через `resolve()` в путь
системного интерпретатора: на POSIX это может быть symlink, и вызов по разрешённому
пути потеряет venv. В Windows используется `Scripts/python.exe`. Сам `work_dir`
можно сделать абсолютным, сохранив имя executable внутри окружения.

## Одна трансформация для train и serve

Авторский контракт: вход содержит `weight_grams` — конечное неотрицательное число
(не `bool`) и `destination` — строку. Возвращаем ровно два float:
`[weight_grams / 1000, len(normalized_destination)]`. Нормализация схлопывает
whitespace через `split/join` и применяет `casefold`. Порядок признаков — часть API.
Пустая строка допустима; неизвестное поле не становится новым признаком само собой.

`train.training_matrix` и `serve.serving_vector` вызывают **одну** функцию
`transform`. Это устраняет конкретный класс skew: одна сторона считает килограммы,
другая — граммы; одна убирает повторные пробелы, другая считает их символами.
Совпадение preprocessing не доказывает качество модели: временной сдвиг, другая
популяция запросов, отсутствующие online-признаки и неверная выборка остаются
отдельными рисками. Если transform обучаемый, например scaler или vocabulary,
обучение идёт только на train, а параметры сохраняются вместе с моделью. Нельзя
заново fit на одиночном serving-запросе.

Пример не обучает модель: он изолирует договор поставки. Для реального сервиса
версия transform, порядок features, dtype, версия модели и совместимость окружения
должны быть зафиксированы в manifest. Изменение preprocessing без обновления
контракта может тихо изменить прогнозы, даже когда HTTP-схема осталась прежней.

## Что именно доказывает clean-env тест

Тест запускает `python -m parcel_features` извне исходников и проверяет численные
результаты, затем смотрит `parcel_features.__file__` и `sys.prefix`. Файл должен
находиться внутри нового venv, а `sys.prefix` отличаться от `sys.base_prefix`.
Отдельный случай с Unicode и некорректной массой проверяет вычисления и валидацию.
Это исполнение реального wheel, а не поиск строк в конфигурации.

Эта проверка не доказывает воспроизводимость байт-в-байт, работу на другой ОС,
совместимость будущих версий Python или поставку native extensions. Для них нужны
отдельные окружения и артефакты. Версия `0.1.0` здесь учебная; опубликование в PyPI
не требуется и автоматически не выполняется.
