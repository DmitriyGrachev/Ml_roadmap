# Async lifecycle: кто завершает оставшуюся работу

Catalog ID: `python-async-lifecycle`.

Предпосылки: [введение в asyncio](../../10_asyncio/README.md),
[теория жизненного цикла](../../10_asyncio/theory.md), исключения, `finally`,
контекстные менеджеры, [bounded fetch](../bounded_fetch/README.md).
Цель: доказать ограничение работы и корректный teardown при успехе, ошибке и отмене.

## Авторский пример

[demo.py](demo.py) реализует `run_batch`: результат каждого источника нужен, порядок
ответов соответствует входу, ошибка одного делает весь batch неуспешным.
TaskGroup владеет дочерними Task, семафор ограничивает **активный fetch**, timeout
охватывает группу вместе с очередью ожидания permit. Сначала проверяется `limit`:
нулевой, отрицательный, дробный и `True` недопустимы даже для пустого входа.

Из корня репозитория после установки окружения:

```bash
uv run --offline python -m modules.01_python_core.exercises.async_lifecycle.demo
uv run --offline pytest modules/01_python_core/exercises/async_lifecycle/test_demo.py -q
```

Ожидаемые ответы `NORTH`, `SOUTH`, `EAST`; строки `closed` показывают `finally`,
но доказательство cleanup дают тесты с искусственным отказом и внешней отменой.
Порядок диагностических строк не является API. Счётчики и событийные барьеры
позволяют отделить ограничение concurrency от случайного порядка исполнения.

## Самостоятельная задача

Реализуйте только `first_healthy` в [starter.py](starter.py). Это **другая** задача:
есть несколько реплик одного источника, нужен первый успешный payload, а не все
результаты. Сохраните каждый occurrence входа как отдельную попытку. Контракт:

1. `limit` — положительный `int`, `bool` недопустим; проверка до запуска probe.
2. Не более `limit` активных `probe`; ожидающие permit не занимают ресурс.
3. Обычная ошибка `Exception` одной реплики не мешает следующим попыткам.
4. Первый успешно завершившийся probe определяет ответ; при одновременных успехах
   допустим любой из них. Все оставшиеся Task отменены и дожданы **до** возврата.
5. Пустой вход или неуспех всех реплик даёт `LookupError`. Не выдавайте последнюю
   случайную сетевую ошибку за стабильный контракт агрегатора.
6. Внешняя отмена пробрасывается как `CancelledError`, общий дедлайн — `TimeoutError`.
   В обоих случаях cleanup активных probe завершён до выхода. `None` отключает
   дедлайн; значения timeout задаются в секундах по семантике `asyncio.timeout`.
7. Входная последовательность не изменяется. Task, созданные вашей функцией,
   не остаются жить после успеха, отказа или отмены.

```bash
uv run --offline pytest modules/01_python_core/exercises/async_lifecycle/test_starter.py -q
uv run --offline python -m roadmap_tools.cli check python-async-lifecycle
```

Starter намеренно вызывает `NotImplementedError`: обычный учебный запуск показывает
`xfail`, строгая проверка не засчитывает это как выполнение. Авторский batch не
вызывайте вместо реализации: его семантика отказа несовместима с контрактом гонки.

## Защита и перенос

Слабое доказательство: «на трёх быстрых coroutine вернулся правильный список».
Сильное: показать событийный тест, где один probe держит ресурс, другой выигрывает,
третий ждёт permit; после ответа счётчик равен нулю и owned Task закончены. Затем
показать тот же инвариант при внешней отмене и при истечении дедлайна. Объясните,
почему `cancel()` без последующего ожидания не доказывает закрытие соединения.

Перенос без готового решения: у реплик есть общий глобальный лимит и лимит на host;
как избежать ситуации, когда запрос держит глобальный permit, ожидая host permit?
Опишите порядок захвата, поведение очереди и один событийный тест. Отдельно
объясните, почему отмена `to_thread` не доказывает остановку вызова блокирующего SDK.
