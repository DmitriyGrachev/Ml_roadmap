# Coroutine, Task и владение временем жизни

Предпосылки: функции, исключения и `try/finally`, контекстные менеджеры,
`Awaitable`, простые тесты. После [вводного примера](example.py) перейдите к
[жизненному циклу задач](../exercises/async_lifecycle/README.md): успешный результат
без корректного завершения фоновой работы ещё не означает корректную программу.

## Что именно запускается

Вызов `async def fetch()` создаёт **coroutine object**. Тело не исполняется в момент
вызова. `await fetch()` запускает coroutine в текущей Task и ожидает результат;
сам по себе такой `await` не создаёт конкурентную ветку. Два последовательных
`await fetch()` остаются последовательными. `asyncio.create_task(fetch())`
создаёт Task, которую event loop будет планировать независимо от вызывающей ветки.
Полученную Task нужно сохранить и в конце дождаться: она хранит результат,
исключение и состояние отмены. Создать Task и забыть о ней — потерять владельца
работы, а не реализовать надёжную фоновую очередь.

Java-аналогия с `CompletableFuture` помогает представить отложенный результат,
но скрывает важное различие: здесь обычный Python-код в одном event loop выполняется
кооперативно. Переключение возможно в точке приостановки. Не каждый `await`
приостанавливает выполнение: уже готовый awaitable может завершиться сразу.
Длинный синхронный цикл без отдачи управления блокирует все запросы этого loop.

## Структура важнее количества create_task

`asyncio.TaskGroup` задаёт область владения: задачи создаются через
`group.create_task(...)`, выход из `async with` ждёт их окончания. При обычной
ошибке одной дочерней задачи группа отменяет остальных и ждёт их завершения.
Несколько ошибок могут попасть в `ExceptionGroup`; обработка подгрупп требует
`except*`, а не предположения, что выйдет единственный `ValueError`.
`KeyboardInterrupt` и `SystemExit` имеют специальную семантику; здесь мы разбираем
обычные ошибки I/O. Отмена отдельной дочерней Task имеет иную семантику, чем
обычная ошибка: она сама по себе не означает отказ всех соседей.

`gather` удобен для агрегирования awaitable и возвращает результаты в порядке
аргументов. При стандартном `return_exceptions=False` первая ошибка передаётся
ожидающему коду, но остальные задачи автоматически не обязаны быть отменены и
дожданы. Если вы вручную реализуете гонку или `FIRST_COMPLETED`, вы сами владеете
оставшимися Task. В `finally` требуется отменить незавершённые и **дождаться всех**,
включая уже завершившиеся с ошибкой. Один `task.cancel()` лишь отправляет запрос.

## Ограничение ресурса и дедлайн

`Semaphore(n)` ограничивает число задач внутри `async with semaphore`, а не
число созданных Task. Размещайте ограничение вокруг реального I/O, соединения или
другого дефицитного ресурса. Если создать миллион Task с семафором 10, одновременно
работать будут примерно 10, но память для миллиона ожидающих Task никуда не исчезнет.
Для неограниченного потока нужны ограниченная очередь и фиксированные workers;
это отдельное решение о backpressure, а не свойство семафора.

В авторском примере `asyncio.timeout(seconds)` окружает всю группу, поэтому бюджет
включает ожидание семафора. Истечение бюджета отменяет текущую Task; менеджер
преобразует вызванную им отмену в `TimeoutError`, который ловят **вне** `async with`.
Внешняя отмена должна остаться `CancelledError`. `wait_for` тоже отменяет ожидаемую
работу и ждёт её завершения; он полезен как предохранитель теста. Дедлайн не означает
жёсткую верхнюю границу времени возврата: cleanup может занять время, а блокирующий
код вообще не отдаёт управление. Для запроса задавайте общий бюджет, а не новый
полный timeout на каждой повторной попытке.

## Отмена — ветка управления, а не случайная ошибка

`asyncio.CancelledError` наследуется от `BaseException`; обычный `except Exception`
его не перехватывает. Обычно достаточно `try/finally` для освобождения ресурса.
Если отмену ловят явно ради логирования, после cleanup её пробрасывают через
`raise`. Молчаливое подавление нарушает договор вызывающего кода и может сломать
структурную отмену. Отмена кооперативна: Task замечает её в точке приостановки.
Повторная отмена может прервать асинхронный cleanup; сложный сетевой teardown должен
иметь собственную продуманную политику, а не бесконечный `shield`.

Проверьте три пути отдельно: вся работа успешна; сосед упал; владелец отменён
извне. На каждом пути открытый ресурс закрыт, permit возвращён, принадлежащие
операции Task закончены. Тестировать только возвращённые значения недостаточно:
осиротевшая задача может ещё писать в БД после ответа с ошибкой.

## Потоки и процессы

`asyncio.to_thread(blocking_call, ...)` подходит для существующего блокирующего
I/O API, если его нельзя заменить async API. Отмена ожидающей Task не прекращает
уже выполняющуюся функцию в потоке. Функции нужны собственные timeout, безопасное
завершение, иногда сигнал остановки. Объект соединения также должен поддерживать
выбранный режим доступа из потоков. Нельзя считать освобождённым внешний ресурс
только потому, что `await to_thread(...)` был отменён.

Для тяжёлого Python CPU-кода процесс часто уместнее потока: у процессов отдельные
интерпретаторы и память, но есть сериализация входов, запуск, передача результата
и стоимость копирования. Некоторые native-библиотеки освобождают GIL и сами
распараллеливают вычисления — измеряйте конкретную библиотеку. Отмена awaitable
у `ProcessPoolExecutor` также не гарантирует остановку уже исполняющейся работы.
Не создавайте новый pool на каждый HTTP-запрос; определите владельца pool и предел
очереди. Это не делает asyncio механизмом CPU-параллелизма.

## Как проверять без удачного sleep

`Event` фиксирует «ресурс открыт», другой Event разрешает завершение; `Queue`
сообщает, кто вошёл в критическую секцию. Сначала дождитесь событий, затем
проверяйте `active`, после отмены — `closed` и состояния Task. Таймаут в две
секунды в тесте является watchdog от зависания, а не доказательством производительности.
Короткий реальный дедлайн в timeout-тесте проверяет переход к cleanup; тест не
сравнивает прошедшие миллисекунды и не требует конкретной скорости машины.

Объясните, почему копирование all-or-fail TaskGroup из batch не решает гонку, где
ошибка одной реплики должна позволить другой вернуть успешный результат.
