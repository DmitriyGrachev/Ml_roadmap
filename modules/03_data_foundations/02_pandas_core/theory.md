## 1. Таблица, столбец и метки

Представьте журнал двух мастер-классов. У каждой строки есть номер записи, у
каждого столбца — имя. `DataFrame` хранит двумерную таблицу; извлечённый столбец
становится одномерной `Series`. `Index` — метки строк, а не обязательно номера
позиций. В отличие от обычного списка или массива NumPy, операция Pandas может
сопоставлять значения по этим меткам.

```pycon
>>> import pandas as pd
>>> visits = pd.DataFrame({"room": ["A", "B"], "seats": [12, 8]}, index=["w-2", "w-1"])
>>> visits.shape, visits.index.tolist(), visits.columns.tolist()
((2, 2), ['w-2', 'w-1'], ['room', 'seats'])
>>> type(visits["seats"]).__name__, visits["seats"].index.tolist(), visits["seats"].tolist()
('Series', ['w-2', 'w-1'], [12, 8])
```

Сначала создана таблица из двух столбцов и двух строк. `shape=(2, 2)` сообщает
только число строк и столбцов; `index` сообщает их идентичность и порядок.
`visits["seats"]` сохраняет метки исходных строк. Число `12` не привязано к
«нулевой строке навсегда»: сейчас оно относится к `w-2`. Java-аналогия с
`List<Row>` полезна для чтения строк, но не объясняет автоматическое
сопоставление по меткам — это отдельное правило Pandas.

Типичная ошибка — принять `Index(["w-2", "w-1"])` за скрытый столбец данных.
Он не входит в `visits.columns`; индекс можно сбросить или заменить. Для
проверки измените порядок меток на `['w-1', 'w-2']`: значения останутся в
указанном порядке строк, но их названия изменятся.

## 2. Выравнивание по меткам, не по позиции

**Прогноз 1.** Какой бонус получит `w-2`: 100 или 200? В `bonus` первым стоит
`w-1`, а в таблице первым стоит `w-2`.

```pycon
>>> import pandas as pd
>>> visits = pd.DataFrame({"seats": [12, 8]}, index=["w-2", "w-1"])
>>> bonus = pd.Series([100, 200], index=["w-1", "w-2"])
>>> visits["bonus"] = bonus
>>> visits["bonus"].tolist()
[200, 100]
>>> visits["seats"].add(bonus).to_dict()
{'w-1': 108, 'w-2': 212}
```

Присваивание `Series` столбцу и сложение двух `Series` используют **label
alignment** — выравнивание по меткам. Для `w-2` Pandas ищет бонус с меткой
`w-2`, то есть 200; для `w-1` — 100. При сложении порядок индекса результата
может отличаться от порядка левого аргумента; поэтому вывод показан как словарь
меток и значений. Порядок элементов в `bonus` не определяет
соответствие. NumPy-массив `bonus.to_numpy()` потерял бы этот смысл: два массива
одинаковой длины складывались бы по позициям. Позиционное поведение бывает
нужно, но его выбирают осознанно после проверки порядка строк.

| Метка строки | seats слева | bonus найден по метке | Присвоенный bonus | Сумма |
| --- | ---: | ---: | ---: | ---: |
| w-2 | 12 | 200 (вторая позиция Series) | 200 | 212 |
| w-1 | 8 | 100 (первая позиция Series) | 100 | 108 |

```pycon
>>> import pandas as pd
>>> seats = pd.Series([12, 8], index=["w-2", "w-1"])
>>> changed = pd.Series([3], index=["w-1"])
>>> seats.add(changed).reindex(seats.index).isna().tolist()
[True, False]
>>> seats.add(changed, fill_value=0).reindex(seats.index).tolist()
[12.0, 11.0]
```

В первом сложении для `w-2` нет пары, поэтому возникает пропуск. Параметр
`fill_value=0` меняет правило **этой операции**, а не исходные данные. Не
подменяйте им бизнес-правило: неизвестный бонус может означать «нет записи»,
а не доказанный ноль. Самостоятельная вариация: добавьте в `changed` метку
`w-3` и предскажите индекс результата. Сложение берёт объединение меток.

## 3. Выбор по метке и по номеру

`loc` (**label-based selection**) выбирает по именам индекса и столбцов;
`iloc` (**integer-position selection**) — по нулевым позициям. У среза `loc`
конечная метка включена, если она присутствует; у `iloc` верхняя граница
исключена, как в Python. Для понятного среза по меткам используйте уникальный
упорядоченный индекс. Целочисленная метка `10` в `loc[10]` всё равно метка,
а не позиция 10.

```pycon
>>> import pandas as pd
>>> visits = pd.DataFrame({"room": ["A", "B", "C"], "seats": [12, 8, 15]}, index=["w-1", "w-2", "w-3"])
>>> visits.loc["w-1":"w-2", "room"].tolist()
['A', 'B']
>>> visits.iloc[0:2, 0].tolist()
['A', 'B']
>>> int(visits.loc["w-2", "seats"]), int(visits.iloc[1, 1])
(8, 8)
```

Оба среза сейчас дали одинаковые строки, но по разным причинам: `loc` включил
конечную метку `w-2`, а `iloc` остановился *перед* позицией 2. Типичная ошибка
— считать `loc["w-1":"w-2"]` аналогом обычного Python-среза с исключённым
концом. Переставьте строки так, чтобы `w-2` стала первой, и предскажите
`iloc[0]` отдельно от `loc["w-1"]`.

## 4. Маска, сортировка и индекс результата

Фильтр обычно строится из булевой `Series` (**boolean mask**) с тем же индексом.
`sort_values` меняет порядок строк по значениям, но сохраняет их метки.
`reset_index(drop=True)` заменяет их новым индексом `0, 1, ...`; это полезно
для отчёта, но стирает прежние имена строк, поэтому применяйте его после того,
как они больше не нужны.

```pycon
>>> import pandas as pd
>>> visits = pd.DataFrame({"room": ["B", "A", "C"], "seats": [8, 12, 12]}, index=["w-2", "w-1", "w-3"])
>>> mask = visits["seats"] >= 10
>>> mask.tolist(), mask.index.tolist()
([False, True, True], ['w-2', 'w-1', 'w-3'])
>>> chosen = visits.loc[mask].sort_values(["seats", "room"])
>>> chosen.index.tolist(), chosen["room"].tolist()
(['w-1', 'w-3'], ['A', 'C'])
>>> chosen.reset_index(drop=True).index.tolist()
[0, 1]
```

Сначала маска отмечает строки с 10 и более местами. Затем `loc` оставляет
`w-1` и `w-3`; сортировка использует вторичный ключ `room`, чтобы разрешить
равенство `seats`. Параметр `kind` применяется к сортировке по одному столбцу;
здесь порядок задают два ключа. Ошибка: считать, что сортировка автоматически
перенумерует индекс. Самостоятельно поменяйте порог на 13 и спрогнозируйте
пустой результат, сохранивший те же столбцы.

## 5. Пропуски, повторы и типы до расчёта

`isna()` отмечает пропуски (`None`, `NaN`, `pd.NA`); `dropna(subset=...)`
исключает строки по **выбранным** обязательным полям. `duplicated(subset=...,
keep=...)` требует определить ключ и правило: целая одинаковая строка и
повтор одного идентификатора — разные задачи. `drop_duplicates` не знает,
какой повтор содержательно правильный. Ниже первый экземпляр `session_id`
остаётся только как демонстрационная политика, не как универсальное правило.

```pycon
>>> import pandas as pd
>>> raw = pd.DataFrame(
...     {
...         "session_id": ["s-1", "s-1", "s-2", "s-3"],
...         "attendees_text": ["12", "12", None, "8"],
...         "room": ["A", "A", "B", None],
...     }
... )
>>> raw["attendees_text"].isna().tolist(), raw.duplicated(subset=["session_id"]).tolist()
([False, False, True, False], [False, True, False, False])
>>> clean = (
...     raw.dropna(subset=["attendees_text", "room"])
...     .drop_duplicates(subset=["session_id"], keep="first")
...     .copy()
... )
>>> clean["attendees"] = pd.to_numeric(clean["attendees_text"], errors="raise")
>>> clean[["session_id", "attendees"]].to_dict("records")
[{'session_id': 's-1', 'attendees': 12}]
>>> raw.shape
(4, 3)
```

Здесь сначала удалены строки без обязательных полей, затем повтор ключа,
затем текстовое число преобразовано в числовой dtype. `errors="raise"`
обнаруживает неожиданный текст; `errors="coerce"` превращает его в пропуск,
который затем нужно обработать отдельно. Не следует полагаться на вид `"12"`
как на доказательство числового типа. После CSV-загрузки проверьте
`frame.dtypes`, несколько строк, число строк и обязательные столбцы: вывод
типов зависит от данных и настроек чтения. Если нужны конкретные типы,
задайте их явно и проверьте результат. Категориальный `category` полезен для
ограниченного словаря значений, но его *неиспользованные* категории влияют на
группировку в следующем разделе. Самостоятельная вариация: замените `"12"`
на `"twelve"` в первой строке и предскажите, в какой операции возникнет ошибка.
Затем измените только вторую строку: дойдёт ли её текст до преобразования?

Для первого чтения незнакомого CSV иногда важно сохранить текстовое
представление полей до вывода типов. `read_csv` по умолчанию распознаёт
некоторые строки, включая `NA`, как пропуски. Это удобно, но может скрыть
разницу между пустой ячейкой и буквальным кодом `NA`. Маленький вход в памяти:

```pycon
>>> from io import StringIO
>>> import pandas as pd
>>> text = "id,value\nA,12\nB,\nC,NA\n"
>>> raw = pd.read_csv(StringIO(text), dtype=str, keep_default_na=False)
>>> raw.to_dict("records")
[{'id': 'A', 'value': '12'}, {'id': 'B', 'value': ''}, {'id': 'C', 'value': 'NA'}]
>>> raw["value"].isna().tolist()
[False, False, False]
```

`StringIO` позволяет читать строку как файл. Для локального CSV вместо него
передайте путь, например `pd.read_csv("путь/к/файлу.csv", dtype=str,
keep_default_na=False)`. Получены тексты, не проверенные числа: теперь нужно
явно определить пустые поля, допустимые коды и ошибки преобразования.
Исходный файл всё равно сохраните: DataFrame не хранит побайтовый вид CSV.
Ошибка — после такого чтения полагаться только на `isna()`: пустой текст здесь
не NA. Вариация: предскажите значения при чтении этого же входа со стандартными
настройками, затем объясните потерю различия между строками B и C.

## 6. `size`, `count`, пропущенный ключ и категории

Группировка (**groupby**) разбивает строки по значениям ключа, затем считает
показатели внутри каждой группы. `size` считает строки, `count` — непустые
значения *указанного столбца*. По умолчанию `groupby` исключает строки с
пропущенным ключом (`dropna=True`); `dropna=False` создаёт для них группу.

**Прогноз 2.** Почему у комнаты `A` может быть `rows=2`, но `known_seats=1`?

```pycon
>>> import pandas as pd
>>> visits = pd.DataFrame({"room": ["A", "A", "B", None], "seats": [12.0, None, 8.0, 5.0]})
>>> summary = (
...     visits.groupby("room", dropna=False)
...     .agg(rows=("seats", "size"), known_seats=("seats", "count"))
...     .reset_index()
... )
>>> summary[["rows", "known_seats"]].to_dict("records")
[{'rows': 2, 'known_seats': 1}, {'rows': 1, 'known_seats': 1}, {'rows': 1, 'known_seats': 1}]
>>> summary["room"].isna().tolist()
[False, False, True]
```

У `A` две строки, но во второй нет `seats`. Последняя группа существует
только из-за `dropna=False`. Если бы оставили стандартное `dropna=True`,
строка с неизвестной комнатой не вошла бы в итог, и сумма `rows` стала бы 3.
Чтобы это не превратилось в незаметную потерю, заранее выберите политику
пропущенных ключей.

Категориальный столбец хранит заданный набор категорий, включая пока не
встречавшиеся. `observed=True` возвращает только наблюдавшиеся группы;
`observed=False` может добавлять пустые категории и комбинации. Указывайте
параметр явно, когда форма отчёта важна.

```pycon
>>> import pandas as pd
>>> visits = pd.DataFrame(
...     {"room": pd.Categorical(["A", "B"], categories=["A", "B", "C"]), "seats": [12, 8]}
... )
>>> visits.groupby("room", observed=True).size().to_dict()
{'A': 1, 'B': 1}
>>> visits.groupby("room", observed=False).size().to_dict()
{'A': 1, 'B': 1, 'C': 0}
```

Ошибка — принять нулевую строку `C` за реальное наблюдение. Варьируйте пример:
добавьте второй категориальный ключ и подсчитайте, сколько ненаблюдавшихся
пар может появиться при `observed=False`.

## 7. Группы и именованные агрегаты

Существующий [пример урока](example.py) создаёт четыре заявки поддержки:

| ticket_id | channel | resolution_minutes |
| --- | --- | ---: |
| S-101 | chat | 8.0 |
| S-102 | email | 30.0 |
| S-103 | chat | 14.0 |
| S-104 | email | 40.0 |

Нужно получить по одному ряду на канал. `.groupby("channel", as_index=False)`
разбивает строки на `chat` и `email`, сохраняя канал обычным столбцом.
**Named aggregation** даёт явные имена результатам: `ticket_count` считает
непустые `ticket_id`, `average_minutes` берёт среднее по длительности.
`sort_values("channel")` устанавливает порядок, `reset_index(drop=True)`
создаёт чистый индекс. Здесь все ID присутствуют, поэтому `count` совпадает
с `size`; при пропусках это уже не так.

```pycon
>>> import pandas as pd
>>> tickets = pd.DataFrame(
...     {
...         "ticket_id": ["S-101", "S-102", "S-103", "S-104"],
...         "channel": ["chat", "email", "chat", "email"],
...         "resolution_minutes": [8.0, 30.0, 14.0, 40.0],
...     }
... )
>>> result = (
...     tickets.groupby("channel", as_index=False)
...     .agg(ticket_count=("ticket_id", "count"), average_minutes=("resolution_minutes", "mean"))
...     .sort_values("channel")
...     .reset_index(drop=True)
... )
>>> result.to_dict("records")
[{'channel': 'chat', 'ticket_count': 2, 'average_minutes': 11.0}, {'channel': 'email', 'ticket_count': 2, 'average_minutes': 35.0}]
```

Проверка вручную: `chat` имеет два значения 8 и 14, поэтому среднее 11;
`email` — 30 и 40, среднее 35. Именованные агрегаты делают схему результата
видимой прямо в коде, без последующего переименования столбцов. **Прогноз 3.**
Если у `S-103` удалить `ticket_id`, но оставить длительность 14, изменятся ли
`ticket_count` и `average_minutes` одинаково? Нет: `count` станет 1,
среднее останется 11. Для числа строк группы потребовался бы `size`.

## 8. Соединение таблиц: строки могут умножиться

`merge` соединяет таблицы по ключу, как SQL `JOIN`; `DataFrame.join` по
умолчанию соединяет по индексу, поэтому для обычных столбцов здесь яснее
`merge(on=...)`. Сначала задайте ожидаемую **кардинальность**: для каждой
строки слева сколько строк справа может подходить? Вот два журнала и
справочник комнат:

| session_id | room |
| --- | --- |
| s-1 | A |
| s-2 | B |
| s-3 | A |

| room | floor |
| --- | ---: |
| A | 1 |
| B | 2 |

Левое соединение `how="left"` оставляет каждую строку слева. Если `room`
в справочнике уникален, каждой строке соответствует не более одной строки
справа: это **many-to-one** (многие занятия → одна запись комнаты).

```pycon
>>> import pandas as pd
>>> sessions = pd.DataFrame({"session_id": ["s-1", "s-2", "s-3"], "room": ["A", "B", "A"]})
>>> rooms = pd.DataFrame({"room": ["A", "B"], "floor": [1, 2]})
>>> joined = sessions.merge(rooms, on="room", how="left", validate="many_to_one", sort=False)
>>> joined.to_dict("records")
[{'session_id': 's-1', 'room': 'A', 'floor': 1}, {'session_id': 's-2', 'room': 'B', 'floor': 2}, {'session_id': 's-3', 'room': 'A', 'floor': 1}]
>>> len(joined) == len(sessions)
True
```

Получился результат:

| session_id | room | floor |
| --- | --- | ---: |
| s-1 | A | 1 |
| s-2 | B | 2 |
| s-3 | A | 1 |

Теперь ошибочно добавим вторую запись `A` с другим этажом. Без проверки
каждое занятие в `A` встретится с **обеими** правыми строками: 3 строки слева
превратятся в 5. Это не дополнительная запись занятия, а умножение строк при
соединении.

| session_id | room | floor |
| --- | --- | ---: |
| s-1 | A | 1 |
| s-1 | A | 9 |
| s-2 | B | 2 |
| s-3 | A | 1 |
| s-3 | A | 9 |

```pycon
>>> import pandas as pd
>>> sessions = pd.DataFrame({"session_id": ["s-1", "s-2", "s-3"], "room": ["A", "B", "A"]})
>>> bad_rooms = pd.DataFrame({"room": ["A", "A", "B"], "floor": [1, 9, 2]})
>>> expanded = sessions.merge(bad_rooms, on="room", how="left", sort=False)
>>> expanded[["session_id", "floor"]].to_dict("records")
[{'session_id': 's-1', 'floor': 1}, {'session_id': 's-1', 'floor': 9}, {'session_id': 's-2', 'floor': 2}, {'session_id': 's-3', 'floor': 1}, {'session_id': 's-3', 'floor': 9}]
>>> len(expanded)
5
```

`validate="many_to_one"` отвергнет неуникальный правый ключ до выдачи
такого результата. Проверка числа строк после соединения полезна, но не
заменяет проверку смысла ключей. `how="left"` сохраняет и строки без пары,
добавляя пропуски в правые столбцы. Особая ловушка: в Pandas **null-ключи
слева совпадают с null-ключами справа** при `merge`, в отличие от обычного
SQL-предположения. Поэтому заранее проверяйте политику пропущенных ключей и
не считайте `validate` проверкой полноты соответствий. Самостоятельная
вариация: добавьте занятие в `C` и предскажите количество строк и пропуск
в `floor` после корректного левого соединения.

## 9. Даты: сначала разбор, затем календарная операция

Текст `"2026-02-01T23:30:00-02:00"` обозначает момент, который в UTC
уже наступил **2 февраля**. `pd.to_datetime(..., utc=True)` разбирает
смещение, приводит моменты к UTC и создаёт тип datetime с часовым поясом.
Только после этого `.dt` даёт календарные поля. Группировка по исходной
строке или по дате до выбора часового пояса может дать другой день.

```pycon
>>> import pandas as pd
>>> events = pd.DataFrame({"start_text": ["2026-02-01T23:30:00-02:00", "2026-02-02T00:15:00Z"]})
>>> events["started_at"] = pd.to_datetime(events["start_text"], utc=True, errors="raise")
>>> events["started_at"].dt.strftime("%Y-%m-%d %H:%M %Z").tolist()
['2026-02-02 01:30 UTC', '2026-02-02 00:15 UTC']
>>> events["started_at"].dt.date.astype(str).tolist()
['2026-02-02', '2026-02-02']
```

`errors="raise"` выявляет неверную дату; если требуется исключать такие
строки, можно выбрать `errors="coerce"`, затем явно проверить `isna()` и
задокументировать их судьбу. Самостоятельная вариация: замените первое
смещение на `+02:00` и предскажите дату в UTC до запуска.

## 10. Изменение данных: Pandas 3 и NumPy

В Pandas 3 **Copy-on-Write (CoW)** — постоянное поведение: выборка может
разделять память с источником до записи, но запись в один объект не должна
неожиданно изменить другой. Это не обещание немедленной физической копии
каждой выборки. Меняйте нужный `DataFrame` одной явной операцией, например
`frame.loc[mask, "seats"] = value`; не полагайтесь на цепочку
`frame["seats"][mask] = value` как способ изменить исходную таблицу.

```pycon
>>> import pandas as pd
>>> frame = pd.DataFrame({"seats": [8, 12]})
>>> selected = frame["seats"]
>>> selected.iloc[0] = 99
>>> frame["seats"].tolist(), selected.tolist()
([8, 12], [99, 12])
>>> frame.loc[frame["seats"] < 10, "seats"] = 10
>>> frame["seats"].tolist()
[10, 12]
```

В NumPy базовый срез массива часто является **view** и запись через него
может изменить исходный массив; fancy indexing часто даёт копию. Не
переносите это правило автоматически на Pandas. Даже при CoW решение не
мутировать аргументы функции остаётся частью контракта: создайте результат
явно и проверьте входы, если обещали их сохранить. `to_numpy()` переносит
данные к правилам NumPy и может терять метки, менять представление типов и
возвращать массив с ограничениями на запись; не используйте его как способ
обойти CoW. Граница аналогии: CoW объясняет *эффект записи*, а не очищает
данные и не обеспечивает правильность join.

## 11. Самопроверка

Сначала ответьте письменно, затем раскройте ответы.

1. Почему `Series([5], index=["b"])` при присваивании таблице с индексом
   `["a", "b"]` не кладёт 5 в первую строку?
2. Чем отличаются `loc["a":"b"]` и `iloc[0:1]` при индексе `["a", "b"]`?
3. Почему после сортировки индекс может выглядеть «не по порядку»?
4. Когда `size` и `count` группы дадут разные числа?
5. Что меняют `dropna=False` и `observed=True` в группировке?
6. Как левый `merge` из 3 строк может дать 5 и какая проверка обнаружит это
   до выдачи результата?
7. Что произойдёт, если у обеих таблиц `merge` ключ отсутствует (`null`)?
8. Почему `utc=True` применяют до извлечения календарного дня?

<details>
<summary>Ответы после попытки</summary>

1. `Series` выравнивается по меткам: `b` получает 5, `a` — пропуск.
2. `loc` включает обе метки `a` и `b`; `iloc[0:1]` берёт только позицию 0.
3. Сортировка меняет порядок строк, сохраняя их метки; `reset_index(drop=True)`
   создаёт последовательный индекс, если старые метки больше не нужны.
4. При пропуске в считаемом столбце: `size` считает строку, `count` — нет.
5. `dropna=False` добавляет группу с пропущенным ключом; `observed=True`
   оставляет лишь встреченные категории и их комбинации.
6. Две правые строки с одинаковым ключом умножают каждую подходящую левую
   строку; `validate="many_to_one"` отвергнет такой правый ключ.
7. Pandas сопоставит эти null-ключи; пропуски в ключах нужно валидировать
   отдельно по правилу задачи.
8. Местный календарный день может отличаться от UTC-дня того же момента.

</details>
