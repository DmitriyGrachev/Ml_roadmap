# Разброс результата: что именно повторяется

## Одна оценка не описывает весь процесс

Вы получили accuracy .84. Это значение зависит от выборки, разделения,
параметров preprocessing, гиперпараметров, алгоритмической случайности и будущей
популяции. Для ответа «насколько стабильно наше обучение» нужно повторять весь
процесс fit, а не только пересчитывать метрику одних и тех же predictions.
У разных экспериментов разные источники неопределенности; смешивать их
в одну полосу «95% надежности» нельзя.

Сначала отделите locked holdout по допустимому для задачи правилу.
Запишите его row IDs и оставьте вне всех циклов выбора. Остальные строки —
development. Внутри development для каждого split_seed сформируйте train pool
и validation. Для каждого размера n возьмите подвыборку train pool и заново
обучите pipeline: fit scaler, fit model, predict validation, посчитайте метрику.
Изменение holdout признаков/меток не должно менять ни выбранные размеры,
ни параметры, ни development scores. Author API получает holdout IDs только
для исключения строк; его значения не используются при fit/evaluation.

## Как читать learning curve

Для одного seed авторский алгоритм переставляет development IDs,
резервирует первые 25% (минимум две строки) под validation, остаток — train pool.
Размеры берутся как вложенные префиксы train pool. Это позволяет сравнивать
размеры при одном validation и согласованных train подвыборках.
Между seeds validation меняется: разброс отражает одновременно состав train
и validation, а не чистую «случайность оптимизатора».

Например, development содержит 50 строк. Validation имеет 12 строк;
train pool — 38. Для seed 2 обучаем новые pipeline на 12 и 30 train строках;
для seed 7 — еще два pipeline на новом разделении. Получаем четыре независимых
fit-вызова, но **не четыре независимых измерения популяции**: строки повторяются
между разделениями. Нельзя автоматически превращать стандартное отклонение
этих четырех оценок в доверительный интервал среднего через `std/sqrt(4)`.
Повторные splits зависимы и оценивают конкретную процедуру на конечном датасете.

Сводная таблица должна содержать seed, размер train, validation count, метрику,
ID/хэш split и параметры pipeline. Сравните средний результат, разброс и
изменение по размеру. Малый train может давать высокую дисперсию;
больший train не обязан улучшить каждую отдельную оценку монотонно.
В авторском примере Ridge детерминирован: меняется split seed, а не внутренний
seed оптимизатора. Чтобы выделить алгоритмический разброс, фиксируют split и
отдельно варьируют random_state стохастической модели. Чтобы оценить оба
источника, строят вложенный эксперимент split×model_seed и явно называют оси.

## Pipeline повторяется целиком

Нельзя сначала обучить StandardScaler/PCA на всех данных, а затем повторять
только estimator: информация validation уже попала в train. В каждом fit
создается новый `make_pipeline(StandardScaler(), model)`.
Точно так же внутри split обучаются imputer, выбор признаков и подбор порога.
Если выбираете модель/гиперпараметры, нужен внутренний validation/CV;
оценка выбранной процедуры требует внешнего разбиения либо отдельного holdout.
В этом упражнении параметры фиксированы заранее, поэтому простой цикл достаточен.

Locked holdout открывается один раз после фиксации выбора.
Результат на нем может оказаться хуже development: это наблюдение, не разрешение
подобрать новый seed на holdout. После такого подбора нужен новый независимый
контроль. Не сообщайте лучший seed как качество процедуры; seed — параметр
воспроизводимости, а не маркетинговый гиперпараметр.

## Paired bootstrap отвечает на другой вопрос

Теперь модели A/B уже обучены и их predictions зафиксированы на одних и тех же
n объектах. Для каждого объекта вычисляем разницу потерь
`d_i=loss_A_i-loss_B_i`; положительное значение выгодно B.
Сэмплируем с возвращением n индексов из `0..n-1`, **одни и те же индексы**
для обеих моделей, и считаем среднюю d. Повторяем B раз; percentile interval
— квантили .025 и .975 полученных средних.
Здесь не происходит новых fit, новых split или пересчета scaler.
Интервал условен на конкретные обученные модели и выбранную evaluation выборку;
он не описывает полную вариативность нового обучения.

Ручной пример: losses A `[1,4,9]`, B `[0,3,8]` дают d `[1,1,1]`.
Любой paired resample имеет среднее 1, интервал `[1,1]`.
Независимый resampling A/B разрушил бы это свойство и добавил лишний шум.
Для accuracy удобно определить `d_i=I(B_i=y_i)-I(A_i=y_i)`:
значения -1/0/+1, положительная средняя снова означает выигрыш B.
В learner fixture y `[0,0,1,1]`, A `[0,1,0,1]`, B `[0,0,1,0]`
дают d `[0,1,1,-1]`, среднее .25. Четыре намеренно простых resample,
каждый повторяющий один индекс четыре раза, дают bootstrap means `[0,1,1,-1]`;
линейные квантили NumPy равны `[-.925,1]`. Это проверка арифметики,
а не надежный интервал для реальной задачи из четырех строк.

Даже интервал выше нуля не объясняет практический размер эффекта,
цену ошибок или устойчивость к сдвигу распределения. Сравнивать много моделей
и предъявить только лучший интервал — тоже selection bias.

## Когда IID-перестановка запрещена

Повторные события одного клиента зависимы. Разделяйте клиентов группами:
все события клиента либо train, либо validation/holdout. Resampling выполняйте
по группам, сохраняя парность A/B внутри каждой группы; определите, имеет ли
каждый клиент равный вес или вес по числу событий.
Во временной задаче train должен предшествовать validation: используйте rolling
или expanding windows и учитывайте gap/embargo, если признаки/метки перекрывают
время. Обучение на будущем ради предсказания прошлого недопустимо.
Для зависимого ряда обычный построчный bootstrap переоценивает количество
независимой информации; нужны временные блоки/другая обоснованная схема.
Настоящий temporal backtest не превращается в IID experiment от добавления seed.

Предоставленные функции рассчитаны на IID строки: они не распознают скрытых
клиентов/время автоматически. До запуска ученик обязан аргументировать единицу
наблюдения и доступность признаков на момент prediction.

## Самостоятельный эксперимент

`classification_sweep` отличается от регрессионного author demo:
для каждого seed переставьте development IDs, первые `validation_size` — valid,
остальные — pool. Для каждого train size заново обучите
`StandardScaler + LogisticRegression(C=1,solver='lbfgs',max_iter=1000)`.
Верните записи с seed, size, train_ids, validation_ids, accuracy.
Требуйте конечную X `(n,d)`, бинарную y `(n,)`, валидные уникальные holdout IDs,
непустые seeds/sizes, `validation_size>=1`, `size>=2` и достаточно pool.
Одноклассовый train отклоняется ValueError; не перебирайте seeds тайком до
«удачного» split. Размеры вложены, valid одинаков внутри seed, holdout исключен.

`paired_accuracy_interval` получает фиксированные y/A/B и готовую матрицу
целочисленных индексов `(B,n)`, B>=2. Верните наблюдаемую среднюю d и массив
двух линейных квантилей [.025,.975]. Отклоняйте несовместимые/пустые формы,
нецелочисленные/вне диапазона индексы. Модели здесь не обучаются.

Слабый ответ: «запустил bootstrap 1000 раз, значит модель стабильна».
Сильный ответ: предъявляет оба эксперимента отдельно, seed/size table и split IDs,
объясняет единицу resampling, отсутствие holdout в выборе и зависимость folds.
Автотесты проверяют вычисления; валидность IID для вашей предметной области
подтверждается анализом данных и human review.
