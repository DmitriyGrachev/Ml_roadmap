# Preregister a bounded experiment

ID: `data-experiment-design` · средняя сложность · 60–90 минут.

Перед началом: [статистический дизайн](../../04_practical_statistics/experiment_design.md),
`data-randomized-experiment` — [единица и назначение arm](../randomized_experiment/README.md).
Повторно писать агрегацию событий или парный bootstrap не нужно.

## Один программный контракт

Реализуйте только `bonferroni_rejections(p_values, alpha=0.05)` в `starter.py`.
`p_values` — полный заранее объявленный непустой набор p-values одного финального
анализа; все числа конечны и лежат в `[0,1]`. Семейный `alpha` конечен и строго
внутри `(0,1)`. Любое нарушение вызывает `ValueError` **даже если** какое-то раннее
значение уже достаточно мало для отклонения.

Верните `tuple[int, ...]` исходных индексов (с нуля) тех гипотез, для которых
`p <= alpha / m`, где m — длина всего набора. Индексы идут по возрастанию;
вход не меняется. Не сортируйте результат по p-value и не уменьшайте m,
выкидывая незначимые значения. Значение на самой границе считается отклонением.
Для непрерывной нормальной модели равенство имеет нулевую вероятность, но кодовый
контракт обязан однозначно определить границу.

Bonferroni использует корректность каждого p-value и ограничивает FWER, а не долю
ложных открытий среди всех открытий. Здесь нет реализации sequential inference:
передавать минимальные p по многим просмотрам как обычные финальные p некорректно.

## Собственная симуляция, отдельно от unit tests

1. Скопируйте [незаполненный шаблон](report-template.md) в собственные учебные
   заметки вне каталога задания. **До запуска** выберите другой содержательный
   сценарий с непрерывной метрикой: единицу, единицы измерения, направление пользы,
   независимость arm и известную sigma как допущение симулятора. Не используйте
   датчики и готовые численные результаты teacher-примера.
2. Запишите H0, двустороннюю альтернативу, практически полезный эффект, отдельный
   MDE для power, alpha семьи, число m заранее объявленных метрик и целевую power.
   Если m>1, объясните, что проверяется power **одного** теста при alpha/m.
3. Выберите seed, repeats и фиксированное n на arm **до просмотра** результатов.
   Начните с n, рассчитанного по формуле, затем проверьте ограничения бюджета:
   `1<=n<=10000`, `1<=repeats<=5000`, `n*repeats<=2000000`. Слишком дорогой план
   уменьшайте до запуска и отмечайте достижимую power; не запускайте подбор seed.
4. Запишите прогнозы: A/A final против alpha/m; A/B final против расчётной power;
   что будет при peeking, при уменьшении MDE вдвое и при увеличении m. Сохраните
   план с датой. После запуска план не редактируйте, отклонения записывайте отдельно.
5. Запустите учительский симулятор **со своей конфигурацией**. Команда из корня
   имеет вид ниже; угловые скобки замените числами, не копируйте их буквально:

   ```text
   uv run --offline --no-sync python -m modules.03_data_foundations.04_practical_statistics.experiment_demo --seed <seed> --repeats <R> --sigma <sigma> --mde <MDE> --alpha <alpha_family> --power <power> --comparisons <m> --n <n_per_arm>
   ```

   Сохраните полную команду, вывод, версию Python и NumPy. Симулятор моделирует
   A/A и A/B **одной метрики** при alpha/m; он не создаёт всю семью m метрик.
   Полный набор p-values для программного контракта задайте отдельно и заранее:
   это детерминированная проверка правил отбора, не итог случайного эксперимента.
6. Рассчитайте Monte Carlo SE для долей A/A final и A/B final; сопоставьте с
   прогнозами, без требования попасть точно в alpha или получить p<0.05 на любом
   seed. Наблюдаемая доля открытий не равна p-value одного опыта.
7. Выполните **одно заранее выбранное** изменение параметра и сохраните второй
   запуск независимо от результата. Не увеличивайте повторы после неприятного
   вывода с целью добиться значимости. Объясните, как ваши выводы ограничены
   нормальностью, известной sigma, независимостью, отсутствием потерь и реального
   механизма назначения arm. Укажите, каких свидетельств не хватает для настоящего A/B.

Теория показывает механизмы на другом примере; готовый отчёт за вас не написан.
Симуляция не обращается к сети, данным клиентов или моделям и ничего не сохраняет
автоматически. Предельный бюджет ограничивает память и время, а не хвосты Normal.

## Проверка и границы зачёта

Из корня репозитория, после подготовки существующего окружения:

```powershell
uv run --offline --no-sync python scripts/learn.py test data-experiment-design
uv run --offline --no-sync python scripts/learn.py check data-experiment-design
uv run --offline --no-sync python -m pytest modules/03_data_foundations/exercises/experiment_design -q -rx
```

До заполнения TODO тесты дают xfail; `check` отклоняет незавершённый starter.
Unit tests детерминированно проверяют порог, индексы, границы и валидацию,
не требуют удачного стохастического результата. Teacher tests проверяют формулы,
накопление одних и тех же данных и ограничения бюджета. Собственная симуляция
и объяснение preregistration проверяются человеком отдельно: CLI не доказывает
хронологию плана, качество настоящей рандомизации и понимание ученика.

Готово, когда contract проходит без xfail и вы можете защитить свой исходный план,
показать оба запуска, объяснить пропуск эффекта, ложное открытие и поправку семьи.
Не меняйте progress только за чтение или повтор готовой демонстрации.
