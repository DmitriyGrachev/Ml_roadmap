# Когда событие уже известно модели

## Prerequisites

Нужны фильтрация DataFrame, `groupby`, joins, временные типы Pandas,
UTC/timezone и понятие train/validation/test. Здесь строка результата означает
запрос на прогноз, а не строку события. Поэтому агрегирование начинается
с явного определения единицы наблюдения и временной границы.

## Схема данных и вычисление

`events` содержит уникальные `event_id`, повторяющиеся `entity_id`, момент события
`event_time` и числовой `amount`. `queries` содержит уникальные `query_id`,
`entity_id` и момент доступности признаков `as_of`. Пара entity/time не обязана
быть уникальной: два запроса в один момент всё равно имеют разные query ID.
Агрегаты нужно вернуть в исходном порядке запросов, даже если для расчёта удобнее
сортировка. Индекс DataFrame не заменяет ID: он может быть разреженным и повторяться.

Пусть для одной сущности есть следующие события:

| ID | UTC | amount |
|---|---|---:|
| before | 1 января, 00:00 | 1000 |
| left | 2 января, 00:00 | 5 |
| inside | 3 января, 00:00 | 7 |
| same | 4 января, 00:00 | 10000 |
| future | 5 января, 00:00 | 100000 |

Для запроса 4 января, 00:00 и окна два дня берём `left` и `inside`:
`count=2`, `sum=12`, `mean=6`. Нижняя граница включена, верхняя исключена.
Значение 10000 в тот же момент не становится прошлым только из-за порядка строк.
Пусть вместо `inside` существуют два независимых события с amount 7 и -1 в тот
же timestamp. Оба входят: count растёт на два, sum на шесть. Дубликат ID при этом
ошибка ввода, а не повод автоматически удалить одну строку.

Для отсутствующей сущности возвращаем нулевые count и sum, но mean NaN. Ноль
в mean заявил бы наблюдённое среднее, хотя наблюдений нет. Это разные признаки,
и downstream-imputer должен обучать свою стратегию только на train. Отрицательные
amount допустимы, например возврат товара: count считает события, не положительные
значения. Нельзя использовать `amount.count()` после молчаливого удаления NaN:
невалидное событие должно быть обнаружено до вычисления.

## Время, timezone и доступность

Timezone-aware UTC отделяет абсолютный момент от локального отображения часов.
Naive `2026-01-04 00:00` не содержит информации о часовом поясе. Автоматическое
`to_datetime(..., utc=True)` может назначить ему UTC, хотя источник подразумевал
местное время. Поэтому функция принимает уже нормализованный UTC dtype и
отвергает смешанную object-колонку; решение о преобразовании лежит на границе
приёма данных. Даже при пустой таблице dtype служит частью схемы.

В реальной системе `event_time` может отличаться от времени получения события.
Если транзакция случилась в 10:00, но пришла в хранилище в 10:05, прогноз в 10:02
ещё не мог её использовать. Контракт упражнения предполагает немедленную
доступность; для поздних данных потребуется `available_at`, второй временной
фильтр и политика перерасчёта. Нельзя переносить решение без обсуждения этой
предпосылки. Разделение train/test по времени не исправляет утечку внутри
признаков, рассчитанных с использованием будущих строк.

## Как организовать расчёт

Для маленьких таблиц полезна эталонная стратегия: для каждого запроса отфильтровать
entity и обе временные границы, затем посчитать агрегаты. Она легко проверяется
вручную, но требует до `O(Q E)` сравнений. Это допустимый учебный старт, если
явно назвать стоимость; не обещайте линейную скорость.

Большие данные можно группировать по entity и сортировать по event_time.
Индексы границ находятся через `searchsorted(..., side='left')` для `as_of-window`
и для `as_of`: верхний указатель должен указывать на первое равное событие,
чтобы одинаковые timestamps полностью исключались справа. Разность префиксных
сумм даёт sum, разность указателей — count. Mean вычисляется после проверки count.
Понадобится сохранить позицию каждого query перед сортировкой и восстановить её
в конце. Не используйте уникальный timestamp как surrogate key события.

При одинаковых timestamp порядок событий можно фиксировать через event_id,
если ID сравнимы, либо стабильную сортировку; агрегат всё равно должен учитывать
все строки. Суммы float могут отличаться на машинный epsilon при перестановке:
для больших диапазонов используйте устойчивую сумму или явно обоснованный допуск.
Тесты упражнения используют точно представимые небольшие суммы.

## Типичные ошибки

- Обычный join по entity создаёт декартово размножение истории каждого запроса.
- `rolling` без проверки `closed` включает событие ровно в момент прогноза.
- `merge_asof` находит одну строку; это ещё не сумма произвольного окна.
- Сортировка запросов становится выходным порядком и отрывает признаки от labels.
- Общая агрегация по entity игнорирует персональный as_of каждого запроса.
- Предварительная фильтрация «будущего» относительно максимального as_of оставляет
  утечку относительно более ранних запросов.
- Конвертация времени или исправление ID внутри функции скрывает проблемы источника.

## Критерии переноса

Нарисуйте новый пример с двумя сущностями и двумя запросами одной сущности.
Для каждого запроса выпишите выбранные event_id до вычисления суммы. Затем
добавьте событие ровно на нижней границе, на верхней и на микросекунду раньше.
Меняются ли ровно те запросы, которые должны? Поменяйте будущие суммы на
миллиарды и проверьте неизменность старых результатов. Назовите источник
`available_at` в задаче кредитного скоринга, мониторинга датчиков или рекомендаций.
Без этого объяснения успешный unit test не доказывает отсутствие реальной утечки.
