# Контроль: надёжность оценки

Цель — оценить, можно ли использовать предложенную оценку качества для решения
о выпуске классификатора эскалации обращения **в момент поступления обращения**.
Учащийся исследует кандидат, формулирует проверяемые объяснения и получает новую,
защищаемую оценку. Высокая исходная accuracy — наблюдение, а не гарантия качества.
Это отдельный открытый контроль, а не повтор большого tabular study.

Prerequisites: `ml-tabular-study` ([исследование](../tabular_study/README.md)),
`ml-validation` ([валидация](../../02_validation/README.md)).

## Входы и ограничения

`fixture.dataset_bytes()` возвращает фиксированный UTF-8 JSON снимок 96 синтетических
обращений; он создаётся только при явном вызове. `id` — обращение, `account_id` —
аккаунт, `opened_day` — день поступления, `channel` — канал, `message_length` — длина
сообщения, `service_code` — код обработки, `touches` — число действий,
`label` — факт эскалации. Это экспорт служебной системы, а не готовый контракт
доступности признаков онлайн. Для каждого использованного поля явно обоснуйте
момент доступности и отделите установленный факт от допущения.

`candidate.py` содержит предоставленный кандидат и его разбиение. Изучать его можно,
изменять исходный кандидат для улучшения его цифры не нужно. Сделайте своё разбиение,
сохраните реальные предсказания и объясните, на какие будущие случаи распространяется
оценка. Конкретный алгоритм, размер тестовой части и минимальный score не навязаны.
Обязательная работа — offline CPU, без внешних моделей и скачиваний.

Редактируйте `starter.py` и при необходимости добавляйте собственные модули.
Не меняйте входы, кандидат, evidence и tests ради прохождения проверки.
`investigate(output_dir: Path) -> Path` должен вернуть `output_dir / "manifest.json"`.
Существующая выходная папка вызывает `FileExistsError`; сохранённая работа не затирается.

## Артефакты

Общий [контракт и шаблон защиты](../../../../docs/project-defense.md#контракт-артефактов-открытых-контролей).
В `artifacts` перечислите SHA-256 всех файлов: `data.json` (точные байты fixture),
`split.json`, `outputs.json`, `implementation.txt`, `report.md` и дополнительные
доказательства. `implementation.txt` — текст фактически использованного исходного
кода с относительными именами его файлов; валидатор его не исполняет.
`dataset_sha256` — SHA-256 `data.json`, `split_sha256` — SHA-256 `split.json`.

`split.json`: непустые уникальные `train_ids`, `test_ids` покрывают все входные ID
без пересечения. Тестовое множество должно отличаться от предоставленного кандидата.
Это структурная проверка; она сама не доказывает корректность разбиения.

`outputs.json`: `run_id`, `dataset_sha256`, `split_sha256` повторяют identity запуска;
`predictions` содержит `{id, prediction}` в порядке `test_ids`, `prediction` — целое
0 или 1. `accounting` содержит `count`, `correct`, `accuracy`, `tp`, `tn`, `fp`, `fn`.
Эти числа пересчитываются по labels входа и сохранённым predictions; собственные
метрики и эксперименты добавьте отдельными hash-bound файлами и обсудите в отчёте.
Сравните наблюдение кандидата с новым результатом, объясните ошибки и ограничения.

## Запуск в Windows / PyCharm

Рабочая директория — корень `_road`, интерпретатор — существующая `.venv`.
Для каждого запуска выбирайте **новое** имя выходной папки.

```powershell
.venv/Scripts/python.exe -m modules.04_machine_learning.exercises.evaluation_case.candidate "$env:TEMP/evaluation-candidate-new"
.venv/Scripts/python.exe scripts/learn.py test ml-evaluation-case
.venv/Scripts/python.exe scripts/learn.py check ml-evaluation-case
.venv/Scripts/python.exe -m modules.04_machine_learning.exercises.evaluation_case.evidence "C:/path/to/your/new-investigation"
```

В PyCharm запускайте свою `investigate(Path(...))` из Python Console либо своего
маленького launcher; точка входа остаётся TODO до вашей реализации.

## Рубрика и подсказки

Зачёт требует воспроизводимых входов/предсказаний, содержательного нового разбиения,
обоснования доступности, честной интерпретации ошибок и защиты. Не требуется победить
число кандидата. Все рассуждения и причинные выводы — `REQUIRES_REVIEW`.

1. Сначала сформулируйте единицу будущего решения и сведения, которыми оно располагает.
2. Если застряли: какие альтернативные объяснения совместимы с наблюдаемым score?
3. Затем предложите проверку, способную различить ваши объяснения, и её ограничения.

На защите получите новую вариацию: иной период или новую популяцию обращений.
Объясните, какие свидетельства надо пересобрать; исходный автоматический контракт
проверяет только исходный fixture. Изменённые данные рассматриваются отдельно человеком.

Unit: арифметика, ID, байты, разбиение. Smoke: повторяемый запуск предоставленного
кандидата в новых временных папках. Evaluation: ваше расследование — `NOT_RUN` до
реального выполнения. `test` допускает TODO xfail, `check` требует реализованного
starter и реальных артефактов. Даже зелёный check не снимает `REQUIRES_REVIEW`:
согласованные SHA-256 не доказывают, каким кодом получены предсказания.
