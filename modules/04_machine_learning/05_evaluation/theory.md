# Оценка модели: от ошибки к решению

Этот урок продолжает [постановку задачи](../01_problem_framing/README.md),
[разбиение](../02_validation/README.md) и [сравнение моделей](../04_models/README.md).
Цель — по сохранённым предсказаниям объяснить, **какое** качество измерено,
какие ошибки важны для решения и на каких данных решение разрешено выбирать.
Формулы нужны ровно настолько, чтобы проверить отчёт вручную. Вопрос до чтения:
если две модели одинаково часто ошибаются, обязательно ли их ошибки одинаково
дороги и одинаково распределены между группами?

## 1. Регрессия: единица измерения и большая ошибка

У учебных поездок на велосипеде истинная длительность в минутах —
`[10, 12, 20, 24]`, прогноз — `[11, 11, 22, 34]`. До вычисления предскажите:
какая из MAE и RMSE сильнее отреагирует на последнюю, ошибочную на 10 минут,
поездку? По отдельности ошибки `prediction − actual` равны `[1, −1, 2, 10]`.

**MAE** (*mean absolute error*) — среднее абсолютных ошибок:
`(1 + 1 + 2 + 10)/4 = 3.5 минуты`. **MSE** (*mean squared error*) — среднее
квадратов: `(1 + 1 + 4 + 100)/4 = 26.5 минуты²`. **RMSE** (*root mean squared
error*) — `√26.5 ≈ 5.1478 минуты`. У MSE квадрат исходной единицы, у MAE и RMSE
исходная единица. Возведение в квадрат делает крупный промах заметнее; оно
не устанавливает само по себе цену минуты для пользователя. Сравнивайте
кандидатов с простым train-only средним/медианным baseline на **одной** выборке
и заранее выбранной основной метрике.

```pycon
>>> from importlib import import_module
>>> route_errors = import_module("modules.04_machine_learning.05_evaluation.example").route_errors
>>> {name: round(value, 4) for name, value in route_errors().items()}
{'overall_mae_minutes': 3.5, 'overall_rmse_minutes': 5.1478, 'flat_mae_minutes': 1.0, 'hill_mae_minutes': 6.0}
```

В [исходном примере](example.py) первые две поездки относятся к ровному маршруту,
последние две — к холмам. Поддержка (*support*) каждой группы здесь всего 2,
поэтому `hill_mae=6` — повод изучить строки, а не надёжная оценка всех холмистых
маршрутов. **Типичная ошибка:** сравнить `26.5` минут² с `3.5` минутами как
две величины на одной шкале. **Вариация:** замените только прогноз `34 → 25`;
до запуска запишите новые MAE и RMSE и объясните, почему обе уменьшились по-разному.

## 2. Классификация: четыре клетки до одного процента

Для учебного датчика `1` означает «нужно проверить», `0` — «не нужно».
Пусть истинные метки `y=[0, 1, 1, 0]`, вероятности класса 1
`p=[0.1, 0.8, 0.4, 0.7]`. До подсчёта решите, какие строки изменят своё решение,
если вместо порога `0.5` использовать `0.7`. Здесь правило зафиксировано как
`decision = 1`, когда `p >= threshold`, включая равенство.

| Строка | `y` | `p` | Решение при `0.5` | Клетка |
| --- | ---: | ---: | ---: | --- |
| A | 0 | 0.1 | 0 | TN |
| B | 1 | 0.8 | 1 | TP |
| C | 1 | 0.4 | 0 | FN |
| D | 0 | 0.7 | 1 | FP |

**Confusion matrix** при порядке `[[TN, FP], [FN, TP]]` равна
`[[1, 1], [1, 1]]`. **Accuracy** = `(TP+TN)/4 = 0.5`, **precision** =
`TP/(TP+FP) = 0.5`, **recall** = `TP/(TP+FN) = 0.5`, **F1** =
`2·precision·recall/(precision+recall) = 0.5`. Если знаменатель ноль,
метрика требует заранее оговорённой конвенции; упражнение
[evaluation report](../06_reproducibility/exercises/evaluation_report/README.md)
использует ноль. Упражнение не требует угадывать эту конвенцию из названия метрики.

Тот же расчёт позволяет проверить код без реализации чужого TODO:

```pycon
>>> from sklearn.metrics import confusion_matrix, precision_score, recall_score
>>> y = [0, 1, 1, 0]
>>> p = [0.1, 0.8, 0.4, 0.7]
>>> decision = [int(value >= 0.5) for value in p]
>>> confusion_matrix(y, decision, labels=[0, 1]).tolist()
[[1, 1], [1, 1]]
>>> (precision_score(y, decision), recall_score(y, decision))
(0.5, 0.5)
```

**Дисбаланс:** если положителен 1 объект из 100, правило «всегда 0» даёт
accuracy `0.99`, но recall положительного класса `0`. Сначала уточните, какая
ошибка важна и какова распространённость класса в будущей популяции. Precision
зависит от этой распространённости: при иной частоте событий та же модель может
показывать другую precision. Не переносите процент из учебного набора на реальный.

## 3. Метки, score, вероятности: разные вопросы

| Вопрос | Вход в метрику | Примеры |
| --- | --- | --- |
| Каковы решения при **этом** пороге? | `y_true` и метки `0/1`, полученные из порога | confusion matrix, accuracy, precision, recall, F1, FP/FN |
| Насколько хорошо объекты упорядочены? | `y_true` и непрерывный score либо вероятность класса 1 | ROC-AUC, average precision (AP) |
| Насколько хороши **числа вероятностей**? | `y_true` и вероятности в `[0,1]` | Brier, log loss, reliability bins |
| Насколько близок численный прогноз к цели? | `y_true` и численный регрессионный прогноз | MAE, MSE, RMSE |

Score (*оценка ранжирования*) может не иметь смысла вероятности: для ROC-AUC/AP
важен порядок, а Brier для такого score не определён как проверка вероятностного
прогноза. Для четырёх строк выше **Brier** = среднее `(p−y)²` =
`(0.01 + 0.04 + 0.36 + 0.49)/4 = 0.225`. Меньше лучше. Уверенная ошибка
`p=0.7` у D стоит `0.49`, хотя решение при пороге `0.5` знает лишь `FP`.

**ROC-AUC** отвечает на вопрос, насколько часто случайный положительный объект
стоит выше случайного отрицательного (при ничьих — половина). Здесь пары
`B>A`, `B>D`, `C>A`, но `C<D`: `3/4 = 0.75`. При редком положительном классе
в дополнение смотрите precision и recall: ROC-AUC может выглядеть приемлемо при
слишком большом числе ложных тревог для заданной частоты событий.

Для **PR-оценки** явно назовите способ интегрирования. Здесь по убывающему
score положительные встречаются на местах 1 и 3. Вклад прироста recall:
`AP = (1/2)·1 + (1/2)·(2/3) = 5/6 ≈ 0.8333` — это **average precision**,
ступенчатое суммирование precision при каждом приросте recall. Если соединить
точки `precision_recall_curve` отрезками и применить трапеции, площадь будет
`19/24 ≈ 0.7917`. Это другая величина; не записывайте её как AP. Дублированные
значения recall не добавляют площади по горизонтали.

```pycon
>>> from sklearn.metrics import auc, average_precision_score, precision_recall_curve, roc_auc_score
>>> y = [0, 1, 1, 0]
>>> p = [0.1, 0.8, 0.4, 0.7]
>>> precision, recall, _ = precision_recall_curve(y, p)
>>> (
...     round(roc_auc_score(y, p), 4),
...     round(average_precision_score(y, p), 4),
...     round(auc(recall, precision), 4),
... )
(0.75, 0.8333, 0.7917)
```

Калибровка (*calibration*) задаёт другой вопрос: среди объектов с предсказанной
вероятностью около `0.7` как часто случается класс 1? На четырёх строках
узкие bins бессодержательны; Brier и reliability table на достаточной выборке
дают ориентир. Сам Brier смешивает калибровку (*reliability*), способность
различать случаи (*resolution*) и неопределённость данных: меньшее значение
не доказывает, что одна только калибровка улучшилась. Хороший порядок не
гарантирует хороших вероятностей, а хорошая
вероятность не выбирает порог сама. После калибровки вероятности и решения
нужно оценить вновь; calibrator нельзя обучать на test.

Разберём один интервал (*reliability bin*) без обучения calibrator за ученика.
Десять учебных прогнозов попали в `[0.65, 0.75)`, средняя вероятность равна
`0.70`; среди этих же десяти объектов положительных оказалось четыре.
До расчёта предскажите, где будет точка относительно диагонали `y=x`.
Горизонтальная координата — среднее вероятностей `0.70`, вертикальная —
наблюдаемая доля `4/10=0.40`, support — `10`. Точка `(0.70, 0.40)` лежит
ниже диагонали: в этом малом интервале модель завысила частоту события.
Это не доказывает общую некалиброванность: десять наблюдений дают шумную долю,
остальные интервалы не рассмотрены. Типичная ошибка — взять долю положительных
по всему набору, а среднее вероятностей только по bin: знаменатели разные.

```pycon
>>> bin_probabilities = [0.70] * 10
>>> positives, support = 4, len(bin_probabilities)
>>> round(sum(bin_probabilities) / support, 2), positives / support, support
(0.7, 0.4, 10)
```

Вариация: оставьте вероятности, но измените число положительных на семь.
Что изменится в этой точке и почему одна точка всё ещё не характеризует
ранжирование или качество выбранного порога?

## 4. Цена ошибок и граница development/test

При проверке датчика пропущенная неисправность (FN) может стоить условно 4,
лишняя проверка (FP) — 1. Это **учебные веса**, не универсальная цена. На
четырёх строках при `t=0.5`: `FP=1`, `FN=1`, суммарная стоимость `1+4=5`.
При `t=0.3`: `FP=1`, `FN=0`, стоимость `1`; при `t=0.7`: `FP=1`, `FN=1`,
стоимость `5` (D с `p=0.7` остаётся положительным). Маленький набор легко
переобучить подбором порога; эти числа показывают арифметику, не рекомендуемый
порог. Нормируйте стоимость на количество наблюдений, если размеры наборов
различаются. Если реальная цена зависит от группы или меняется во времени,
простая таблица требует пересмотра.

Протокол: заранее сформулируйте единицу наблюдения, допустимые признаки,
основную метрику и разбиение; **отложите test**. На development data обучайте
модели и преобразования только на соответствующих train строках/фолдах;
там же сравните features, гиперпараметры, варианты калибровки и пороги. При
необходимости выделите отдельную calibration часть внутри development.
Зафиксируйте pipeline, calibrator, правило порога и код отчёта. Один раз
оцените замороженный выбор на test. После просмотра test не подбирайте новый
порог или признаки и не называйте повторный результат независимой финальной
оценкой. Подробная схема разбиения — в [validation](../02_validation/README.md).

Новая [преподавательская демонстрация](../06_reproducibility/README.md#сквозная-преподавательская-демонстрация)
использует отдельные синтетические поездки и датчики: выбор регрессионной
модели по validation MAE; для датчиков — selection Brier, отдельные calibration
строки, выбор raw/calibrated вероятностей и порога по development, затем
замороженный test. В ней один selection набор используется для нескольких
решений — это возможный источник оптимизма внутри development; test нужен
именно как независимая заключительная проверка данного выбора. Она не
заменяет [кросс-валидацию](../04_models/README.md) в иных постановках.

## 5. Ошибки по группам, неопределённость и важность признаков

Сначала выберите группы, имеющие смысл для решения: тип датчика, солнечное/теневое
место или маршрут. Для каждой назовите `n` (*support*), базовую частоту класса,
TP/FP/FN/TN либо MAE и покажите самые характерные ошибочные строки. Общая метрика
может скрыть провал группы, а группа с `n=2` не доказывает стабильного различия.
Если много групп осмотрено после результата, самая крайняя могла появиться случайно;
описательный срез не даёт нового разрешения выбирать модель по test.

Для сравнения двух моделей сохраняйте предсказания **для тех же объектов** и
считайте парные потери. [Парное сравнение](../../03_data_foundations/exercises/paired_model_comparison/README.md)
показывает, как сохранить пары и повторно выбирать независимые единицы, например
целые устройства, а не зависимые строки. [Практическая статистика](../../03_data_foundations/04_practical_statistics/theory.md)
объясняет изменчивость оценки; интервал не исправляет leakage или подбор после
просмотра test.

**Permutation importance**: на разрешённой оценочной части перемешайте один
признак, оставив fitted model неизменной, и измерьте изменение заранее выбранной
метрики. Повторите перестановки; сохраните исходную и изменённую оценки.
Это говорит, насколько **данная модель на данном распределении** опирается на
признак. Коррелированные признаки делят информацию, а перемешивание может
создать невозможные комбинации. Даже большое падение score не доказывает,
что изменение признака причинно изменит цель. До финальной проверки не
используйте test importance для нового выбора признаков.

## 6. Перенос в практику

Сначала письменно предскажите, как смена порога в таблице §2 изменит FP/FN;
пересчитайте. Затем разберите ошибочную интерпретацию: «ROC-AUC высока,
значит вероятность `0.8` соответствует 80% случаев». После этого выполните
[threshold policy](../exercises/threshold_policy/README.md) (`ml-threshold-policy`):
