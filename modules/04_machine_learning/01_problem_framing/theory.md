# Постановка ML-задачи: что мы знаем в момент решения?

[Вход в урок](README.md) · [Следующий урок: validation](../02_validation/theory.md) · [Пример baseline](example.py)

После [основ данных](../../03_data_foundations/README.md) вы умеете различать строку, признак и пропуск. Теперь нужно решить, *какую будущую величину предсказывать и по каким сведениям*. Модель пока не выбираем. Разобранные ниже данные маленькие и учебные; они не подтверждают качество в эксплуатации.

## 1. Вопрос до формулы

Велоклуб хочет до старта оценивать длительность поездки. В его учебном наборе есть `distance_km` (длина), `climb_m` (запланированный набор высоты) и `surface` (покрытие: `paved`/`gravel`). Фактическая длительность `target` в минутах станет известна после финиша.

Прогноз: допустимо ли добавить «среднюю скорость за всю поездку»? Она сильно связана с длительностью. Однако в момент ответа поездка ещё не состоялась. Если такой столбец попал в исторический экспорт, он делает *offline* оценку обманчивой: на будущем входе значения нет.

**Объект наблюдения (observation)** здесь одна поездка. **Признаки (features, `X`)** — доступные до старта свойства этой поездки; одна строка `X` соответствует одному объекту. **Цель (target, label, `y`)** — фактическая длительность в минутах. В обучающих строках известны и `X`, и `y`; у новой поездки есть только `X`. Прогноз числа минут — **регрессия (regression)**. В другом учебном наборе вопрос «потребуется ли обслуживание машины в следующий день?» даёт ответ «да/нет» — **бинарную классификацию (binary classification)**.

Не путайте этот прогноз с причинным выводом. Модель может заметить, что длинные маршруты обычно длятся дольше. Из этого одного наблюдения не следует, что искусственное изменение длины конкретного маршрута на километр *причинно* добавит рассчитанное моделью число минут: люди, рельеф и условия могут измениться вместе с длиной.

## 2. Маленький prediction contract преподавателя

Для второго, сквозного учебного сценария сформулируем контракт до открытия метрик:

| Поле контракта | Решение для машин мастерской |
| --- | --- |
| Единица строки | Одна отдельная учебная машина; повторных строк одной машины в этом наборе нет |
| Момент прогноза | После текущих измерений, до решения об обслуживании |
| Горизонт и `y` | Потребуется ли обслуживание в следующий день: `target` равен `1`/`0` |
| Допустимые `X` | Текущие `vibration_mm_s` и `temperature_c` |
| Запрещённый «полезный» столбец | Гипотетический код выполненного ремонта: появился бы после решения и события; в учебном наборе его нет |
| Проверяемая полезность | В сквозной демонстрации сравнить вероятности по Brier score и решения по стоимости `FP + 4 × FN` на отложенных машинах; цену ошибок здесь задаёт учебное предположение |
| Новые случаи | Другие независимые машины из той же учебной популяции; для повторных замеров или будущих периодов нужен иной [протокол](../02_validation/theory.md). |

В учебном примере цена пропуска обслуживания может быть выше цены лишней проверки, но это предположение нужно согласовать с предметной областью. Нельзя объявить `accuracy` достаточным критерием только потому, что она удобна в коде. Если решение однозначно задаётся устойчивым правилом, например «при официальном аварийном сигнале всегда отправить техника», применяйте правило; ML полезен, когда разрешённые признаки дают дополнительный проверяемый выигрыш относительно такого решения.

Самостоятельно предскажите: если позже добавить пять замеров одной машины, сколько будет строк и сколько уникальных машин? Почему тогда придётся пересмотреть validation?

## 3. Сначала простой baseline

**Baseline** — заранее выбранное простое правило для сравнения на *тех же* отложенных объектах и по *той же* метрике. В ручном примере ниже берём медиану обучающих длительностей и самый частый класс; сквозная демонстрация использует среднюю training длительность и training частоту положительного класса как baseline вероятности. Все эти значения учатся только из training `y`, не из validation или test.

Мини-расчёт для регрессии (минуты):

| Training `y` | Предсказание медианы | Новые истинные `y` | Абсолютные ошибки | MAE |
| --- | ---: | --- | --- | ---: |
| `20, 25, 30` | `25` | `22, 32` | `3, 7` | `(3 + 7) / 2 = 5` минут |

Для классификации training метки `0, 0, 0, 1` дают baseline «всегда 0». На четырёх новых машинах с метками `0, 0, 0, 1` он прав в 3 случаях: accuracy `3/4 = 0.75`, но обнаружил `0/1` нуждающихся в обслуживании: recall положительного класса `0`. Эти числа иллюстрируют механику, не качество какой-либо рабочей системы.

Запустите существующий пример из корня проекта:

```powershell
uv run python modules/04_machine_learning/01_problem_framing/example.py
```

В нём *другая* нейтральная пара задач — посещения парка и полив растений. До запуска предскажите: может ли большинство обеспечить accuracy `0.75` и одновременно recall `0`? В примере training посещения `10, 12, …, 24` дают медиану `17`; ошибки на отложенных `15, 17, 19, 21` равны `2, 0, 2, 4`, поэтому MAE `2` посещения. Ожидаемый словарь: `{'visits_mae': 2.0, 'watering_accuracy': 0.75, 'watering_recall': 0.0}`. Если заменить единственную положительную метку на отложенных строках нулём, accuracy константы станет `1.0`; это ничего не скажет о способности замечать редкие положительные случаи.

**Типичная ошибка:** выбрать метрику и признаки после просмотра удобного результата. Контракт, доступность каждого поля, baseline и цена ошибок фиксируются до сравнения моделей. Отложенная проверка и выбор настроек — предмет [следующего урока](../02_validation/theory.md).

## Проверьте перенос понимания

1. Для маршрута с известной до старта погодой и фактической средней скоростью назовите разрешённое и запрещённое поле. Как проверить момент получения погодного прогноза?
2. Если цель машины — обслуживание в следующий день, почему метка «обслуживание когда-либо» отвечает на другой вопрос?
3. Когда правило «проверять каждый аварийный сигнал» лучше честно оставить без ML?
4. Как изменится baseline регрессии, если сравнивать MSE вместо MAE? Объясните через [ошибки и средние](../../03_data_foundations/04_practical_statistics/theory.md), не подбирая класс sklearn.
5. Может ли `0.75` accuracy большинства быть полезной для решения о выезде? Какие цены ошибок нужны для ответа?
6. Какие два возможных deployment-вопроса скрыты фразой «будущие сенсоры»?

Теперь самостоятельно напишите предусмотренный в [README](README.md#exercises) пятистрочный контракт для **очереди публичной библиотеки**. Сначала предскажите, какой столбец исторического экспорта окажется недоступным в момент ответа; затем проверьте каждое поле на время получения. Не переносите значения из преподавательского контракта без обоснования. После validation и preprocessing примените baseline в [`ml-model-comparison`](../04_models/exercises/model_comparison/README.md), сохранив его собственный контракт сравнения. Диагностируйте ошибку, если baseline «побеждает»: возможно, задача сложна, split отвечает другому вопросу или метрика не совпала с полезностью.
