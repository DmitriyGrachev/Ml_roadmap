# Flush ещё не означает «сохранено навсегда»

## Зачем и что уже нужно знать

В каталоге метки уникальны по имени. Сначала запишем `Atlas`, затем попробуем
одной операцией добавить `Beacon` и повторный `Atlas`, наконец запишем `Cedar`.
Нужно объяснить, почему после ошибки не остаётся половины второй операции
и почему следующая сессия продолжает работать. Нужны
[исключения и контекстные менеджеры](../../01_python_core/06_exceptions_io/README.md)
и представление о таблице, INSERT и UNIQUE.

## Прогноз и интуиция

До запуска выпишите три ожидаемых состояния таблицы после каждой попытки.
Сохранится ли `Beacon`, если его INSERT прошёл раньше конфликтующего `Atlas`?
Автоматически ли выход из `with Session(...)` сохраняет изменения?

Интуиция: транзакция задаёт границу общего результата для группы записей.
Сессия временно связывает Python-объекты и работу с базой. Это не очередь
необратимых записей: SQL может уже выполниться, но общий результат ещё отменяем.

```text
Session создана → add → flush ── успешно ──► commit → close
                        │
                        └── ошибка UNIQUE → rollback → close → ошибка вызывающему
                                                            │
                                   новая Session → новый успешный commit
```

`close` нужен на обеих ветках; он не заменяет успешный commit. Схема показывает
границы Python-кода, а не отдельное сетевое соединение для каждого шага.

## Слова и состояния

**Session** — ORM unit of work, то есть ограниченная область отслеживания
объектов и транзакционной работы. **Engine** управляет способом подключения;
сама конструкция Session ещё не обязана взять физическое соединение.
**Flush** отправляет ожидающие изменения в текущую транзакцию.
**Commit** фиксирует её; **rollback** отменяет, а **close** освобождает ресурсы
сессии. SQLAlchemy допускает повторное использование закрытой сессии при обычной
конфигурации; в уроке каждая операция намеренно создаёт новую.
[SQLAlchemy — Session Basics](https://docs.sqlalchemy.org/en/20/orm/session_basics.html).

| Момент | Python/ORM | База в текущей транзакции | Зафиксировано? |
|---|---|---|---|
| `Label(name="Atlas")` | transient, ещё вне Session | новой строки нет | нет |
| `session.add(...)` | pending, ожидает flush | INSERT ещё не обязателен | нет |
| успешный `flush()` | persistent, ORM знает identity | INSERT выполнен | нет |
| успешный `commit()` | по умолчанию состояние может expire | транзакция завершена | да |
| ошибка и `rollback()` | новая неудачная работа отменена | строки этой операции убраны | прошлые commits остаются |

**Persistent** — термин состояния ORM, не синоним долговечности записи.
**Expire** означает, что при следующем чтении атрибута Session может перечитать
его из БД; это не удаление строки. Наш вывод читает имена отдельным select в
новой сессии, чтобы проверять содержимое базы, а не сохранённый Python-список.

## Разобранная демонстрация

В [walkthrough.py](walkthrough.py) `Label` задаёт таблицу `labels`, числовой
первичный ключ и уникальный name. `create_all()` создаёт пустую учебную схему;
это не миграция существующей базы. `write_batch` — один показанный unit of work,
не реализация student repository:

```python
with Session(engine) as session:
    try:
        session.add_all(Label(name=name) for name in names)
        session.flush()
        session.commit()
    except Exception:
        session.rollback()
        raise
```

В полном файле между шагами добавляется журнал событий. `with` гарантирует
выход из Session на успешном и аварийном пути. Голый `raise` повторно поднимает
исходную ошибку, чтобы вызывающий код не принял отказ за успех. Здесь мы
перехватываем обычные ошибки операции; не скрываем их и не возвращаем None.

Прогноз: если убрать явный flush, где проявится ошибка? `commit()` сам выполняет
flush оставшейся работы. Явный шаг здесь нужен для наблюдения границы, а не для
того, чтобы SQLAlchemy вообще заметил изменения. SELECT тоже может запускать
autoflush, поэтому добавленные объекты не всегда ждут следующего commit.

```powershell
uv run --no-sync python modules/02_python_backend/06_sqlalchemy/walkthrough.py
uv run --no-sync pytest modules/02_python_backend/tests/test_r02_boundaries.py -q
```

Полный stdout:

```text
['Atlas']: open -> pending=1 -> flushed=1 -> commit -> close
persisted: ['Atlas']
rejected: duplicate label
['Beacon', 'Atlas']: open -> pending=2 -> rollback -> close
persisted: ['Atlas']
['Cedar']: open -> pending=1 -> flushed=1 -> commit -> close
persisted: ['Atlas', 'Cedar']
```

Во второй попытке обе новые метки pending. UNIQUE-конфликт возникает во время
flush. Отсутствие `flushed=2` означает, что весь flush не завершился, а не то,
что никакой INSERT не успел выполниться. Откат убирает и возможный INSERT Beacon.
Первый Atlas относится к прошлой уже зафиксированной транзакции, поэтому остаётся.

При неудачном flush SQLAlchemy уже откатывает транзакцию БД, но явный
`session.rollback()` завершает также логическое состояние Session. Иначе
попытка продолжить в ней может дать PendingRollbackError. Урок после ошибки
закрывает эту сессию и открывает следующую, которая успешно фиксирует Cedar.
Тест использует настоящий временный файл SQLite и отдельный connection для
проверки строк — не имитацию SQLAlchemy.

Измените в копии только повторный `Atlas` на `Birch`. Предскажите ветку журнала
и итоговый отсортированный список. Затем подумайте о другом изменении:
вызвать успешный flush, но выйти без commit. Почему строка не должна считаться
зафиксированной, хотя журнал уже содержит flushed?

## Типичная ошибка и границы примера

Ошибка — держать одну глобальную Session и ловить IntegrityError без rollback.
Следующий запрос наследует неуспешное состояние, а время жизни ресурсов становится
непонятным. Другая ошибка — считать context manager аналогом Spring `@Transactional`:
`with Session(engine)` закрывает сессию, но сам по себе не фиксирует запись.
В SQLAlchemy есть отдельный `session.begin()` context, который задаёт commit/
rollback; это другой менеджер с отдельным договором.

Здесь SQLite, один поток и локальная in-memory БД в демо. Тесты используют
временный файл. Проверка не доказывает поведение блокировок, конкурентных
транзакций, изоляции или PostgreSQL типов. Engine также закрывается через
dispose в finally; эта уборка не является commit.

## Проверка понимания

1. Чем pending отличается от persistent, а persistent от committed?
2. Почему SELECT внутри Session может неожиданно отправить INSERT?
3. Если первый INSERT второй операции успел выполниться, почему Beacon исчезает?
4. Почему rollback второй операции не удаляет первый Atlas?
5. Зачем явный rollback после ошибки flush, если БД уже откатилась?
6. Чем `with Session(...)` отличается от `with session.begin()`?
7. Почему проверка базы новой сессией сильнее проверки поля уже созданного объекта?
