# Где заканчивается JSON и начинается обещание модели

## Зачем и что уже нужно знать

HTTP-клиент передаёт JSON, а сервису нужны значения с понятными свойствами.
На печать принимаются положительные количества листов, кратные четырём:
`8` означает два полных пакета. Разберём, кто преобразует строку `"8"` в число,
кто отклоняет `6` и почему клиент видит имя поля в ошибке. Нужны
[аннотации Python](../../01_python_core/04_typing/README.md) и
[первый маршрут FastAPI](../01_fastapi/README.md).

Это маленькое правило одного поля. Здесь нет валюты, времени, денег или готовой
модели Transaction. Сервис хранит принятые количества в памяти, чтобы его
побочный эффект был виден после запроса.

## Сначала прогноз

Для `POST /print-batches` сравните три тела:
`{"quantity": "8"}`, `{"quantity": 6}`, `{"quantity": "oops"}`.
Какие дойдут до сервиса? Будет ли ошибка `6` привязана к всему телу или к quantity?

Интуиция: граница запроса работает как два последовательных вопроса.
«Могу ли я прочитать это как целое число?» и «Разрешено ли такое число?». Это
не две HTTP-попытки: оба этапа входят в обработку одного запроса.

```text
JSON quantity
   │
   ▼
int parsing ── ошибка ──► 422, body.quantity, int_parsing
   │ целое число
   ▼
field rule ─── ошибка ──► 422, body.quantity, value_error
   │ положительное кратное 4
   ▼
route → service.create → 201 + количество пакетов
```

Текстовая версия: неуспех любого из первых двух этапов завершает запрос до
вызова route handler. Схема не означает, что вообще никакие зависимости FastAPI
не выполнялись: отдельная dependency может быть разрешена до вызова маршрута.
Обещание демонстрации — именно отсутствие вызова `PrintService.create`.

## Точный механизм

**Parsing** (разбор/преобразование) создаёт типизированное значение из входа.
В обычном, не strict, режиме Pydantic принимает для `int` подходящую строку.
**Field validator** проверяет или преобразует конкретное поле; `mode="after"`
передаёт нашей функции уже разобранный `int`. **ValidationError** объединяет
ошибки модели, а FastAPI превращает ошибки входного запроса в HTTP 422.
Слово `after` относится к разбору поля, а не к исполнению сервиса.
[Pydantic, field validators](https://docs.pydantic.dev/latest/concepts/validators/#field-validators).

Ключевой фрагмент [walkthrough.py](walkthrough.py):

```python
class PrintBatch(BaseModel):
    quantity: int

    @field_validator("quantity", mode="after")
    @classmethod
    def complete_packs(cls, value: int) -> int:
        if value <= 0 or value % 4 != 0:
            raise ValueError("quantity must be positive and divisible by 4")
        return value
```

`%` — остаток деления. `8 % 4 == 0`, `6 % 4 == 2`. Проверка `value <= 0`
нужна отдельно: ноль и отрицательные кратные тоже дают нулевой остаток.
`@classmethod` передаёт класс первым параметром `cls`; экземпляра готовой
модели ещё нет. `return value` обязателен: его результат становится значением
поля. Нельзя просто проверить и забыть вернуть число.

| Вход | После parsing | Правило поля | Наблюдаемый результат |
|---|---|---|---|
| `"8"` | `8`, тип `int` | проходит | 201, `packs=2` |
| `6` | `6`, тип `int` | остаток 2 | 422, `value_error` |
| `0` | `0`, тип `int` | не положительное | 422, `value_error` |
| `"oops"` | число не получено | after не запускается | 422, `int_parsing` |

Это осознанно допускающий преобразования контракт. Если приложение требует
JSON number и запрещает числовые строки, решается другой вопрос — strict
validation. Не путайте допустимость преобразования с арифметическим правилом.
Сходство с Java DTO полезно для роли границы, но Python-аннотация сама не
выполняет Bean Validation: здесь реальную работу выполняет Pydantic.

## Запуск и полный вывод

Из корня репозитория, с существующим окружением:

```powershell
uv run --no-sync python modules/02_python_backend/02_pydantic/walkthrough.py
uv run --no-sync pytest modules/02_python_backend/tests/test_r02_boundaries.py -q
```

```text
valid: 201 {'quantity': 8, 'packs': 2}
invalid 6: 422 ['body', 'quantity'] value_error
invalid 'oops': 422 ['body', 'quantity'] int_parsing
service accepted: [8]
```

Это проекция настоящего HTTP-ответа: демонстрация выводит status code,
`detail[0].loc` и `detail[0].type`, а не весь JSON ошибки. В нём также есть
сообщение и исходный input. Прямой `PrintBatch.model_validate(...)` даёт loc
`("quantity",)`; HTTP-граница добавляет `"body"`. Имя поля позволяет форме
подсветить конкретный ввод. Тексты сообщений могут зависеть от версии,
поэтому контракт проверяется по месту и виду ошибки.

`service accepted: [8]` — настоящий список принятых значений. Оба отклонённых
запроса не изменили его; тест отдельно начинает со свежего сервиса и убеждается,
что после каждого невалидного запроса список пуст. Валидный ответ проверяется
полностью, включая JSON-число 8, а не строку.

В копии демо замените только `6` на `12`. До запуска назовите статус, число
пакетов и финальный список сервиса. Затем замените только `"oops"` на `"0"`:
почему место ошибки сохранится, но `int_parsing` сменится на `value_error`?

## Типичная ошибка

Проверить количество внутри сервиса и вернуть `None` при нарушении — значит
смешать ошибку входа с успешным ответом и потерять сведения о поле. Другая
ошибка — вынести независимое правило quantity в model validator, а потом
ожидать field-specific loc. **Model validator** нужен, когда правило относится
к сочетанию полей, например «начало раньше конца»; его ошибка обычно относится
к модели целиком. Наличие `int` не обещает ни положительность, ни кратность.

## Проверка понимания

1. Какой тип видит complete_packs при входе `"12"`?
2. Почему проверка только остатка допустила бы `0` и `-4`?
3. Как отличить parsing error от нарушения правила при одинаковом loc?
4. Что произойдёт, если забыть `return value` в валидаторе?
5. Почему loc модели и loc HTTP-ответа различаются первым элементом?
6. Где проверять правило, сравнивающее два поля, и как изменится смысл loc?

## Перенос в практику

Независимая вариация: контракт `Reading(temperature: float)` для датчика с
допустимым диапазоном от −40 до +85 включительно. Решите, разрешены ли строки,
NaN и бесконечности. Выпишите прогнозы для границ и одного значения за каждой
границей; только потом напишите модель и HTTP-пробу. Здесь нет кратности или
пакетов, поэтому объяснение нужно перенести, а не скопировать арифметику.

Затем [backend-transaction-contract](exercises/transaction_contract/README.md):
правила независимых полей должны сохранить свои места в 422. Понадобятся также
Decimal и работа с datetime; читайте контракт каждого поля. Полная модель,
нормализация и JSON Schema остаются вашей самостоятельной работой.
