# Правильные строки сначала, план и время потом

## Зачем и что уже нужно знать

Индекс меняет способ поиска строк. До обсуждения ускорения нужно убедиться,
что запрос возвращает правильные значения в нужном порядке. Здесь посылки
`parcels(parcel_id INTEGER PRIMARY KEY, zone TEXT, weight INTEGER)` и простой
поиск зоны, а не готовое решение events/support. Нужны WHERE, ORDER BY и
[основной контракт analytics SQL](README.md); сначала разберитесь с его
cardinality и tie-break, затем возвращайтесь к измерению.

## Ситуация и прогноз

В таблице 20 000 посылок, 1 000 зон. Нужны двадцать посылок зоны `Z017`.
Как найти их без дополнительной структуры? Если читать каждую строку и
проверять zone, ответ получится, но придётся просмотреть всю таблицу.
Что должно измениться после индекса: значения результата, порядок или путь
доступа? До запуска предскажите число строк.

Интуиция: индекс похож на отсортированный указатель «зона → места строк».
Указатель не заменяет данные посылки и требует собственной памяти. Это образ
для поиска, а не обещание постоянного времени или бесплатного обновления.

```text
Без индекса: таблица 20000 строк → проверить zone каждой → 20 совпадений
С индексом:  найти Z017 в индексе → 20 rowid → прочитать weight в таблице
                                               │
                         один ORDER BY parcel_id → те же 20 упорядоченных строк
```

Текстовая альтернатива: scan читает все строки; lookup использует диапазон
ключей зоны и получает значения остальных колонок из таблицы. Схема относится
к этому простому запросу, не к оконным функциям и нескольким join.

## План — описание работы, не секундомер

**Query plan** — выбранный СУБД путь исполнения. SQLite `EXPLAIN QUERY PLAN`
возвращает дерево операций с колонкой detail. В локальном демо без индекса
получился `SCAN parcels`, после индекса — `SEARCH ... (zone=?)`.
SCAN вообще может читать и индекс целиком; слово само по себе не доказывает
отсутствие любого индекса. SEARCH обозначает выбор подмножества.
Текст/форма плана могут меняться с версиями, их не следует превращать в
неизменный acceptance contract.
[SQLite — EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html).

Основной запрос [plan_demo.py](plan_demo.py):

```sql
SELECT parcel_id, weight
FROM parcels
WHERE zone = ?
ORDER BY parcel_id;
```

`?` — параметр: zone передаётся отдельно от SQL. `ORDER BY` — явная часть
контракта порядка. Нельзя выводить обязательный порядок только из того, что
сейчас SQLite вернул строки в удобной последовательности.

Добавляется ровно один индекс:

```sql
CREATE INDEX idx_parcels_zone ON parcels(zone);
```

Здесь `INTEGER PRIMARY KEY` соответствует SQLite rowid. В обычном индексе
zone одинаковые ключи дополнительно упорядочены rowid. Поэтому этот конкретный
поиск зоны может дать нужный порядок parcel_id без отдельной сортировки.
Индекс не covering для weight: за ним ещё нужно обратиться в таблицу.
[SQLite — Query Planning](https://www.sqlite.org/queryplanner.html).

| Свойство | Что проверяем | Чего это не доказывает |
|---|---|---|
| Корректность | точные строки и порядок до/после | правильность любого другого запроса |
| План | SCAN или SEARCH, имя индекса | сколько миллисекунд займёт запрос |
| Время | несколько полных fetchall, все samples | универсальный коэффициент ускорения |
| Цена индекса | дополнительные страницы базы | точное число байтов Python RAM или цена каждого INSERT |

## Как устроен эксперимент

Данные задаются формулами для `parcel_id` от 0 до 19999 включительно:
`zone = Z + (parcel_id % 1000)` с тремя цифрами, `weight = parcel_id % 10`.
Для Z017 это ID 17, 1017, …, 19017, у всех weight 7. Ручная проверка первых
двух строк: `17 % 1000 = 17`, `1017 % 1000 = 17`, оба остатка по 10 равны 7.
Поэтому число совпадений — 20, порядок задаёт ID по возрастанию.

Каждая фаза сначала получает эталонный список и прогревает запрос, затем
семь раз измеряет полный `execute(...).fetchall()` через `perf_counter`.
Замер включает чтение результата в Python, но не заполнение таблицы, создание
индекса или EXPLAIN. Каждая выборка сравнивается с первой выборкой своей фазы,
а обе фазы сравниваются друг с другом. Авторский тест дополнительно проверяет
набор 3 000 строк по независимому литералу: `(17, 7), (1017, 7), (2017, 7)`.
Равенство двух неправильных списков не заменяет такую проверку ожидаемого ответа.

Прогноз: что произойдёт для отсутствующей Z999 при размере таблицы 30? Ответ
будет пустым и до, и после индекса; пустой результат тоже часть контракта.

Медиана — среднее по порядку наблюдение после сортировки семи длительностей,
а не среднее арифметическое и не «самый быстрый результат». В этом запуске
индекс помог. Иная избирательность (**selectivity**, доля совпадающих строк),
размер, cache, версия SQLite и нагрузка способны изменить план и время.
Это in-memory база и тёплые запросы; здесь нет измерения холодного диска,
сетевой задержки или конкуренции. Порядок фаз фиксирован: before затем after.
Строгий performance benchmark потребовал бы контроля порядка и дополнительных
повторов; тест намеренно не задаёт порог скорости.

## У индекса есть цена

В пустом от других изменений эксперименте разность PRAGMA page_count до/после
индекса составила 60 страниц; page_size — 4096 байт, то есть 245 760 байт
дополнительного размещения SQLite. Это не прямое измерение RSS процесса и не
размер файла: база находится в памяти. На иных данных разность может отличаться.

INSERT, DELETE и UPDATE zone теперь требуют поддерживать также индекс.
Создание индекса тоже занимает время; ни оно, ни write overhead в timings выше
не включены. Запрос, выбирающий почти все строки, может не окупить дополнительные
lookup; больше индексов не означает автоматически более быстрый продукт.

Типичная ошибка: увидеть слово INDEX и объявить задачу решённой. Сначала
докажите правильность строк, потом объясните план, затем измерьте конкретную
нагрузку и цену. Другая ошибка — убрать ORDER BY ради красивого времени, а
после сравнивать только множества строк. Так теряется требуемый порядок.

## Проверка понимания

1. Почему равенства before/after недостаточно без независимого ожидаемого ответа?
2. Чем SCAN отличается от SEARCH и может ли SCAN использовать индекс?
3. Почему weight требует обращения в таблицу после поиска zone?
4. Что именно включено в один timing и что исключено?
5. Почему нельзя фиксировать требование «индекс обязан ускорить минимум в N раз»?
6. Что измеряет разность page_count и чего она не измеряет?
7. Какие операции записи стали дороже и почему?

## Независимая вариация и перенос

После своего корректного analytics_query сохраните результат на неизменной
копии данных, прочитайте его EXPLAIN QUERY PLAN и обоснуйте один кандидат
индекса для своего запроса. Добавьте индекс только в отдельной экспериментальной
копии базы, сравните точные упорядоченные строки и повторные измерения.
Отдельно увеличьте долю подходящих событий: как изменится полезность индекса?
Не меняйте fixture и acceptance tests ради желаемого плана.

Это самостоятельная защита понимания, не новая автоматическая проверка ID
`backend-analytics-sql`. Student query, cardinality, оконный tie-break и выбор
индекса остаются вашей работой; parcel demo не решает ни один из этих этапов.

PostgreSQL здесь **NOT_RUN**. Обсуждение `EXPLAIN (ANALYZE, BUFFERS)` не означает,
что PostgreSQL-запрос выполнялся. ANALYZE у PostgreSQL действительно исполняет
запрос; используйте подготовленную среду и отдельно проверяйте семантику/план,
не переносите строки SQLite EXPLAIN как обещание для другого движка.

## Источники и остановка

Официальные английские страницы проверены через web 2026-10-11:

- [SQLite — EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html):
  начало и Table and Index Scans; остановиться до сложных compound queries.
- [SQLite — Query Planning](https://www.sqlite.org/queryplanner.html):
  Lookup By Index, Covering Indexes и Sorting; схемы объясняют лишний lookup.
- [SQLite — PRAGMA page_count](https://www.sqlite.org/pragma.html#pragma_page_count)
  и [page_size](https://www.sqlite.org/pragma.html#pragma_page_size): единицы
  измерения размера, не время выполнения.
- [PostgreSQL — Using EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html):
  только значение ANALYZE и BUFFERS для последующего опционального эксперимента.

Локальный SQLite запуск и авторские тесты выполнены; PostgreSQL, холодный диск,
стоимость записи и производственная нагрузка не проверялись. Progress не меняется.
