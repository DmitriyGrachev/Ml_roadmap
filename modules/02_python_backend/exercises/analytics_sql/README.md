## Схема и требуемый результат

Таблица `events(event_id INTEGER PRIMARY KEY, user_id TEXT, event_type TEXT,
occurred_at TEXT)` хранит события; время — UTC ISO-8601 строка в форме
`YYYY-MM-DDTHH:MM:SSZ`. Таблица `support_tickets(ticket_id INTEGER PRIMARY KEY,
user_id TEXT, status TEXT)` хранит обращения. Все поля кроме первичных ключей
обязательны. Связь по `user_id` не уникальна: у пользователя может быть несколько
событий и несколько обращений. У обращения может не быть события, а у пользователя
с событием может не быть обращения.

Рассмотрите срез `2026-09-01T00:00:00Z <= occurred_at <
2026-09-08T00:00:00Z`. Среди событий **каждого пользователя в срезе** выберите
одно последнее: сначала по `occurred_at` по убыванию, при равенстве по `event_id`
по убыванию. Используйте оконную функцию для выбора. Затем сгруппируйте пользователей
по `event_type` выбранного события. Верните строки с колонками в точном порядке:
`event_type`, `user_count`, `ticket_count`, `users_without_tickets`. Последняя
колонка считает пользователей без обращений. `ticket_count` считает все обращения
этих пользователей независимо от `status`. Сохраните пользователей без обращений
через left join; чужие обращения не добавляются. Строки отсортируйте по
`event_type` по возрастанию.

Тест исполняет возвращённый запрос на временной базе и сравнивает результатные
строки, в том числе после изменения данных. В fixture есть равное время разных
событий, дубликаты ключа в обращениях, отсутствующие стороны join и событие на
исключённой верхней границе среза. Никакого сравнения точного текста SQL нет.

## Запуск и защита

```powershell
uv run --no-sync python scripts/learn.py test backend-analytics-sql
uv run --no-sync python scripts/learn.py check backend-analytics-sql
```

`test` допускает xfail только от TODO; `check` требует выполненный запрос.
Unit проверяет устройство fixture, локальный SQLite smoke исполняет SQL и сверяет
строки. ML evaluation здесь нет. Реальное выполнение PostgreSQL — `NOT_RUN` без
подготовленной среды; при желании обсудите отличия синтаксиса и план запроса,
не выдавая обсуждение за выполненный тест. Защита остаётся `REQUIRES_REVIEW`:
используйте общий [шаблон](../../../../docs/project-defense.md), объясните новую
вариацию данных, tie-break и cardinality на каждом этапе.

## Подсказки по этапам

1. Определите единицу каждой промежуточной таблицы до соединения: событие,
   пользователь или обращение.
2. Проверьте, что равный timestamp даёт единственный устойчивый выбор.
3. После left join пересчитайте вручную пользователей с нулём и несколькими
   обращениями; затем сверяйте агрегат по `event_type`.
