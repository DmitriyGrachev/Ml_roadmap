# Миграция схемы — изменение договора с существующими данными

Предпосылки: SQL DDL/DML, ограничения `NOT NULL`/`CHECK`, транзакции,
SQLAlchemy engine, тесты с временными файлами. Java/Spring-аналог — версионируемые
миграции Flyway/Liquibase, но здесь мы используем Alembic и проверяем реальные
revision-файлы, а не только ORM metadata. `Base.metadata.create_all()` создаёт
недостающие таблицы; он не является историей последовательных изменений схемы.

## История и состояние

У revision есть `revision`, `down_revision`, `upgrade()` и `downgrade()`.
`alembic_version` хранит текущую позицию в графе истории. В нашем линейном примере
`0001` создаёт таблицу, `0002` добавляет производный признак. `upgrade head`
применяет отсутствующие изменения. Повторный вызов на том же head не должен снова
создавать колонку или дублировать данные. Это идемпотентность **перехода по истории**,
а не обещание, что тело произвольной migration-функции безопасно выполнить дважды.
`stamp` меняет отметку истории без выполнения DDL — использовать его вместо
upgrade, чтобы получить зелёную проверку, значит скрыть несоответствие схемы.

Autogenerate даёт черновик изменения metadata, но не выводит бизнес-смысл backfill.
Переименование колонки может выглядеть как drop/add. Человек обязан решить,
как преобразовать старые строки, что делать с нарушениями инвариантов, допустим
ли простой и как восстановиться после ошибки.

## Разобранный пример на заполненной базе

В [0001_prediction_jobs.py](demo_migrations/versions/0001_prediction_jobs.py)
таблица содержит `id`, `model_name`, `latency_millis`. Все три поля уже могут
использоваться приложением. Нужно добавить `latency_seconds`, не потеряв старые
измерения. [0002_latency_seconds.py](demo_migrations/versions/0002_latency_seconds.py)
выполняет последовательность:

1. До DDL проверяет старые строки: отрицательное или отсутствующее latency нельзя
   молча преобразовать в нормальную статистику. Нужно остановиться и исправить
   источник/данные по отдельному решению владельца.
2. Добавляет nullable-колонку, чтобы существующие строки оставались допустимыми.
3. Заполняет `latency_seconds = latency_millis / 1000.0`. Знаменатель явно дробный,
   поэтому сохраняется часть секунды; 1250 превращается в 1.25, 999 — в 0.999.
4. После backfill устанавливает `NOT NULL` и именованный `CHECK >= 0`.

Это маленькая учебная миграция, поэтому стадии объединены в один revision.
Для большого online-сервиса такой переход часто разбивают на несколько релизов:
expand schema; развернуть совместимые dual writers; backfill порциями с контрольной
точкой; проверить полноту; переключить readers; усилить ограничения; позже удалить
устаревшее поле. Если сразу сделать новое поле обязательным, старый writer,
который его не передаёт, начнёт получать ошибку. В примере после `0002` новый writer
обязан передавать оба значения. Совпадение двух производных полей при последующих
UPDATE не обеспечивается одним `CHECK`: нужен договор приложения, generated column
или другая явно выбранная схема. Наличие колонки не поддерживает её актуальность.

## Транзакции и восстановление

Важная граница raw `sqlite3`: `with connection` делает commit или rollback,
но **не закрывает соединение**. Поэтому demo и тесты используют внешний
`contextlib.closing(sqlite3.connect(...))` и внутренний транзакционный контекст
`connection`: сначала заканчивается транзакция, затем закрывается handle,
и только после этого удаляется временная директория. Это существенно для Windows,
где открытый файл БД может помешать удалению. Сборка мусора не заменяет владельца ресурса.

Контекст `connection.begin()` задаёт намерение атомарности, но реальное поведение
DDL зависит от СУБД и драйвера. В SQLite legacy transaction mode драйвера может
не начинать транзакцию перед DDL так, как ожидает новичок. Поэтому
[env.py](demo_migrations/env.py) явно отключает автоматическое управление драйвера
и отправляет `BEGIN` при начале SQLAlchemy-транзакции. Проверка не должна делать
вывод «SQLite == PostgreSQL». `batch_alter_table` на SQLite умеет пересоздать
таблицу, перенести строки и заменить старую; это требует места, блокировок и
аккуратности с индексами и ограничениями. Именованные constraints проще удалить
и сохранить предсказуемо. Новые реальные схемы требуют тестов и для внешних ключей,
triggers, views и собственных индексов.

В тесте намеренно создаётся legacy-строка с отрицательным значением через
отключение CHECK только для фикстуры. Upgrade должен упасть **до** изменения схемы:
строка сохранена, revision остался `0001`, новой колонки нет. После исправления
строки повторный upgrade проходит. Это проверка отказа и возобновления. Второй failure-тест сначала выполняет
реальный `ADD COLUMN`, затем намеренно выбрасывает ошибку: явная транзакция
откатывает колонку, данные и revision остаются прежними, повторная попытка проходит.
Эта SQLite-проверка не доказывает поведение PostgreSQL при потере соединения
посреди DDL: там нужен отдельный fault-injection эксперимент с production-драйвером.

Если миграция использует несколько транзакций ради уменьшения блокировки,
частичный результат становится возможным по замыслу. Тогда нужны возобновляемые
порции, отдельный признак прогресса, проверка диапазонов и способ отличить
«не обработано» от настоящего нулевого значения. Большой backfill нельзя объявить
безопасным только потому, что маленькая таблица теста обработалась за миллисекунды.

## Downgrade и данные

Наш downgrade удаляет только производную `latency_seconds`; исходные milliseconds,
ID, названия и новые добавленные строки сохраняются. Повторный upgrade снова
вычисляет секунды. Это возможно, потому что исходная величина осталась в таблице.
Если upgrade округлил, удалил данные или объединил строки, универсального обратного
преобразования может не существовать. «Написан downgrade» не означает «восстановим
любые данные». Backup/restore, rollback приложения и downgrade схемы — три разных
операции с разными ограничениями. Перед опасным изменением проверяют восстановление
на копии, а не наличие файла backup как такового.

## SQLite как быстрый контракт и PostgreSQL как отдельное доказательство

SQLite-тесты запускаются локально без сервера и проверяют наш переход на конкретных
строках. PostgreSQL-маршрут использует те же author revisions через URL
`postgresql+psycopg://...` и уже имеющийся драйвер psycopg. Он запускается только
на отдельной учебной БД явной командой. PostgreSQL обладает другими блокировками,
типами, поведением конкурентных writers и DDL; успешный SQLite-тест не даёт за этот
маршрут автоматический зачёт. Команды и статус исполнения приведены в README.

Alembic — optional dependency group `migrations`. Без неё tests явно `skip`,
а строгий `roadmap_tools.cli check` помечает проверку незавершённой. Нельзя удалять
skip-тесты из catalog или считать отсутствие сервера/зависимости доказательством
компетенции. Сначала установите группу, затем получите реальные pass; PostgreSQL
остаётся отдельно отмеченным необязательным экспериментом.
