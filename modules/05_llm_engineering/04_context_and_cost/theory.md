# 04. Весь запрос должен поместиться вместе с ответом

Практический вопрос: почему нельзя взять все доступные страницы справочника и попросить модель «ответить коротко»? Прочитайте [построение запроса](../02_prompt_contracts/theory.md) и [существующий пример цены](example.py).

Интуиция: контекстное окно — общий ресурс для сериализованного входа и будущего вывода. **Output reserve** оставляют до выбора фрагментов. Если вход занял всё окно, модель не сможет закончить ответ; автоматическое обрезание может убрать решающее отрицание `not` из правила о ночном хранении.

Разобранный пример из `walkthrough.py` использует **вымышленные единицы учёта**. Они намеренно не объявлены токенами конкретного tokenizer:

| Составная часть | Условные единицы |
| --- | ---: |
| Chat framing и служебные маркеры | 15 |
| Инструкция и формат | 20 |
| Вопрос | 10 |
| Контекст `G-01` вместе с ID/версией | 35 |
| Схема tool (в этом запросе операций нет) | 0 |
| **Итого вход** | **80** |
| Резерв вывода | 20 |
| **Общий учебный лимит** | **100** |

`15+20+10+35+0=80`, `80+20=100`, остаток ноль. Поля состава находятся в `trace.json`; отсутствие tool вызова обозначено нулём, а не скрытой схемой. При лимите 99 отдельная функция `account_budget` отвергает такую конфигурацию; реальный adapter должен поставить эту проверку перед вызовом. На практике число токенов зависит от конкретных tokenizer и chat template; слова и символы не равны токенам. Для точного учёта нужен tokenizer/формат выбранной модели либо usage конкретного API. При грубой оценке оставляют дополнительный запас. Кроме общего окна могут действовать отдельные пределы input и output.

**Prompt engineering** здесь определяет, как использовать `G-01`; **context engineering** решает, попадёт ли актуальная и разрешённая запись вообще в запрос. Если длинная страница вытеснила отрицание, новая формулировка prompt не вернёт пропущенное доказательство. В [самостоятельном budget exercise](exercises/context_budget/README.md) нужно решить выбор целых документов собственным счётчиком; этот walkthrough не реализует его алгоритм. Отдельное [context packing](../exercises/context_packing/README.md) сохраняет свой приоритетный контракт.

Для стоимости [старый пример](example.py) использует **фиксированные учебные ставки**, 2 условные денежные единицы за миллион входных и 8 за миллион выходных токенов. При **заданных**, не измеренных, 1200 и 300 токенах: `(1200×2 + 300×8)/1 000 000 = 0.0048` единицы. Это не текущая цена поставщика. Повторные попытки добавляют использование; cached input, другие модальности и тарифы могут считаться иначе. Из вымышленного бюджета 100 выше реальную стоимость вывести нельзя.

Типичная ошибка — считать `len(text)` количеством токенов или суммировать отдельно tokenized строки, забыв маркеры ролей. Самостоятельная вариация: контекст вырос с 35 до 42 условных единиц. Каков новый итог, при каком шаге запрос должен остановиться и какие сведения нельзя молча обрезать? Ограничение: наша арифметика проверяет только распределение заданных единиц, не реальный биллинг и не качество выбранных фрагментов.

## Источники и практика

- Hugging Face, [Chat templates: `apply_chat_template`](https://huggingface.co/docs/transformers/v5.17.0/chat_templating#using-apply_chat_template), англ.: увидеть специальные маркеры и токенизацию всего сообщения.
- Hugging Face, [GenerationConfig: `max_new_tokens`](https://huggingface.co/docs/transformers/v5.17.0/en/main_classes/text_generation#transformers.GenerationConfig), англ.: предел нового текста в конкретном API.
- Python 3.12, [decimal arithmetic](https://docs.python.org/3.12/library/decimal.html), англ.: точная десятичная арифметика фиксированных ставок; остановитесь после вводного объяснения.

Практика: ID `llm-context-budget` и `llm-context-packing`. Сначала вручную предскажите, какой разрешённый фрагмент останется при уменьшении лимита, затем проверьте контракт своих реализаций. Не используйте teacher fixture как tokenizer.
