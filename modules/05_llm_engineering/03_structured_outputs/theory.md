# 03. Пять ворот между completion и действием

Практический вопрос: если модель вернула валидный JSON `{"status":"available"}`, можно ли сообщить клиенту, что велосипед допустимо оставить на ночь? Нет: форма и содержание проверяются раздельно. Перед этим уроком прочитайте [контракт запроса](../02_prompt_contracts/theory.md) и [пример каталога](example.py).

Интуиция: **structured output** облегчает разбор, но JSON не является доказательством истинности. У приложения есть пять разных вопросов: (1) получен ли технически законченный ответ, (2) соответствует ли он schema, (3) допустимы ли сочетания значений, (4) подтверждается ли утверждение доступными данными, (5) разрешено ли пользователю предложенное действие. Для защищённого контекста проверка прав происходит ещё **до** вызова модели.

В teacher trace готовый `success` содержит `status=unavailable`, `next_step=none`, `evidence_id=G-01`, `evidence_quote=Overnight storage is not offered.`. Сначала `finish_reason=stop` и непустой текст; затем Pydantic проверяет четыре поля, строгие литералы и отсутствие лишних полей; затем правило `unavailable → none`; затем **узкая** проверка для этого одного вопроса и фиксированного `G-01` сверяет ID и цитату с конкретной известной фразой. Только после этого приложение разрешает `display_answer_only`; никаких внешних операций нет.

| Подготовленный completion | Первые ворота отказа | Что разрешено дальше |
| --- | --- | --- |
| `unavailable / none / G-01 / точная цитата` | все пройдены | показать ответ |
| `unavailable / visit / G-01 / точная цитата` | смысл: шаг противоречит статусу | показать недоступность результата |
| `available / visit / G-01 / Pickup by 19:00.` | опора: цитата есть, но ночное хранение не подтверждает | показать недоступность результата |
| `{broken` | schema/JSON | показать недоступность результата |
| пустая строка при `stop` | техническая полнота | показать недоступность результата |
| отказ или `length` | техническая полнота | отказ либо новая ограниченная попытка |

Это также контрпример «schema-valid, unsupported»: `available/visit` проходит типы и совместимость значений; существование `G-01` и подстроки `Pickup by 19:00.` не подтверждает доступность ночного хранения. Наша проверка намеренно source-specific и deterministic. Она не решает задачу общего **entailment** и не переносится на произвольные документы. Для открытых утверждений требуются эталон, человеческая проверка или оценщик с собственными ограничениями.

У разных API constrained JSON, tool calling и потоковые дельты имеют разные гарантии и поля. Даже если поставщик ограничивает формат во время генерации, приложение должно обработать отказ, обрезание, несовместимую схему и ложный факт. Не «чините» произвольный текст удалением Markdown-обёртки до тех пор, пока он распарсится: это меняет политику приёма.

Самостоятельная вариация: completion цитирует верное предложение, но присваивает `status=available`. На каких воротах он остановится и почему наличие цитаты ещё не означает доказательство? Ограничение: пример описывает один известный policy fact, а не универсальный фактчекинг.

## Источники и практика

- Pydantic, [Strict mode](https://pydantic.dev/docs/validation/latest/concepts/strict_mode/), англ.: чем строгая проверка отличается от преобразования типов; смотрите разделы про `model_validate_json` и JSON input.
- Pydantic, [JSON parsing](https://pydantic.dev/docs/validation/latest/concepts/json/), англ.: граница JSON parsing и модели; остановитесь до оптимизаций.
