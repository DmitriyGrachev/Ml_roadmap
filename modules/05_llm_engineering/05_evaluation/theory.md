# 05. Ответ, задержка и цена измеряются отдельно

Практический вопрос: после успешного `trace.json` можно ли выпускать функцию ответа о правилах мастерской? Нет: трасса показывает один контролируемый контракт, а не частоту правильных ответов реальной модели. До этого прочитайте [пять ворот](../03_structured_outputs/theory.md) и [старый пример выбора вариантов](example.py).

Интуиция: **quality**, **latency** и **cost** — разные оси. Качественный ответ может быть слишком медленным; дешёвый — ошибаться именно на отказах. Для оценки нужны заранее определённые критерии и данные, которые не использовались при настройке prompt.

Маленький пример на `G-01`: эталон для вопроса о ночи — «хранение недоступно». Готовый `success` верен в этом узком случае; `unsupported` ошибочно говорит `available`, хотя содержит существующий citation ID и реальную цитату о времени выдачи. Проверка существования ID устанавливает только происхождение записи, не поддержку утверждения. Другие случаи: нет ответа в справочнике → корректное воздержание; отказ модели на обычный вопрос → недостающий ответ; отказ при запрещённом контексте → проверка доступа прежде модели. Для каждого случая отмечают отдельно корректность по проверяемому эталону, подтверждение каждого существенного утверждения, корректность ссылок, полноту и полезность.

Точный протокол: версия задачи/источника/prompt/model, раздельные development и held-out случаи, одинаковые вопросы для сравниваемых вариантов, заранее выбранные рубрики. Не подбирайте prompt по финальному набору. Сравнивайте answerable и refusal-required срезы: система, которая отказывает всем, может показать идеальную долю корректных отказов и нулевую полезность. Для открытых текстов возможны человеческая рубрика и **LLM-as-judge**, но judge ошибается, зависит от собственного prompt и может предпочитать стиль смыслу. Его оценка не становится независимой истиной; спорные результаты проверяет человек или внешний проверяемый факт.

В [старом `example.py`](example.py) три **вымышленных** summary сравниваются с порогами качества, p95 задержки и стоимости. Это демонстрация политики принятия решения, не замер live API. Например, `120 ms` в примере — заданное число; в этой части не измеряли latency. Для реального протокола фиксируют число запросов, p50/p95 и ошибки/таймауты, стоимость по usage и действующим ставкам, повторяют прогоны при вариации модели. Нельзя смешивать симулированную задержку с измеренной.

| Наблюдение | Возможный этап ошибки | Различающая проверка |
| --- | --- | --- |
| JSON оборван | лимит вывода или stream/transport | termination reason, собранные дельты, резерв |
| Поле правильное, факт ложен | контекст или генерация | был ли нужный источник в запросе; поддерживает ли цитата факт |
| Отказ на обычный вопрос | prompt/модель/политика | тот же доступный источник, версия prompt, доля ложных отказов |
| Ответ ссылается на старую версию | отбор контекста | версия и дата `G-01`, обновление индекса позже в RAG |
| Показан защищённый текст | access/context selection | журнал разрешений до вызова модели; не логировать сам секрет |

Типичная ошибка — принять прохождение unit tests за измерение качества. Самостоятельная вариация: вариант улучшил полноту на development, но на held-out начал выдумывать работу после 19:00. Как изменится решение о выпуске, если p95 и стоимость остались прежними? Ограничение: в этом пакете нет вызова модели и нет статистической оценки качества; понимание ученика проверяется отдельно.
