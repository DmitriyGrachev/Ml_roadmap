# 04. Сохранить состояние, возобновить точную работу

Практическая проблема: `waiting` остановился перед человеком. Через минуту другой процесс видит сохранённый JSON. Что ему нужно знать, чтобы продолжить без повторного предложения и без подмены действия? Сначала предскажите: даст ли старое подтверждение право на `pickup_at=18:00`, если изначально было `19:00`?

Интуиция: checkpoint — снимок **структурированного workflow state**, а не вся память ассистента. История сообщений — последовательность реплик; per-call model context — выбранный для *одного* вызова модели фрагмент инструкций/источников/истории; workflow state — проверенные поля статуса, бюджета и pending call; checkpoint — сериализованный снимок этого состояния; long-term store — отдельное долговременное хранилище данных между запросами. Переполнить checkpoint полной перепиской или скрытыми рассуждениями модели значит увеличить риск раскрытия и неоднозначного восстановления. В учебном JSON нет chain of thought, токенов, секретов и чувствительного текста.

[`walkthrough.py`](../walkthrough.py) сохраняет `checkpoint.json` для `waiting`: `schema_version=1`, `run_id`, `version=1`, `call_id`, `pickup_at`, `approval_target`, status, счётчики `steps/attempts/elapsed_ms`, лимиты, receipt, локальный `effects` и краткие события. При возобновлении приложение передаёт **независимый** `RunPolicy(max_steps, max_attempts, deadline_ms)` из своей конфигурации: `resolve_reminder(checkpoint, decision, approval, policy=..., can_remind=...)` сверяет его с JSON до любого действия. Иначе изменение `max_attempts: 1 → 2` внутри файла дало бы лишнюю попытку. Затем проверяются поля, версия, счётчики, последний event, инварианты эффекта/receipt и exact target. Восстановление читает сериализованное состояние, а не создаёт заново «успешный» сценарий. JSON — учебный artifact доверенного происхождения; нет подписи, шифрования, аутентификации, конкурентного durable store или внешнего восстановления после crash.

Точная цель подтверждения задаётся существующим [`approval_digest`](example.py): run ID + версия + tool + аргументы, в которых здесь включён call ID. При `changed_args` время `18:00` само по себе допустимо, но digest от `19:00` больше не подходит: `approval_mismatch`, attempts 0, effects 0. Отказ `refuse` и отмена `cancel` также не делают вызова. Для новой операции нужно новое предложение и отдельное подтверждение. Текущее право повторно проверяется непосредственно у симулированного эффекта: отозванное право останавливает даже ранее подготовленный вызов.

После `success` checkpoint содержит receipt `call-1`. `known_replay` перечитывает именно этот checkpoint и не увеличивает ни `attempts`, ни `effects`: 1 и 1. Это лишь локальная защита от повторной обработки **известного результата**. В `unknown_after_effect` действие в имитации произошло, но receipt отсутствует; состояние сохраняет `unknown_needs_reconciliation`, повторный resolve ничего не делает. Если настоящий удалённый сервис совершил эффект, а процесс погиб до durable receipt, простой checkpoint не докажет исход. Без транзакции/идемпотентности получателя невозможно обещать exactly-once. Конкурентное обновление реального store потребовало бы compare-and-swap или транзакции.

Типичная ошибка — сохранять `approved: true` без привязки к run/version/call/tool/args, затем восстанавливать и запускать что угодно. Другая ошибка — брать *и счётчики, и их пределы* только из одного изменяемого JSON. В учебном вызове policy и право поступают из приложения; если приложение построит их из того же JSON или пользовательского текста, независимой проверки нет. Проверка структуры здесь предотвращает ряд невалидных переходов, но **не аутентифицирует** происхождение файла. Hash target не удостоверяет личность человека. Реальная проверка подтверждения живёт в доверенном приложении.

Практика: [checkpoint/resume](exercises/checkpoint_resume/README.md), ID `agents-checkpoint-resume`, оставляет ученику контракт exact replay и version conflict. Самостоятельная вариация: после подтверждения изменились аргументы; опишите минимальное состояние нового запроса и кто должен разрешить его. Ещё одна: пользователь отменил задачу после сохранения `waiting`; какие данные нужно сохранить и какая ветка не должна выполняться?

Самопроверка: чем checkpoint отличается от long-term store? Почему надо сохранить budgets? Что значит receipt и где его предел? Почему `can_remind` нельзя брать из текста модели? Можно ли по одному digest доказать одобрение человеком? Почему завершившийся шаг может быть повторно исполнен после crash?

Источники: LangChain, [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence), англ., хранение graph state; [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts), англ., возобновление и повторное выполнение узла. Изучите эти границы, не считайте локальный JSON реализацией durable checkpointer.
