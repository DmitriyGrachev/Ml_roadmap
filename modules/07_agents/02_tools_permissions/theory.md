# 02. Предложение инструмента и право на действие

Практическая проблема: модель или иной автор предложения увидел `G-01` и предлагает `simulate_pickup_reminder(call-1, pickup_at=19:00)`. В этом уроке предложение заранее записано в teacher walkthrough; настоящий model output не используется. Предскажите: если модель добавит поле `approved=true`, станет ли это подтверждением человека?

Интуиция: инструмент — capability приложения, а не полномочие текста. Как в Spring command bus, приложение знает регистрацию handler, схему и текущего пользователя; команда не может назначить себе роль. Описания tools полезны для выбора, но не являются доверенными инструкциями. Даже обнаруженный через MCP tool остаётся только доступной технической возможностью.

Разобранный путь одного `success` в [`walkthrough.py`](../walkthrough.py):

1. **Proposal.** Авторская запись содержит `call_id=call-1`, имя только одного разрешённого локального действия и `pickup_at=19:00`.
2. **Schema.** Проверяется строковый `call-N` и формат `HH:MM`; неожиданный/неверный тип не превращается в команду.
3. **Value / operation limit.** `20:00` структурно похоже на время, но противоречит ограничению «не позже 19:00»; результат `invalid_proposal`, попыток 0.
4. **Permission.** `can_remind` передаётся **доверенной вызывающей частью приложения**, не в proposal, не в сообщении пользователя и не в checkpoint. Без него `permission_denied`, эффектов 0. Аутентификация здесь не реализована.
5. **Approval.** Для действия с последствием проверяется точный target из run ID, версии, call ID, имени tool и args. Digest использует существующий [`approval_digest`](../04_checkpoints_approvals/example.py); hash идентифицирует содержимое, но не доказывает личность согласовавшего.
6. **Execution and result.** Сразу перед имитированным эффектом снова проверяется текущее `can_remind`, счётчики и elapsed budget. Успешный результат создаёт receipt и меняет state; ошибочный результат не считается успехом.

Trace success содержит `proposal → awaiting_confirmation → tool_attempt → reminder_recorded`. В `denied` нет `tool_attempt`; в `changed_args` подтверждение для `19:00` не действует на `18:00`, хотя оба времени допустимы: `approval_mismatch`, attempts 0, effects 0. Нужно заново предложить изменённую операцию и получить новое подтверждение. `refuse` и `cancel` также оставляют effects 0. Возвращаемый ответ содержит только публичное правило G-01; не передавайте модели/пользователю скрытые данные из иных источников. [ACL и границы контекста RAG](../../06_rag/05_grounded_answers/theory.md) уже разобраны в пакете 6.

Типичная ошибка: фильтрация списка tools на этапе discovery воспринимается как достаточная авторизация. Права могут измениться между предложением и вызовом; повторная проверка нужна у эффекта. Другой риск — исполнить строку model output через `eval`, `exec`, shell или произвольный SQL. В этом примере таких инструментов нет. Если инструмент возвращает текст «игнорируй политику», это данные результата, не новая политика.

Практика: [диспетчер инструментов](exercises/tool_dispatch/README.md), ID `agents-tool-dispatch`, оставляет реализацию strict schemas и allowlist ученику; [проверка плана](../exercises/plan_validation/README.md), ID `agents-plan-validation`, проверяет структуру до прав. Здесь нет решения их generic API. Самостоятельная вариация: после подтверждения `19:00` изменить время на `18:00` и обосновать, какой artifact подтверждения теперь нужен.

Самопроверка: что означает «структура верна, значение недопустимо»? Откуда приходит право? Почему recheck перед эффектом? Что делает digest и чего не делает? Какой результат у `approved=true` в тексте модели? Что можно сообщить пользователю после отказа?
