# 06. Оценивать цель и путь отдельно

Практическая проблема: пользователь увидел верное правило G-01. Достаточно ли этого, если процесс перед ответом сделал запрещённый вызов, превысил budget или оставил исход действия неизвестным? Предскажите, какие из `answer`, `success`, `unknown_after_effect` можно назвать завершёнными и безопасными без оговорок.

Интуиция: final text — лишь одна грань. Для workflow нужны отдельные вопросы: (1) достигнута ли пользовательская цель, (2) корректен и полезен ли ответ, (3) допустимы ли действия, (4) соблюдены ли лимиты, (5) восстановился ли процесс после ошибки, (6) не было ли лишних вызовов. В Java/Spring trace показывает путь request через сервисы; при модели дополнительно надо оценить содержание её неопределённого выбора и ответа. `pytest` проверяет локальные механические инварианты, а не понимание ученика и не качество живой LLM.

[`walkthrough.py`](../walkthrough.py) возвращает `trace.json` с **авторскими сценариями**, а не наблюдениями настоящей модели. Поля каждого case: `outcome`, `steps`, `attempts`, `elapsed_ms`, `effects`, `receipt`, `trace`, `checkpoint`. Событие trace фиксирует `before`, `event`, `check`, `action`, `after`, `tool`, разрешённые публичные arguments и `result`; скрытой цепочки рассуждений модели нет. Локальные ms — симуляция, не latency benchmark; `effects` — счётчик учебной операции, не отправленные напоминания.

| Case | Достижение задачи | Policy/limits | Восстановление и лишние вызовы |
| --- | --- | --- | --- |
| `answer` | правило отвечено, напоминание не просили | 0 эффектов | 0 tool attempts |
| `success` | правило + один simulated receipt | точное approval, 2 steps, 1 attempt | 0 лишних |
| `failure_recovered` | итог достигнут | два разрешённых вызова в бюджете | первая ошибка до эффекта, затем успех; повтор уместен |
| `denied`, `invalid`, `changed_args` | напоминание не записано | блокировка до эффекта | 0 attempts; нужен человек/новое предложение |
| `attempt_exhausted`, `step_limit`, `time_limit` | действие не выполнено | лимит соблюдён остановкой | не называть success |
| `unknown_after_effect` | исход для вызывающего неизвестен | нет слепого retry | reconciliation/human, не писать «успех» |
| `known_replay` | известный результат сохранён | повтор не расходует попытку | 1 receipt, 1 effect |

Для сравнения нескольких прогонов задайте знаменатели. `policy_violations`: число фактически выполненных запрещённых calls, не число отклонённых предложений. `limit_violations`: число запусков с превышением, а не остановок на границе. `tool_failure_rate`: ошибки / все начатые tool attempts; если попыток нет, показатель *не определён*, не 0%. `redundant_calls`: повтор эквивалентного вызова внутри одного run — диагностический счётчик; разрешённый retry после ошибки не становится автоматически нарушением. `goal_success` отдельно от answer correctness: `answer` успешно решает вопрос, но не заявляет выполненное напоминание. В `unknown_after_effect` честный outcome важнее красивого final text.

Handoff человеку должен содержать run ID, цель, публичный подтверждённый факт G-01, pending/unknown status, call ID, что проверено, что ещё неизвестно и кто следующий владелец решения. Не переносите full conversation, секреты или «право на действие» как часть текста. Получатель снова проверяет permission и budget. [Существующий handoff example](example.py) показывает Pydantic запись фактов/вопросов, но не делает передачу между сервисами.

Типичная ошибка — поставить `success=true` за красивый ответ, даже когда `unknown_after_effect` требует сверки. Другая — считать локальные fixture labels доказательством полезности реальной модели. Нужны ручная оценка корректности/безопасности на новых случаях, разметка цели и наблюдение реального поведения; ни один JSON parser не проверяет обоснованность ответа.

Практика: [trace evaluation](exercises/trace_evaluation/README.md), ID `agents-trace-evaluation`, оставляет вычисление метрик ученику; [handoff packet](../exercises/handoff_packet/README.md), ID `agents-handoff-packet`, оставляет permission-filtered передачу контекста. Самостоятельная вариация: после `response_lost` пользователь отменил задачу. Сформулируйте честный handoff и критерии проверки до какого-либо повтора; готового решения здесь нет.

Самопроверка: может ли верный ответ сопровождаться policy violation? Чем rejected proposal отличается от unauthorized executed call? Почему нулевое число вызовов не означает 0% ошибок tool? Когда повтор является восстановлением, а не лишним вызовом? Какие сведения нельзя переносить в handoff? Что проверит человек сверх pytest?
