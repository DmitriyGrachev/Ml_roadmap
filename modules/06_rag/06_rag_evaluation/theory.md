# 06. Что измерять и как найти причину ошибки

Практический вопрос: `found` отвечает верно, `missed` воздерживается, `conflict` тоже воздерживается. Одинаково ли хороши эти отказы? Сначала изучите [конкретные traces](../05_grounded_answers/theory.md) и прежний [протокол LLM-оценки](../../05_llm_engineering/05_evaluation/theory.md).

Интуиция: оценивайте **retrieval quality** и **answer quality** отдельно. Пустой context может быть верным решением, если факта нет, и поломкой поиска, если факт есть. Удачная цитата может стоять рядом с неверным утверждением. Предскажите: если система откажет на все вопросы, какой показатель отказов улучшится, а какая полезность упадёт?

Маленький ручной расчёт на двух авторски размеченных запросах этого корпуса. Единица релевантности здесь — **chunk** актуальной публичной ревизии. Для `found` релевантен `G-01@2026-09:p1`, и разрешённый top-1 содержит его: Recall@1 = 1/1 = 1. Для `missed` тот же релевантный chunk существует, но `night shelter` даёт пустой список: Recall@1 = 0/1 = 0. Macro Recall@1 двух запросов = `(1 + 0) / 2 = 0.5`. Связанные ниже упражнения оценивают **document IDs**, а не chunks: при переходе к ним единицу и judgments нужно определить заново, не переносить числитель этого расчёта молча. Случай `absent` с нулём размеченных положительных примеров надо учитывать по заранее выбранной политике, а не незаметно выбрасывать. Это расчёт по реальным case IDs и фактическому retrieval; не универсальный evaluator-код и не обещание статистической точности.

Точный протокол: зафиксируйте source snapshot, access role, query IDs, единицу релевантности, judgments и одинаковый набор запросов для сравниваемых методов. **Recall@k** показывает долю размеченных релевантных единиц среди первых k. **MRR** усредняет `1/rank` первого релевантного результата (или 0 при отсутствии), поэтому заботится о раннем первом попадании, не о полном покрытии. **nDCG@k** суммирует graded gains по позициям с discount и делит на лучший возможный DCG; он отличает сильно и слабо релевантные результаты. В существующем задании gain `2^grade - 1`, а не просто grade. Неполная разметка: unjudged оценивается как grade 0 по контракту, что не доказывает нерелевантность. В ручном примере tie сортируется стабильным chunk ID; дубликатов нет. Для нового эксперимента объявите duplicate/tie/no-positive policy **до** вычислений.

Существующие student-контракты различаются, поэтому не переносите одну реализацию в другую. [Retrieval evaluation](exercises/retrieval_evaluation/README.md), ID `rag-retrieval-evaluation`, отвергает duplicate ranked IDs даже **после k** и включает запросы без положительных judgments в macro denominator с нулём. [Retrieval regression](../exercises/retrieval_regression/README.md), ID `rag-retrieval-regression`, удаляет повторы с сохранением первого появления **до k** и тоже назначает ноль запросу без positives. [Ranking study](../exercises/ranking_study/README.md), ID `rag-ranking-study`, требует строгую уникальность, group-separated train/test и human review; не является автоматическим доказательством победы. Эти требования намеренно не изменены и решения TODO здесь нет.

Для answer quality задайте рубрику по каждому вопросу: точный ожидаемый факт (`G-01`: нет ночного хранения, pickup до 19:00), подтверждение **каждого** claim доступной текущей цитатой, целостность citation ID/quote, полнота/полезность, правильное воздержание или нежелательный отказ. Раздельно смотрите technical success, schema validity и смысловую поддержку из Module 05. Измеряйте реальную задержку (например p50/p95 по заранее выбранному определению) и стоимость по реальному usage и применимой ставке; в этой offline трассе оба значения **NOT_MEASURED**. **LLM-as-judge** может ускорить предварительную рубрикацию открытых ответов, но зависит от своего prompt/model, ошибается на отрицании и стиле и не становится независимой истиной; спорное проверяет человек или внешний факт.

Диагностика по одному наблюдению:

| Симптом | Конкурирующие этапы | Различающая проверка |
| --- | --- | --- |
| Нужный факт отсутствует в выдаче | extraction, chunking, lexical OOV, ACL, cutoff | raw→cleaned text, chunk boundaries, query vector, полный разрешённый rank до k |
| Hit найден, context пуст | старая версия, смена access, delete, budget | current revision/digest/role и `drop_reasons` |
| Контекст содержит оба противоположных правила | конфликт источников, редакционная политика | owner, effective date, ручная adjudication; не выбирать по score |
| Ответ ложен при верном context | generation или смысловая проверка | claim-by-claim support и исходный passage |
| Citation ID/quote существуют, утверждение неверно | поверхностная citation validation | проверка entailment отрицания и условий |
| Служебный материал виден посетителю | ACL до retrieval или recheck/context/cache | разрешённый snapshot и отсутствие защищённого ID/текста в пользовательской трассе |
| Метрика выросла только на финальных запросах | утечка при настройке/сдвиг групп | audit train/dev/final query groups и версии настроек |

Подбор chunk size, query rewrite, k, fusion weights и prompt делайте на **development** запросах; финальный evaluation set отделяйте по семействам намерений, замораживайте и смотрите один раз по принятому протоколу. Сравнивайте baseline и новую конфигурацию на одних query IDs и ролях. Hybrid, reranker или более сложный prompt не обязаны победить baseline; проверяйте качество и цену отдельно.

Ещё одна проектная развилка на том же `G-01`: **direct search** показывает актуальную страницу и хорош, если достаточно открыть правило; **RAG** формулирует короткий ответ с источником, когда это приносит пользу, но добавляет риск unsupported claim; **fine-tuning** меняет веса модели и не подходит как замена регулярному обновлению часов выдачи. Fine-tuning здесь не выполняется. Самостоятельная вариация: посетитель просит только ссылку на действующие часы. Выберите способ, метрику и проверку доступа; затем объясните, как отличите `missed` от `absent` без semantic oracle. Ограничение: маленький синтетический корпус не даёт надёжной оценки качества на реальном трафике.

Локально уже проверяются механизм TF-IDF, rank, ACL и recheck. [Будущая real RAG lab](../../../labs/03_real_rag/README.md) остаётся **PLANNED**: настоящие embeddings, provider/model, persistent index, фактические latency/cost и измеренное качество ещё не сделаны. Следующие Agents/Production материалы тоже не реализуются этим пакетом.

## Источники

- Stanford IR Book, [Evaluation of ranked retrieval results](https://nlp.stanford.edu/IR-book/html/htmledition/evaluation-of-ranked-retrieval-results-1.html), англ.: precision/recall и ranked evaluation; сверяйте с локальным контрактом, а не копируйте определения вместо расчёта.
- scikit-learn 1.9, [ndcg_score](https://scikit-learn.org/1.9/modules/generated/sklearn.metrics.ndcg_score.html), англ.: назначение nDCG; локальное упражнение само задаёт exponential gain и обработку ties, поэтому API не является готовым решением.
