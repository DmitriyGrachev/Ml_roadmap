# 04. Слияние кандидатов и повторная сортировка

Практический вопрос: если [TF-IDF пропустил синоним](../03_lexical_dense_retrieval/theory.md), поможет ли второй метод поиска и как объединить две выдачи? Сначала сформируйте **два разрешённых** списка; после глобального top-k исправить потерю доступного документа уже нельзя.

Интуиция: **hybrid search** даёт нескольким поисковикам шанс предложить кандидатов. **Fusion** объединяет их списки, а **reranker** заново оценивает уже найденный shortlist. Второй этап не возвращает запись, которую никто не предложил. Предскажите: что произойдёт с `G-01`, если он отсутствует в обоих входных списках?

Маленький ручной пример на той же семье сервисных документов — только для механизма, не новый исполняемый student RRF и не заявка на улучшение качества. Пусть после ACL lexical ранжирует `G-01` первым, `G-02` вторым; условный dense метод ранжирует `G-02` первым, `G-01` вторым. При **reciprocal rank fusion (RRF)** с `k=60`, одинаковыми весами, rank с единицы:

```text
RRF(G-01) = 1/(60+1) + 1/(60+2) = 0.032522...
RRF(G-02) = 1/(60+2) + 1/(60+1) = 0.032522...
```

Это tie: нужен заранее заданный стабильный порядок, например chunk ID. Rank-based сумма работает с позициями, поэтому не требуется складывать TF-IDF cosine и dense score на несопоставимых шкалах. Но rank fusion не доказывает поддержку ответа. Если ни одна ветка не предлагает `G-01`, fusion не может восстановить его. Этот числовой пример иллюстрирует формулу; **реальные TF-IDF scores/ranks** в [trace](../walkthrough.py) вычисляются отдельно, dense метод и fusion там не запускаются.

Точный механизм: у каждого поискового branch собственная индексация, snapshot, ACL и candidate limit. Разрешайте источники и пересчитывайте ранги **до** fusion; объединяйте по устойчивым chunk IDs и сохраняйте source/revision. После fusion можно передать ограниченный shortlist в **reranker**: модель оценивает пару (вопрос, документ), обычно тратя больше времени на каждую пару, чем поиск готового вектора. Его score — сигнал порядка, не авторизация и не entailment. Отдельно задайте: сколько кандидатов приходит из каждой ветки, сколько проходит reranker и сколько chunks реально помещается в context. Доступ и текущую ревизию перепроверяют непосредственно перед контекстом даже при cache hit.

Типичная ошибка — сложить `0.525060` из `found` с условным cosine другого метода и объявить победителя. Сравнение методов допустимо лишь на одинаковом наборе запросов, с одинаковыми правами, единицей релевантности и snapshot. Более сложный метод не обязан превосходить lexical baseline. Самостоятельная вариация: dense branch находит `G-07` первым, lexical — `G-01` первым, а `G-07` противоречит `G-01`. Предскажите возможный порядок, затем объясните, почему fusion и reranker сами по себе не разрешают конфликт фактов. Ограничение: ручная таблица RRF не является измерением dense embeddings, а демонстратор не включает reranker.

Практика: [Reciprocal rank fusion](exercises/reciprocal_rank_fusion/README.md), ID `rag-rank-fusion`, требует собственного кода по прежнему контракту. [Context diversity](../exercises/context_diversity/README.md), ID `rag-context-diversity`, заставляет решить, какие разные evidence fragments сохранить при ограниченном context. Не подменяйте эти задания ручным примером выше.

## Источники

- Cormack, Clarke, Büttcher, [Reciprocal Rank Fusion outperforms Condorcet and individual Rank Learning Methods](https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf), англ.: определение rank-based fusion и контекст эксперимента; результат статьи не обещает победу в нашем корпусе.
- scikit-learn 1.9, [cosine_similarity](https://scikit-learn.org/1.9/modules/generated/sklearn.metrics.pairwise.cosine_similarity.html), англ.: сверить, что локальный lexical score — similarity, а не RRF-число.
