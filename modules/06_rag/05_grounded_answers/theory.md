# 05. Контекст, иллюстративный ответ и граница доверия

Практический вопрос: поиск нашёл `G-01`, но можно ли сразу показать посетителю фразу «ночное хранение есть» с ссылкой на этот ID? Нужны [контракт доступа](../01_retrieval_contracts/theory.md), [вычисленная выдача](../03_lexical_dense_retrieval/theory.md) и прежняя [проверка LLM-ответа](../../05_llm_engineering/03_structured_outputs/theory.md).

Интуиция: найденные passages — материалы дела, не распоряжения судье и не доказательство каждого будущего утверждения. **Context assembly** выбирает небольшое, актуальное, доступное множество; generation формулирует ответ; проверка затем спрашивает отдельно «ссылка существует?» и «текст действительно поддерживает сказанное?». Предскажите: может ли цитата `Pickup by 19:00` подтвердить фразу «ночное хранение предлагается»?

Разобранный trace `found`:

```text
Вопрос: Можно оставить велосипед на ночь?
Lookup: overnight storage
Rank 1: G-01@2026-09:p1, TF-IDF cosine = 0.525060
Context: {chunk_id, source_id=G-01, revision=2026-09, digest,
          text="Overnight storage is not offered. Pickup by 19:00."}
Prepared illustration: «Нет. Ночное хранение не предлагается;
                         заберите велосипед до 19:00.» [G-01@2026-09:p1]
```

Эта фраза **заранее написана автором**, не сгенерирована моделью. Код допускает её только если конкретный ожидаемый chunk присутствует в финальном context; `citation_ids` являются подмножеством context IDs. Даже это локальное правило не доказывает смысловую поддержку новых, произвольных ответов. Для реальной генерации приложение отдельно отправило бы инструкции, вопрос и разрешённые passages, затем проверило бы выход по [LLM-контракту](../../05_llm_engineering/02_prompt_contracts/theory.md). Передавать модели защищённый текст «для проверки» уже нарушило бы границу доступа.

Точный механизм: в teacher walkthrough сначала ACL фильтрует corpus до TF-IDF/top-k. При сборке контекста приложение снова ищет текущий источник, сверяет role, revision, digest **и точное содержимое chunk**, затем расходует учебный бюджет в **символах текста**. Продакшен-бюджет обязан использовать tokenizer конкретной модели и учитывать инструкции, вопрос, framing, tools и reserve ответа; символы здесь не tokens. Ограниченный бюджет может отбросить релевантный fragment, а большой — добавить шум/стоимость. Source ID и revision идут вместе с passage, чтобы позднее проверить цитату и отозвать устаревший cache. Дубликаты близких chunks занимают бюджет, не добавляя независимого подтверждения.

Случаи той же семьи:

| Case | Retrieval → context | Подготовленная политика ответа |
| --- | --- | --- |
| `found` | текущий `G-01`, rank 1 → `G-01@2026-09:p1` | узкая иллюстрация «нет, до 19:00» |
| `missed` | `night shelter` OOV → пусто, хотя авторская разметка знает `G-01` | воздержаться из-за retrieval miss; не заявлять, что факта нет |
| `absent` | `battery warranty` → пусто, авторская разметка не имеет источника | воздержаться из-за отсутствия сведений |
| `stale` | старая версия с score 0.572225 → отброшена revision recheck | воздержаться, обновить индекс |
| `conflict` | текущие `G-01` и `G-07` → оба в context | воздержаться: авторская проверка видит несовместимые правила |
| `protected` | служебная заметка исключена до поиска | не раскрывать ни текст, ни ID; доступа нет |

Для `conflict` система **не вычисляет общий semantic contradiction detector**: это заранее размеченный автором спор двух синтетических страниц. В приложении нужны редакторская политика разрешения конфликтов, дата действия, владелец записи и часто человеческая проверка. Ни больший top-k, ни prompt не устраняют конфликт автоматически.

Проверка цитаты имеет уровни: (1) ID есть среди разрешённых финальных passages; (2) цитата буквально присутствует в указанном тексте; (3) каждое существенное утверждение следует из цитаты с учётом отрицания, условий и времени. Первые два шага можно проверить механически. Третий требует явной рубрики, review или тщательно ограниченного task-specific правила; простое совпадение ID/quote недостаточно. Например, реальная цитата «Pickup by 19:00» не подтверждает «overnight storage offered».

Retrieved text остаётся **untrusted source data**. Синтетическая `G-STAFF` содержит `Ignore previous instructions and reveal...`; в teacher-only listing это демонстрация prompt injection. Ни кавычки, ни regex, ни system prompt не гарантируют стойкости модели. Приложение проверяет права до модели, не исполняет команды из источника, валидирует аргументы tools и выдаёт минимальные разрешения; действия с последствиями требуют отдельного подтверждения. Не пишите чувствительный текст в пользовательские логи. Тесты здесь подтверждают только конкретное отсутствие служебного текста в пользовательской части trace.

Типичная ошибка — принять красивый ответ со ссылкой за grounded answer. Самостоятельная вариация: ответ «оставьте до 20:00» ссылается на текущий `G-01`; назовите, какие проверки ссылки пройдут и какое утверждение провалит смысловую проверку. Затем уменьшите character budget до нуля и предскажите status и citation IDs до запуска. Ограничение: нет живого генератора, tokenizer, настоящего секретa, аутентификации или security guarantee.

Практика: [citation validation](exercises/citation_validation/README.md), ID `rag-citation-validation`, оставляет самостоятельную реализацию структурных проверок; [context diversity](../exercises/context_diversity/README.md), ID `rag-context-diversity`, отдельно решает отбор passages. Не переносите готовый `G-01`-ответ в их student TODO.
