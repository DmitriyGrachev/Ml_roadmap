# 02. От страницы до актуального chunk

Практический вопрос: редактор меняет правило выдачи велосипедов. Как не оставить в поиске старую фразу «ночное хранение есть»? Нужны [контракт происхождения](../01_retrieval_contracts/theory.md) и старый [пример плана обновления](example.py); решения learner-заданий здесь нет.

Интуиция: индекс — производная копия документа. Пересчитать только новые строки недостаточно, если старая страница стала короче: её прежний «хвост» останется поисковым результатом. Подумайте заранее: что случится с `p2`, если после правки у `G-01` останется один абзац?

Маленький пример **до → после** из teacher corpus:

```text
raw G-01, revision 2026-09:
Overnight storage is not offered. Pickup by 19:00.

Please bring your collection ticket.

normalization unicode-nfc-paragraphs-ws-v1:
p1 = "Overnight storage is not offered. Pickup by 19:00."
p2 = "Please bring your collection ticket."

chunking one-paragraph-no-overlap-v1:
G-01@2026-09:p1 → p1
G-01@2026-09:p2 → p2
```

Точный механизм: extraction в этом локальном примере читает уже заданный текст, приводит Unicode к NFC, переводит CRLF в LF, делит по пустым строкам и схлопывает пробелы **внутри** абзаца. HTML/PDF parser здесь отсутствует; в настоящем импорте надо сравнить исходник и extracted text, особенно отрицание `not`, часы и таблицы. Digest — SHA-256 от строки `normalization-policy + NUL + chunk-policy + NUL + normalized paragraphs`. Это отпечаток содержимого и политики, не электронная подпись и не доказательство доверенности. В metadata остаются source ID, revision, `public/staff`, digest и номер абзаца. У `G-01` текст `p1` несёт правило вместе со временем выдачи; разрезание по словам могло бы отделить исключение. Этот демонстратор намеренно использует абзацы без overlap; упражнение применяет другие offsets и не получает здесь готовый алгоритм.

Обновление: индекс 2026-08 возвращает `G-01@2026-08:p1` для `overnight storage` с вычисленным cosine `0.572225`. Текущий реестр источника говорит `2026-09`; сборка контекста повторно проверяет revision и digest, отбрасывает кандидат с причиной `stale_revision` и воздерживается. Высокий score устаревшей фразы не спасает её. При переиндексации приложение должно атомарно заменить все chunks `G-01` новой ревизией, убрать старый хвост, удалить tombstoned sources и инвалидировать сохранённые результаты/answer cache, которые ссылались на прежнюю версию. [Старый `source_digest`/`update_plan`](example.py) показывает сравнение snapshot fingerprints и категории `unchanged`, `replace`, `tombstone`; не хранит индекс и не выполняет удаление. Новый parser или политика очистки требует пересчёта digest даже при тех же исходных bytes.

Типичная ошибка — считать `G-01:p1` вечным адресом: после правки он указывает на другое утверждение. Самостоятельная вариация: в новом `G-01` удалён второй абзац и появился новый заголовок без изменения правила. Составьте план: какие идентификаторы исчезнут, что перевычислить, какие cache entries инвалидировать, как проверить отсутствие старого хвоста. Не реализуйте learner TODO здесь. Ограничение: учебная трасса не моделирует транзакционную публикацию индекса и не считает model tokens.

Практика: [chunking](../exercises/text_chunking/README.md), ID `rag-text-chunking`, требует собственные word offsets; [index sync](../exercises/index_sync/README.md), ID `rag-index-sync`, требует самостоятельного update plan. Прежде чем открыть код, предскажите, что теряется при границе между предложением и исключением.

## Источники

- Python 3.12, [hashlib.sha256](https://docs.python.org/3.12/library/hashlib.html#hashlib.sha256), англ.: понять digest от bytes; остановитесь до выбора алгоритма для криптографической подписи — такой задачи здесь нет.
- scikit-learn 1.9, [TfidfVectorizer](https://scikit-learn.org/1.9/modules/generated/sklearn.feature_extraction.text.TfidfVectorizer.html), англ.: `fit_transform` зависит от корпуса; после изменения snapshot веса IDF могут измениться даже для неизменённых chunks. API сверено с локальной 1.9.1.
